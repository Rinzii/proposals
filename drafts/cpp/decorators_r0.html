Abstract

We propose explicit constant-evaluated decorators that compose returned descriptions of one class or function definition.

Applications run from the nearest outward, passing each returned description and its computed annotations to the next application before the compiler installs the final definition. Structural validators may return their input unchanged. The proposed contract permits edits to authored declarations while preserving destination identity, retained bindings, and diagnostic origin. This semantic model remains unimplemented and requires wording and compiler evidence. The examples establish no fundamental expressiveness advantage over existing generation facilities. Independent per-application retention and mandatory checks of completed classes and specializations remain unmet requirements outside this narrow core. Completion checks add an execution point and independent retention may add compiler-managed publication state. Their integration can change the execution model. We request direction on this contract for composing semantic edits while keeping those requirements explicit.

1. Revision history

R0: Initial revision.

2. Introduction

We propose explicit decorators that compose returned descriptions of one class or function definition. A library can change existing members, generate new content, validate its input, or attach computed metadata. The compiler installs the final description at the original definition site after the applications succeed.

[P0707R5] already composes metaclass functions through prototypes. [P4380R0] provides token generation, annotation callbacks, and composable declaration descriptions. The direction here adds a contract for editing an established destination before its definition is installed:

  1. Explicit constant evaluation in a defined application order.

  2. Structural edits with proposed rules for destination identity, retained member bindings, and diagnostic origin.

  3. Computed annotations carried by each returned description.

Independent per-application retention and mandatory checks of completed classes remain requirements outside this narrow core. They are not satisfied by ordinary annotation preservation or structural validation. Their addition can require changes to the execution model.

The examples build on reflection from [P2996R13] and remain design sketches. Provisional-definition queries, edits, and preserved bindings require unimplemented facilities. We use stdx:: for the proposed description operations and token construction from [P4380R0] where stated. Choosing std::meta::info as their carrier does not implement those operations or prove their semantics.

2.1. Encapsulate fields while retaining the authored class

A library can make public fields private and generate read access without moving the class into a prototype namespace. This example is restricted to an ordinary non-template class with public scalar fields and no bases. The library definition shown below must precede the application in a translation unit. The class’s constructor and method remain authored code:

consteval std::meta::info readable_fields(std::meta::info);

struct Node;
using Handle = Node*;
void enqueue(Handle);

[[@readable_fields]]
struct Node
{
    Node* next = nullptr;
    int value = 0;

    Node(Node* link, int initial) : next(link), value(initial) {}
    void enqueue_next() const { enqueue(next); }
};

The transformation changes access on each existing field description and appends a getter. The new operations below return descriptions without installing them:

consteval std::meta::info readable_fields(std::meta::info definition)
{
    auto members = stdx::meta::nonstatic_data_members_of(
        stdx::meta::as_class(definition),
        std::meta::access_context::unchecked());

    for (auto member : members)
    {
        auto type = stdx::meta::type_of(member);
        auto getter_name = std::string{"get_"}
            + std::string{stdx::meta::identifier_of(member)};
        if (stdx::meta::has_member_named(definition, getter_name))
            throw std::meta::exception("Getter name already exists", member);

        definition = stdx::meta::with_access(
            definition, member, stdx::meta::access::private_);

        auto getter = std::meta::id(getter_name);
        definition = stdx::meta::append_members(definition, ^^{
            public:
                auto \(getter)() const noexcept -> \(type)
                {
                    return this->\(member);
                }
        });
    }
    return definition;
}

with_access retains the field’s identity, type, initializer, and position while changing its access. append_members parses generated member fragments in the destination’s context and adds their descriptions. Interpolating a provisional member handle into the getter is also proposed: it denotes that retained member without resolving its spelling again. The interpolation of reflected entities in [P4380R0] does not establish this rule for provisional members. The sketch assumes the stated input restrictions, with a library validator rejecting unsupported inputs before this transform.

The expected final definition is ordinary C++:

struct Node
{
private:
    Node* next = nullptr;
    int value = 0;

public:
    Node(Node* link, int initial) : next(link), value(initial) {}
    void enqueue_next() const { enqueue(next); }

    auto get_next() const noexcept -> Node* { return this->next; }
    auto get_value() const noexcept -> int { return this->value; }
};

Node tail{nullptr, 2};
Node head{&tail, 1};
static_assert(std::is_same_v<decltype(head.get_next()), Handle>);

The constructor still initializes the same fields. The retained call to enqueue keeps its original binding and next still has type Node*. Public field access is deliberately removed. Getter-name collisions fail at the responsible application. This is a concrete contract to implement and test, not a consequence of representing the input with info. A generator that reconstructs this final class can produce the same behavior.

3. Decorator order

A decorator receives a value representing a provisional definition and returns the next description of that definition. Applying decorators requires constant evaluation even if no metadata is queried. Applications belong to class or function definitions rather than forward declarations. [[=constant-expression]] supplies passive annotations.

// The nearest decorator runs first.
[[@schema::derive]]
[[@schema::validate]]
struct User
{
    [[=schema::Field{}]] int id;
    [[=schema::Field{}]] std::string name;
};

schema::validate runs first. schema::derive receives the validated definition and returns the final definition of User. At each application, the compiler evaluates the decorator expression and invokes the resulting callable before proceeding outward. This also specifies the order when an expression constructs a configured decorator.

3.1. Explicit applications select execution

The decorator expression selects the operation to invoke. Passive annotation types remain library inputs. An annotation containing a callable does not schedule it for class completion or template definition. The narrow core carries metadata on the returned definition. It supplies no independent occurrence or result registry. Whether a library convention is sufficient for application history remains an explicit design question in Independent application retention.

4. Transform descriptions before completing the destination

A provisional definition describes declarations, annotations, retained body structure, and generated fragments before the compiler installs the final definition. We propose the following sequence:

  1. Establish the destination entity at the original declaration site, retaining its name and scope.

  2. Make the source definition available as a description with structural queries and source locations.

  3. Evaluate and invoke decorators from the nearest application outward, passing each returned description to the next.

  4. After successful evaluation, install one final definition for the destination, including the annotations retained by the last decorator.

The core ends at installation. Mandatory completed-class checks require the additional execution point discussed in Completed-class requirements.

We propose that a class destination denote the same type throughout this sequence. The current working draft [CXXDRAFT] preserves type identity between an incomplete declaration and its later completion in [basic.types.general]. Its one-definition rule prohibits multiple definitions of that class in one translation unit, [basic.def.odr]. Intermediate descriptions are not additional class definitions.

Under the proposed contract, every returned description retains the destination entity and declaration category. The initial function model also preserves the original function type, signature, and overload identity. Replacing a body does not create a second function through which callers are redirected.

The distinction between a description and an entity does not require a separate C++ representation type. std::meta::data_member_spec already returns std::meta::info representing a data member description. define_aggregate uses those descriptions to define an incomplete destination class and returns the same class reflection, [meta.reflection.define.aggregate]. This provides a limited precedent for descriptions followed by definition. It covers only the members that facility can generate. General class and function descriptions remain proposed facilities.

An erased std::meta::info representation permits category-checked description queries. A distinct definition-description type could instead reject category errors earlier. [P4380R0] section 4 chooses a distinct std::meta::token_sequence for token indexing, concatenation, and iteration while its section 4.1 still uses info for declaration descriptions. These choices can coexist: a definition description can contain generated token fragments without being interchangeable with arbitrary tokens. Parsing requires a scope, lookup context, and supported grammar. No arbitrary lossless token-to-semantic round trip is assumed.

The examples retain std::meta::info as a provisional choice for definition descriptions:

// These proposed queries inspect the definition before installation.
auto class_definition = stdx::meta::as_class(definition);
auto function_definition = stdx::meta::as_function(definition);
auto body = stdx::meta::body_of(function_definition);

The proposed stdx::meta queries below inspect member names, known declared types, and annotations in those descriptions. Member queries take an explicit access context. Queries returning types or annotation values return ordinary reflections that existing reflection facilities can consume.

Existing std::meta::members_of and nonstatic_data_members_of require the class to be complete from a point in the evaluation context, [meta.reflection.member.queries]. They cannot supply the proposed inspection of every intermediate description. Structural inspection needs its own contract without promising that layout, completed member bodies, or every type trait is available during transformation.

4.1. Definition changes stay within the returned description

A decorator may add, remove, or replace declarations within its returned description. It may not invoke facilities that inject declarations or define or modify a class or function during evaluation, including its own destination. This restriction applies throughout the application, including callable construction, helper calls, and cleanup. Ordinary template instantiation and constant metadata materialization remain permitted. The schema example’s std::define_static_string calls are therefore compatible with this model.

The restriction concerns where the decorator supplies definition content. Friend declarations and definitions within a returned class follow ordinary C++ rules, including their namespace membership, [class.friend]. These effects occur when the returned definition is installed. They do not authorize separate injection or modification of an unrelated definition.

During transformation, ordinary operations that inspect an active destination’s unsettled members, bases, layout, conversions, or other definition-dependent properties are diagnosed. This applies even inside a requires expression or substitution and cannot be suppressed by catching a reflection exception. Such probes cannot return a cached negative answer about the provisional class. Changed satisfaction of an identical atomic constraint is already ill-formed under [temp.constr.atomic].

Operations independent of the unsettled definition remain permitted. These include comparing type identities, forming C*, evaluating sizeof(C*), and querying std::is_class_v<C>. A template argument that mentions C does not by itself make the helper invalid. Structural inspection uses description queries. Checks requiring the final class need a separate invocation after completion. The core does not schedule that invocation. The boundary between permitted operations still needs precise wording.

Operations that separately generate companion declarations belong in explicit calls after the definition. An invalid transformation-time operation is not rescheduled for a later event.

4.2. Installation follows successful evaluation

Each explicit application completes its required evaluation and cleanup before the next application begins. Its returned description and metadata must survive that boundary. Failure stops the chain without installing the destination definition. The compiler installs the final definition and retained annotations only after every application and required metadata materialization succeeds.

Ordinary helper calls within an application retain C++ evaluation rules. A nested helper expression therefore need not have the cleanup boundaries of separate explicit applications. Temporaries can survive until the end of the containing full-expression under [class.temporary]. Nested calls in an immediate-function context need not be separate immediate invocations, [expr.const.imm]. Constant evaluation also permits locally caught exceptions when their objects are destroyed within that evaluation, [expr.const.core]. Description storage and lifetime across those boundaries still need specification. This installation rule does not promise rollback of ordinary template instantiations or materialized constants.

4.3. Diagnostics retain the source origin

Descriptions retain enough source origin to identify the decorator application and the declaration, annotation, or body construct being checked. Diagnostics for generated constructs also need an origin policy, such as identifying the generating application. The representation and propagation rules remain to be specified.

Existing source_location_of returns an implementation-defined location for relevant entities and an empty location for data member descriptions, [meta.reflection.names].

4.4. Completion and lookup need explicit rules

Preserving the destination’s identity does not settle the timing of semantic checks. Member function bodies and default member initializers are already complete-class contexts, [class.mem.general]. A rule that runs decorators after the closing brace is insufficient to explain which definition those contexts observe.

We propose checking retained bodies that require the completed class against its final definition while preserving established name bindings and source locations. If a retained construct refers to a removed member, the transform must repair that construct or the compiler must diagnose it. A declaration with the same spelling does not silently acquire those references. For templates, nondependent constructs cannot acquire a different interpretation at instantiation under [temp.res.general]. The representation needed to retain these bindings through transformation remains unresolved.

The proposed contract assigns stable handles to retained members. Changing access preserves a handle, while removing a member and adding another with the same name creates a new one. Intermediate descriptions need representable declaration structure, not the validity of separately completed classes. A temporarily invalid retained use must be repaired before installation. Queries of removed members diagnose the invalid handle rather than finding a replacement by name. Self-names, forward references, and the point at which complete-class contexts acquire bindings need compiler evidence before these rules can be considered settled.

Wording also needs to specify which edits preserve member identity. Generated definitions need rules across translation units and modules. The existing rule for injected definitions requires matching characteristic sequences across translation units, [basic.def.odr]. Constant evaluation alone does not establish that consistency.

The intended module rule reuses an imported completed definition and its stored annotations. Importing a template retains the decorator expressions and provisional definition needed for newly instantiated specializations. Those specializations run the selected definition’s chain under the ordinary instantiation rules. Correspondence between independently instantiated definitions and their retained reflections remains part of the required wording.

4.5. Templates transform when a specialization needs its definition

We propose specialization-time transformation. A template definition records its decorator expressions and provisional definition. Parsing and nondependent lookup occur at template definition. The chain runs when a specialization’s definition is instantiated, after ordinary specialization selection and substitution of the information needed to describe it. For class templates, the ordinary completeness requirements determine implicit instantiation, [temp.inst].

Implicit and explicit instantiation use the selected definition’s chain. A partial specialization has its own chain. An explicit class specialization follows the rule for a non-template class definition. Neither inherits applications from the primary template. This is one transformation stage per instantiated destination, with no promise of once-per-program evaluation across translation units.

Decorators may inspect substituted member types and annotations. Substitution required to form the provisional declaration structure must succeed before transformation. Removing a declaration later cannot rescue an earlier substitution failure. Decorators cannot change the template head, associated constraints, specialization selection, destination identity, or established nondependent bindings. A generated name cannot repair failed nondependent lookup in the template definition. Wording must specify which dependent lookups can observe generated members. Queries requiring the destination’s own completed layout remain unavailable during transformation.

Describing a class specialization does not require instantiating every member body. Ordinary class instantiation leaves non-deleted member-function definitions uninstantiated, [temp.inst]. Later instantiation of a retained or generated body does not rerun the enclosing class’s decorators. References already bound to a removed member must be repaired or diagnosed without silently rebinding them by spelling.

Function-template decorators likewise run when the function definition is required. For both ordinary functions and function templates, the initial scope requires a return type specified independently of the body. Parameter types, return type, exception specification, associated constraints, and overload identity remain fixed. Functions with deduced return types need a separate deduction contract. A failed decorator application is an error in the required definition, not a new means of removing an overload candidate.

This choice checks structural policies and derives metadata for every specialization whose definition is instantiated from a decorated definition. Transforming the template pattern once would instead restrict libraries to symbolic information before concrete member types are available.

4.6. Completed-class requirements remain outside the core

A structural validator checks the description it receives. It can reject duplicate names or unsupported member types without knowing the enclosing class’s layout. A size policy instead needs the completed class. std::meta::size_of requires completeness, [meta.reflection.layout].

The following extension sketch makes the outstanding requirement concrete. bounded requests a final check before a later decorator adds storage:

consteval bool fits_storage(std::meta::info type)
{
    return std::meta::size_of(type) <= 64;
}

consteval std::meta::info bounded(std::meta::info definition)
{
    return stdx::meta::with_postcondition(definition, ^^fits_storage);
}

consteval std::meta::info add_audit_storage(std::meta::info definition)
{
    return stdx::meta::append_members(definition, ^^{
        char audit[65];
    });
}

template<class T>
[[@add_audit_storage]]
[[@bounded]]
struct Packet
{
    T contents;
};

Packet<char> oversized;

The final Packet<char> contains char audit[65], so it exceeds the 64-byte bound regardless of padding. The required outcome is a diagnostic even if nobody queries a descriptor or calls a member. bounded cannot establish that outcome by checking its own input. Placing a layout check in an unused member function also does not make it mandatory for the specialization.

The core does not supply with_postcondition. A completion extension would need to preserve every registered condition through later transformations, run it on each completed specialization produced by the selected decorated definition, and identify both the requesting application and any later conflicting edit. An undecorated specialization would require its own policy. Failure, recursive dependencies, modules, and the permitted effects of predicates need specification. A check-only predicate that cannot inject declarations or modify definitions is the intended restriction.

[P4380R0] section 2.5 already provides on_complete after its pre-completion member-injection hook. A callback can check the final size. Packet therefore demonstrates a requirement, not a counterexample to that proposal. Adding equivalent mandatory checks here introduces a second execution point. It may require compiler-owned condition storage and a change to the execution model.

4.7. Independent application retention remains a separate requirement

A schema migration generator may need the descriptor produced before a field rename as well as the descriptor produced afterward. Applying schema::derive on both sides of that rename gives distinct applications even if both use the same callable. A final singleton SchemaInfo answers what the output contains. It cannot also identify either application’s earlier result after that result has been replaced.

A library could preserve both descriptors in annotations or generate separate immutable declarations. Those alternatives can satisfy a cooperating pipeline. The stronger requirement is retrieval by application identity even when a later transform replaces output metadata. Ordinary annotation preservation is not independent application history and a saved reflection is not necessarily a snapshot of earlier properties.

This requirement remains unmet by the core. A retention extension needs occurrence identity, publication after successful evaluation and cleanup, payload lifetime, reflected-handle semantics, specialization correspondence, and import rules. Publication would also need to say what happens when a later application fails. Keeping the info-to-info signature could still require compiler-managed state associated with an application. A separate return carrier would change composition. Neither option is guaranteed to be a library-only addition.

[P3603R1] section 6.1 explicitly leaves mutable consteval variables to future work. It does not supply a mutable shared cache that resolves these questions. Memoization of equivalent requests, metadata on the final entity, and independently retained application results require separate contracts.

4.8. Static members keep their ordinary inheritance behavior

A retained static member belongs to the final class. When lookup through a derived class finds that member, it denotes the same declaration, [class.member.lookup]. A non-thread-local static data member has one shared object, [class.static.data]. Intermediate descriptions introduce no additional runtime objects.

Deriving from a decorated class neither reapplies its decorators nor copies its computed class annotations onto the derived class.

4.9. Libraries choose the query access context

Configured decorators can receive an access context as an ordinary value. access_context::current() captures the context where its invocation lexically appears, [meta.reflection.access.context]. Calling a helper from a class does not give that helper the class’s private access. An invocation before the class definition also supplies no implicit in-class access grant.

Libraries can deliberately use access_context::unchecked() for unrestricted member enumeration, as illustrated in [meta.reflection.member.queries]. The proposed description queries retain this explicit choice of access policy.

5. Optional metadata is computed on request

A library can also inspect a completed type and derive its metadata when a consumer requests it. [P3394R4] section 3.3 uses passive annotations to configure consumer-driven serialization. This approach needs no decorator application or new execution trigger. It follows the preference in [SD10] section 4.7 for consteval libraries when they provide equivalent usability, expressiveness, and performance.

Passive annotations hold configuration such as field names or binding numbers. The library query performs the expensive validation and derivation. If no use requires that computation, metadata inconsistencies remain undiagnosed. An explicit decorator application requests mandatory checking at the definition. Querying annotations does not implicitly invoke any callable they contain.

The optional query returns a descriptor without changing the queried entity. Layout, member lookup, and function signatures must be settled before ordinary code uses them. Deferring their transformation until a metadata query would let query order affect earlier semantic decisions. Definition staging therefore remains separate from optional metadata derivation.

Completed entities and provisional descriptions require different inspection facilities. Libraries can share validation and derivation algorithms over extracted records. Separate helpers obtain those records from each representation.

5.1. Deferral does not remove all compilation costs

An annotation expression must satisfy the existing constant-expression requirements even when its value is never queried, [dcl.attr.annotation]. Its constructor should store inexpensive configuration because derivation there would defeat deferral. Parsing and ordinary semantic checking also remain necessary. Template definitions can be needed for constant evaluation even when the evaluation does not ultimately use them, [temp.inst]. Heavy derivation belongs in the requested function body, away from constraints, defaults, and type computations that may be needed earlier.

The mechanism introduces no required runtime dispatch or validation call. Generated code and any metadata materialized for runtime use retain their execution and storage costs.

The model does not promise automatic memoization or once-per-program evaluation. Reflection queries can depend on the evaluation context, [expr.const.reflect]. A cache keyed only by entity identity is therefore insufficient for arbitrary queries. A library can explicitly materialize a descriptor at a chosen point, with defined inputs and the ordinary cross-translation-unit consistency requirements. Any retained descriptor must remain valid or be recomputed, as described in Decorator composition.

6. Library uses

The following examples use unchanged-input validators and computed output annotations. Their description queries are proposed facilities with the timing and access rules above.

6.1. Schema generation

The schema helpers inspect public member descriptions using their own access permissions. Each Field remains an input annotation, separate from the computed descriptor:

namespace schema
{
    struct Field
    {
        const char* name = nullptr; // Null keeps the declared field name.

        consteval Field() = default;

        consteval Field(std::string_view field_name)
            : name(std::define_static_string(field_name))
        {
        }
    };

    struct FieldInfo
    {
        const char* name;
        std::meta::info type;
    };

    struct SchemaInfo
    {
        std::meta::info fields;
    };
}

Field{} retains the null default, which selects the declared name. Field{"user_id"} promotes its name before annotation formation. A raw pointer to a string literal would fail the constant-template-argument requirements used by reflect_constant, [temp.arg.nontype]. An explicitly empty name remains distinct from the null default so validation can reject it.

The omitted library helpers reject misplaced Field annotations and empty or duplicate names. describe_fields preserves declaration order and stores names in static storage with std::define_static_string [P3491R3].

namespace schema
{
    consteval std::meta::info validate(std::meta::info definition)
    {
        check_fields(stdx::meta::as_class(definition));
        return definition;
    }

    consteval std::meta::info derive(std::meta::info definition)
    {
        // Inspect provisional members without requiring class layout.
        auto fields = describe_fields(stdx::meta::as_class(definition));
        auto descriptor = SchemaInfo{
            std::meta::reflect_constant_array(fields)
        };

        // Carry the computed schema with the returned definition.
        return stdx::meta::with_replaced_annotation(
            definition,
            std::meta::reflect_constant(descriptor));
    }
}

The proposed with_replaced_annotation helper removes every annotation in the description whose value has the supplied constant’s type, then appends the new value. It preserves other annotations in their relative order. This is the library policy for the singleton descriptors in these examples. It does not make annotations generally unique by type. Deriving a schema again therefore replaces its earlier SchemaInfo, including after a structural change.

reflect_constant_array returns a reflection of a template parameter object containing the field descriptors.

reflect_constant requires a cv-unqualified, copy-constructible structural type other than a reference type. The supplied value must also be valid for the invented template argument, [meta.reflection.result].

Failure of the required constant evaluation makes the program ill-formed.

After definition, consumers retrieve stored metadata without repeating validation or derivation:

// Retrieve retained metadata without running the decorators again.
constexpr auto annotation = std::meta::annotations_of_with_type(
    ^^User, ^^schema::SchemaInfo)[0];

constexpr auto descriptor =
    std::meta::extract<schema::SchemaInfo>(annotation);

6.2. Primary key validation

The primary-key validator counts annotations across public non-static data member descriptions and reports errors with std::meta::exception [P3560R2].

namespace schema
{
    struct PrimaryKey {};

    consteval std::meta::info validate_primary_key(std::meta::info definition)
    {
        auto class_definition = stdx::meta::as_class(definition);
        auto access = std::meta::access_context::current();
        std::size_t count = 0;

        for (auto member : stdx::meta::nonstatic_data_members_of(class_definition, access))
            count += stdx::meta::annotations_of_with_type(member, ^^PrimaryKey).size();

        if (count > 1)
            throw std::meta::exception("At most one primary key is permitted", class_definition);

        return definition;
    }
}

[[@schema::validate_primary_key]]
struct Invoice
{
    [[=schema::PrimaryKey{}]] int invoice_id;
    std::string customer;
};

[[@schema::validate_primary_key]]
struct Batch
{
    // Expected error: the annotation applies to both declarators.
    [[=schema::PrimaryKey{}]] int batch_id, sequence;
};

Invoice passes. Batch fails because its annotation applies to both declarators. Repeated annotations on one member also fail.

6.2.1. Child annotations require an explicit parent validator

A parent decorator can also validate annotations on base relationships or function parameters once the corresponding description queries are specified. Omitting the parent decorator performs no such check. Definition-only applications also leave declaration-only functions outside this mechanism.

Parameter queries need an additional decision. Existing annotations_of gathers annotations from reachable declarations of the corresponding parameter, [meta.reflection.annotation]. Occurrences written on the current definition need to be distinguished from that accumulated set. The parameter-description contract remains open.

A library marker that requires a pointer parameter would validate its declaration but would not itself enforce non-null arguments.

6.3. Guard validation

GuardedBy can name a public non-static data member declared later in the class:

namespace locking
{
    struct GuardedBy
    {
        const char* member_name;

        consteval GuardedBy(std::string_view name)
            : member_name(std::define_static_string(name))
        {
        }
    };

    consteval std::meta::info validate_guards(std::meta::info definition)
    {
        auto class_definition = stdx::meta::as_class(definition);
        auto members = stdx::meta::nonstatic_data_members_of(
            class_definition, std::meta::access_context::current());

        for (auto member : members)
            for (auto annotation : stdx::meta::annotations_of_with_type(member, ^^GuardedBy))
            {
                auto guard = std::meta::extract<GuardedBy>(annotation);
                bool found = false;
                for (auto candidate : members)
                    if (stdx::meta::has_identifier(candidate)
                        && stdx::meta::identifier_of(candidate) == guard.member_name)
                        found = true;

                if (!found)
                    throw std::meta::exception("GuardedBy names a missing member", member);
            }

        return definition;
    }
}

[[@locking::validate_guards]]
struct Connection
{
    // The guard may appear later in the same definition.
    [[=locking::GuardedBy{"mutex"}]] int refcount = 0;
    [[=locking::GuardedBy{"mutex"}]] bool connected = false;
    std::mutex mutex;
};

Missing or misspelled member names fail validation. The check does not inspect guard types or locking within function bodies.

6.4. Command validation

cli::Command accepts a non-member function of type void(command_context&) or void(command_context&) noexcept without changing its body. Comparing function types also rejects variadic functions.

struct command_context
{
    std::ostream& out;
};

namespace cli
{
    struct CommandInfo
    {
        const char* name;
        bool is_noexcept;
    };

    struct Command
    {
        const char* name;

        consteval Command(std::string_view command_name)
            : name(std::define_static_string(command_name))
        {
        }

        consteval std::meta::info operator()(std::meta::info definition) const
        {
            using signature = void(command_context&);
            using nothrow_signature = void(command_context&) noexcept;
            auto function_definition = stdx::meta::as_function(definition);
            auto function_type = stdx::meta::type_of(function_definition);
            // Exact function-type checks also exclude variadic signatures.
            if (stdx::meta::is_class_member(function_definition)
                || (!std::meta::is_same_type(function_type, ^^signature)
                    && !std::meta::is_same_type(function_type, ^^nothrow_signature)))
                throw std::meta::exception(
                    "Command requires a non-member void(command_context&) function", function_definition);

            return stdx::meta::with_replaced_annotation(
                definition,
                std::meta::reflect_constant(CommandInfo{name, stdx::meta::is_noexcept(function_definition)}));
        }
    };
}

[[@cli::Command{"status"}]]
void status(command_context& context)
{
    context.out << "Ready\n";
}

6.5. Material resource bindings

A rendering library can derive a shader resource layout from a material declaration. In this example, each public direct non-static data member represents one resource visible to the fragment shader. The library requires a unique set and binding pair for each resource.

The omitted UniformBuffer, SampledTexture2D, and Sampler wrappers are library types. MaterialParameters is the application’s material parameter type. The omitted describe_binding helper requires exactly one Binding annotation per inspected member, rejects unsupported resource types, and returns the slot and resource kind.

namespace gfx
{
    struct Binding
    {
        unsigned set;
        unsigned binding;
    };

    enum class ResourceKind { uniform_buffer, sampled_texture, sampler };

    struct BindingInfo
    {
        Binding slot;
        ResourceKind kind;
    };

    struct BindingLayout
    {
        std::meta::info bindings;
    };

    consteval std::meta::info material(std::meta::info definition)
    {
        auto members = stdx::meta::nonstatic_data_members_of(
            stdx::meta::as_class(definition),
            std::meta::access_context::current());
        std::vector<BindingInfo> bindings;

        for (auto member : members)
        {
            auto entry = describe_binding(member);
            // Resource slots must be unique even when their types differ.
            for (auto previous : bindings)
                if (previous.slot.set == entry.slot.set
                    && previous.slot.binding == entry.slot.binding)
                    throw std::meta::exception(
                        "Duplicate material resource slot", member);
            bindings.push_back(entry);
        }

        auto layout = BindingLayout{
            std::meta::reflect_constant_array(bindings)};
        return stdx::meta::with_replaced_annotation(
            definition, std::meta::reflect_constant(layout));
    }
}

[[@gfx::material]]
struct Material
{
    [[=gfx::Binding{1, 0}]] gfx::UniformBuffer<MaterialParameters> parameters;
    [[=gfx::Binding{1, 1}]] gfx::SampledTexture2D albedo;
    [[=gfx::Binding{1, 2}]] gfx::Sampler sampler;
};

constexpr auto layout = std::meta::extract<gfx::BindingLayout>(
    std::meta::annotations_of_with_type(
        ^^Material, ^^gfx::BindingLayout)[0]);

Material retains its input annotations and gains a BindingLayout that a renderer can translate into backend resource bindings. Changing the sampler’s slot to Binding{1, 1} makes the definition fail with "Duplicate material resource slot", even if no consumer queries the layout.

Derivation uses declared resource types and explicit binding numbers without member offsets or completed class layout. Shader interface compatibility and device limits require separate checks by the rendering library.

6.5.1. The same binding policy can be checked on demand

To defer checking Material, omit [[@gfx::material]] and replace the stored-layout retrieval above with:

// Without the decorator, checking occurs only when this query is required.
constexpr auto requested_layout = gfx::bindings_for<Material>();

The omitted bindings_for helper uses ordinary reflection to extract the declared bindings and apply the same library policy. It returns a BindingLayout without attaching an annotation or modifying the class. Duplicate slots are diagnosed when this computation is required. Without the query, the binding policy does not prevent ordinary use of the completed class.

6.6. Composition carries current metadata by library policy

A decorator can call other decorators and pass each returned definition to the next. Serialization can exclude a field from its descriptor while retaining that field as ordinary program state. The proposed schema::Transient annotation below is a passive input to describe_fields:

namespace schema
{
    struct Transient {};
}

consteval std::meta::info prepare_schema(std::meta::info definition)
{
    definition = schema::validate(definition);
    return schema::derive(definition);
}

[[@prepare_schema]]
struct Session
{
    [[=schema::Field{}]] int id;
    [[=schema::Transient{}]] int cached_hash = 0;
};

For this policy, describe_fields omits members marked Transient and diagnoses a member marked both Field and Transient. The final schema contains id. The final class still contains cached_hash. Serialization policy does not remove runtime storage.

Each transform specifies which annotations it preserves or recomputes. A transform that changes schema inputs must invalidate or recompute the descriptor before publishing it as the current schema. The singleton replacement policy makes that responsibility visible but does not enforce it for arbitrary decorators. Intermediate records that a cooperating library preserves are still output annotations, subject to subsequent edits.

Saving an entity reflection does not freeze the properties observed by later queries. For example, is_complete_type depends on the evaluation context, [meta.reflection.queries]. References to removed provisional members also require the identity rules described in Completion and lookup.

Validation applies to the description passed to that validator. Structural validation of final invariants belongs after the relevant edits. Completed-layout invariants require the separate completion mechanism that the core leaves unresolved.

6.7. Companion aggregates

A separate namespace-scope consteval block can use the schema to define a companion aggregate. Defining that second entity lies outside the decorator’s permitted effects:

struct UserRow;

consteval
{
    constexpr auto annotation = std::meta::annotations_of_with_type(
        ^^User, ^^schema::SchemaInfo)[0];
    constexpr auto descriptor = std::meta::extract<schema::SchemaInfo>(annotation);

    std::vector<std::meta::info> members;
    for (auto field : [:descriptor.fields:])
        members.push_back(std::meta::data_member_spec(field.type, {.name = field.name}));

    // Defining a second entity requires work outside the decorator.
    std::meta::define_aggregate(^^UserRow, members);
}

static_assert(std::is_same_v<decltype(UserRow::id), int>);

UserRow uses the schema’s names, types, and declaration order. Serialization names containing punctuation need separate C++ identifiers. Matching the schema does not require matching User’s object layout.

7. Prior work and alternatives

Other languages and earlier C++ proposals provide precedents for decorator composition and definition transformation. The choice here concerns how transformations compose and which effects an application permits.

7.1. Other languages provide composition and transformation precedents

Runtime decorators, syntax macros, and transformations of reflected definitions differ in what an operation receives and what its result can replace.

7.1.1. Python and TypeScript compose decorated values

Python applies function and class decorators from the nearest outward. Each returned value passes to the next decorator. The final value is bound to the declared name. [PYTHONDECORATORS] This supplies a direct precedent for return-value composition. Python operates on runtime function and class objects. Our proposed operations instead transform provisional definitions during constant evaluation while retaining the destination entity. The shared application order does not establish identical expression-evaluation or cleanup rules.

The decorator model documented in TypeScript 5.0 also applies method decorators from the nearest outward. A decorator receives the method and a context object and may return a replacement method. The context’s addInitializer operation separately schedules initialization work. [TS50DECORATORS] Its runtime initialization callbacks differ from the constant-evaluated completion checks considered here.

7.1.2. C# combines attributes with additive source generation

C# custom attributes provide metadata for consumers. Applying one does not itself execute a user-defined compile-time transformation. [CSHARPATTRIBUTES] Roslyn incremental generators can select annotated declarations, inspect syntax and symbols, and add members through partial classes. They can also report diagnostics, though Roslyn recommends separate analyzers for that purpose. Their output is additive and cannot remove existing fields or rewrite existing bodies. [ROSLYNGENERATORS] C# therefore provides prior art for annotation-driven generation and validation. The ordered transformation of an existing definition remains a separate contract.

7.1.3. Rust attribute macros replace syntax during compilation

Rust attribute procedural macros receive token streams for their arguments and the annotated item. The returned token stream replaces that item with zero or more items. Derive macros instead append items after the original definition and can declare inert helper attributes. [RUSTPROCMACROS] These facilities provide precedents for compile-time transformation and passive configuration consumed by an explicit operation. Rust’s replacement contract operates on tokens and permits multiple output items. The contract here returns one description for an established destination entity.

7.1.4. Swift attached macros separate expansion roles

Swift’s attached macro design passes attribute and declaration syntax to expansion functions with declared roles. Member macros add members, peer macros add adjacent declarations, and accessor macros can turn stored properties into computed properties. [SWIFTSE0389] SE-0415 also specifies function-body replacement, with at most one body macro per function. The original body must parse but need not type-check before expansion. [SWIFTSE0415] This is close prior art for the value-object and function-instrumentation examples. Our proposed chain composes whole-definition results while preserving established bindings.

7.1.5. Scala macro annotations preserve the original symbol

Scala 3’s experimental MacroAnnotation facility is particularly close to the proposed representation model. Its transform operation receives reflected definition trees and an optional companion, then returns a nonempty list containing the transformed definition. That definition must retain the original symbol. Additional definitions are permitted under ownership and visibility restrictions. [SCALAMACROANNOTATION] Definition transformation with preserved identity therefore has direct prior art. Our output is restricted to the destination definition, with companion generation performed separately.

These precedents support treating composition, representation, identity, and permitted effects as separate design decisions. The C++ rules for specialization-time transformation and the proposed completion extension still require their own specification.

7.2. Annotation callbacks and explicit decorators have prior art

[P3394R4], Annotations for Reflection, section 4.5 explores callbacks for conditional and composed annotations and completion-triggered formatter generation. It leaves callback syntax, mutation, naming, and registration unresolved. Explicit execution is therefore an existing design question.

[P3587R0], Reconsider reflection access for C++26, section 6.2.2 illustrates a possible Python-like decorator that transforms a class for serialization by generating a constructor and friend access. It supplies prior art for explicit class transformation without specifying a complete decorator mechanism. The return-value composition and effect restrictions proposed here still require their own design.

7.3. Explicit validation

A separate consteval block can validate the completed entity using ordinary reflection. The author must keep that check with the definition. Applying a decorator makes structural validation part of the definition. Validation alone does not establish the need for definition transformation.

7.4. Ordinary assertions cover structural checks, not final layout

A generated class-scope static_assert can check a dependent member type when the specialization is instantiated. It cannot generally inspect the enclosing class’s final layout because it is not a complete-class context, [class.mem.general]. Moving it into an unused member function does not make the check mandatory, [temp.inst].

A following consteval call can inspect a completed class but does not automatically follow future template instantiations. The completion extension would need to address that requirement. Ordinary assertions remain suitable where the checked information is already available. External generation stays explicit so the author selects its scope and position relative to other declarations.

7.5. Prototype composition already exists

[P0707R5] section 3 uses a reflected prototype to generate a class. Section 3.2 applies multiple metaclass functions in listed order through successive prototypes. Both class transformation and composition are therefore prior art. The proposed difference here is an established destination with retained bindings across descriptions.

A naive prototype of Node changes its injected-class-name references to prototype::Node. Copying the resulting pointer type unchanged would give the final class the wrong link type. Copying a retained return this body also needs an account of its new owner. Rebinding self-types can fix the pointer case. A destination-parameterized prototype can defer dependent constructs and generation can emit the retained body in the final class. These alternatives prevent self-reference alone from establishing an expressiveness separation. They also identify the rebinding work that the proposed description contract must handle.

7.6. Generation and completion hooks already exist

[P4380R0], Token Sequence Injection, provides on_template_defined, inject_members, and on_complete in section 2.5. It also provides declaration cloning, composable declaration descriptions, declaration macros, and source-oriented diagnostic examples in sections 2.7, 4.1, 3.6, and 2.10. Those facilities support semantic inspection, generation, and eager checking.

For readable_fields, appending getters with inject_members leaves the earlier fields public. An appended private: label changes only subsequent declarations. The published interface does not specify editing those existing fields' access or preserving their handles through such an edit. That is a direct semantic-edit API gap.

A declaration macro can instead receive the whole source form and generate the expected Node, including its private fields and destination-typed links. A prototype-based generator can also work with an explicit rebinding policy. Declaration cloning helps reconstruct function interfaces. Neither technique is ruled out by the examples here. No fundamental expressiveness separation from [P4380R0] has been established.

Function instrumentation gives the same result under scrutiny. A scope guard inserted at an explicit injection site can preserve the existing function, recursion, and early returns. A declaration macro can wrap a restricted body. The proposed benefit is semantic access to an ordinary authored definition with a specified replacement contract. An initial body-edit facility would preserve the function type and bindings and exclude constructors, coroutines, function-try-blocks, contracts, and deduced return types. Exceptions and cleanup would follow the guard’s ordinary semantics, with a nonthrowing guard required for the sketch.

7.7. A semantic edit contract is the proposed improvement

The proposed library interface combines edits to retained declarations with token fragments for new declarations. For Node, with_access changes the existing fields and append_members adds the getters. Library authors specify those edits without reconstructing the whole class. The token and declaration facilities in [P4380R0] remain useful building blocks.

Design criteria for the proposed semantic edit contract and its alternatives.
Criterion Proposed improvement or remaining test
Semantic clarity State which destination and member each retained reference denotes. Node tests self-types, authored initializers, and the binding of enqueue.
Composability Every application receives the previous returned description. [P0707R5] already composes prototypes and [P4380R0] composes declaration descriptions. The additional contract concerns edits to the original definition.
Practical transformations Demonstrate changes to existing access and retained bodies. Generation can reproduce the restricted examples, so reduced library reconstruction is the claim to test.
Diagnostics Identify the application, original construct, and conflicting generated construct. [P4380R0] already demonstrates source-oriented errors. Diagnostic quality needs comparison in a prototype.
Implementation burden Stable handles, deferred checks, preserved bindings, templates, and modules require compiler work. [P4380R0] reports implemented examples. This core has no implementation and no demonstrated cost advantage.
Reflection compatibility Reuse ordinary type and constant reflections, access contexts, and generated token fragments. Provisional inspection and editing need new operations.

7.8. Executable tests support a limited semantic-edit experiment

A local Clang-based source transformer implements readable_fields and field renaming for ordinary classes with directly spelled public scalar fields. It edits declarations, constructor initializers, and AST-bound uses, reparses the output, and audits selected bindings. Its independently rerun suite passes 69 mixed checks, including 17 clean runtime executions under address and undefined-behavior sanitizers. Three emitted programs pass four available frontends under C++20 with -pedantic-errors. The local evidence bundle, scratch/decorator-prototype, contains the implementation, inputs, emitted programs, commands, diagnostics, and review regressions.

The tests exercise self-references, prior forward declarations, saved function addresses, shadowing parameters, both transformation orders, and stale metadata. Renaming before getter generation changes the getter’s name. Renaming afterward keeps that name and changes its bound field use. Independent review found and verified repairs for cross-file field-identity collisions, missed field references, and sanitizer failure detection. The retained collision reproducer changed an unrelated access’s result from 3 to 8 before repair. Both runtime tests now verify that the unrelated access returns 3.

Ten probes on the actual [P4380R0] experimental compiler produce five successful executions, two compile-only successes, and three intended compilation failures. Member-injection getters and declaration macros, including a rename using explicit field placeholders, succeed. The on_complete hook rejects the oversized completed Packet specialization. A fitting specialization and an uninstantiated template pass. In two negative cases, an injected getter hides an unqualified function or type used in an existing body. Explicit global qualification repairs both and the repaired programs execute successfully.

The local transformer requires already-valid input and uses simulated origin handles and metadata history. Its reconstruction baseline shares the same semantic extractor. The binding audit covers selected references and has explicit unsupported cases. These results do not implement provisional definitions, preserve compiler declaration identity across parses, or establish general binding preservation. Native scheduling, annotation publication, and independent application retention remain unimplemented. The next experiment needs a compiler hook before final semantic completion, with retained declarations in one semantic context.

7.9. An attribute spelling still needs execution semantics

A spelling such as [[transform(schema::derive)]] could be specified to invoke a decorator. Existing attribute rules do not provide that invocation: attribute-token names undergo no name lookup and their order within an attribute-list is insignificant, [dcl.attr.grammar]. Lookup of the argument, mandatory evaluation, and composition order would all need specification. The @ spelling makes that explicit application visible. The definition model is independent of the spelling.

8. Conclusion

We request SG7, EWG, and LEWG direction on explicit constant-evaluated decorators that compose descriptions of one destination before installation. The proposed gain is a defined way to edit authored members while retaining their bindings and diagnostic origin. Existing reflection, token generation, and declaration cloning can support that work. The provisional semantic model still needs implementation evidence and wording.

Independent per-application retention and mandatory completed-class or specialization checks remain unmet requirements outside this core. Completion checks add an execution point and independent retention may add compiler-managed publication state. Their eventual integration can change the execution model.

The next compiler experiment needs to establish the Node contract and compare it with prototype and declaration-macro generation. The examples have not established a fundamental expressiveness advantage over [P4380R0]. They support investigating a direct semantic edit interface whose composition and identity rules library authors can rely on.
