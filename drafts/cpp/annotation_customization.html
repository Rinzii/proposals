Abstract

We propose that if the type of an annotation’s underlying constant provides consteval void operator()(std::meta::annotation_context) const, the implementation invokes that operator after annotation formation. We call such an annotation active. The operator receives the declaration context and may perform compile-time work over it, but cannot alter the annotation or the declaration. Failure makes the program ill-formed. No new syntax, ABI surface or linker protocol is introduced. Several core-language changes are needed and § 15 Wording Impact lists them. One of them is separable from the rest: [expr.const.core] paragraph 2.32 has to admit an annotation invocation, without which an operator cannot inject a declaration. Refusing that leaves the validation half of the facility intact (§ 8.5 Invocation contract).

1. Introduction

The working draft provides typed annotations ([P3394R4]), reflection queries that recover those annotations ([P2996R13]), and a compile-time metadata model based on std::meta::info.

What it does not provide is a way for an annotation to observe the declaration to which it appertains and act on that information during translation. [P3394R4] anticipated that gap and left the shape of the facility open (§ 5.2 The callback P3394R4 anticipated).

We propose the following rule: if the type of an annotation’s underlying constant provides

consteval void operator()(std::meta::annotation_context) const;

the implementation invokes that operator after formation, at a defined semantic point, once for each construct the annotation appertains to. The operator may perform any work available during constant evaluation but cannot alter the annotation or the declaration it is attached to. Failure makes the program ill-formed.

An annotation whose type provides that operator is an active annotation. One whose type does not is passive and behaves exactly as it does today (§ 8.3 Types without the operator).

The most common application is attachment-site validation, but the mechanism is intentionally general.

The target is C++29. Everything the facility builds on shipped in C++26 and nothing else has to be adopted first. Stable names and paragraph numbers cited throughout are those of [N5054].

2. Motivation

Annotations attach typed metadata to declarations in a form that reflection can observe. Many practical uses also require compile-time behavior that depends on the annotated declaration:

  • A serialization-field annotation must reject attachment to anything other than a non-static data member with a non-empty key.

  • A thread-safety annotation must reject a declaration that is not a non-static data member.

  • A command annotation must require a function with a specific signature.

  • A binding annotation must require an exported declaration or a complete type.

Standard C++ has no way to perform any of these checks where the annotation is written so they move instead into ad hoc library code, vendor extensions, macros, or external tooling. Each of those placements separates the check from the declaration it constrains. An author then learns about a violation somewhere other than where they made it.

2.1. Why annotations

Annotations ([P3394R4]) already supply typed values, declaration-local syntax, and standard reflection visibility ([P2996R13]). They require nothing at run time.

A broader declaration-metadata proposal would need new syntax, ignorability rules ([P2552R3]), lookup machinery, runtime exposure, linker interaction, and new query APIs. The facility proposed here needs none of that, because the representation it acts on already exists.

Attributes are the other place this could have gone and they are further from it than they look. Reflecting an attribute at all is a separate C++29 proposal ([P3385R8]). In Sofia EWG preferred it without the metafunction that made an attribute appertain to an entity and the revision after dropped it. An annotation already reflects and already appertains. That is all the operator here needs of it.

2.2. Existing practice

Clang’s thread safety analysis takes annotations such as GUARDED_BY(mu) on a data member and diagnoses violations under -Wthread-safety. Its own documentation says to enable those attributes only with Clang and that they can be safely erased when compiling with other compilers. Microsoft’s SAL covers similar ground: _In_ and _Out_, defined in <sal.h>, are read by Visual Studio code analysis for C++. Qt’s moc reads a header, finds the class declarations carrying Q_OBJECT, and writes a separate C++ source file that must then be compiled and linked with the class. Boost.Describe stays in the source. BOOST_DESCRIBE_STRUCT lists the base classes and public members by hand, beside the type.

Each of these is either tied to one vendor or puts the work in a separate declaration or build step. Making the annotation itself active keeps the check portable and at the declaration site without committing the language to runtime registries or source injection.

3. Design Rationale

3.1. Typed values as the representation

Annotations are already constant expressions whose values are preserved by reflection. Existing queries recover typed annotation values. Keeping the value as the sole metadata representation avoids a second metadata model for the same language feature.

Free-standing functions would separate the payload from its behavior and trait-based designs would add boilerplate while putting that behavior somewhere other than the type that owns the metadata. Raw-reflection designs force a library to reconstruct typed meaning from std::meta::info.

3.2. Why operator()

consteval void operator()(std::meta::annotation_context) const;

The case for operator() over a differently named member, ADL, traits, or a registration mechanism:

  • The mechanism is a general compile-time invocation and a purpose-specific name such as on_attach would be simpler to explain but would narrow the perceived scope without restricting the capability. It would also reserve a new magic member name where operator() reserves none.

  • The cost is the adoption break. A reserved name would be its own opt-in and no existing type would have one, where operator() makes a C++26 type with a viable consteval call operator active without an edit (§ 8.3 Types without the operator). This paper accepts that break and the Open Questions revisit it.

  • An annotation that acts on its declaration context is a callable that takes a context argument. operator() is the standard spelling for one.

  • One operator suffices. Separately named members for separate purposes would cover no more than a single mechanism does, now or as the reflection facilities grow.

ADL widens the discovery surface and makes behavior depend on associated namespaces. Traits move behavior away from the type that owns the metadata. A registration mechanism moves it further still, out of the annotation type and into a compiler-facing plugin (§ 14.4 Java annotation processors). None is appropriate here: the operator is part of the annotation type’s own semantics, not an external adaptation point.

Detection is by overload resolution (§ 8.1 Detecting an active annotation) so an operator() a type already has opts in only if it can be called with an annotation_context, is consteval, and returns void. That rules out ordinary function objects, whose call operator takes something else. A consteval one that is viable for a context and returns something else neither opts in nor passes quietly: it is a hard error (§ 8.1 Detecting an active annotation). It does not rule out a generic operator()(auto), which will match. That case is deliberate and it is not forced. A rule naming annotation_context or a reference to it would admit the const annotation_context& spelling and still reject operator()(auto). A narrower detection rule is therefore available and it would shrink the adoption break (§ 8.3 Types without the operator). This paper takes the broader rule for two reasons. A type whose call operator accepts anything has already said it accepts anything. And detection then needs no rule of its own beyond ordinary overload resolution, which is what keeps a private or inaccessible operator behaving the way the language already says it should (§ 8.1 Detecting an active annotation).

3.3. Signature: consteval void operator()(...) const

3.3.1. consteval

The operator runs during translation. constexpr would leave a runtime-callable operator on the annotation type and would remove the discriminator detection relies on (§ 8.1 Detecting an active annotation). consteval makes compile-time evaluation mandatory, prevents the operator from appearing to be a reusable runtime API, and matches the hard-error annotation model.

3.3.2. void

The operator either completes or fails. void expresses that directly. A bool return would need a separate channel to carry the reason and a string-returning form would duplicate the diagnostics mechanism that already exists. A status object adds weight for no gain. If a library needs a reusable predicate, it can provide one as a separate helper or concept.

3.3.3. const

const is a consequence of the invocation model. The operator is called on a const T (§ 8 Semantic Model) and detection never mentions const at all (§ 8.1 Detecting an active annotation). An implicit object parameter has to be const to bind to that call. An explicit object parameter carries its own qualification in its type instead. A by-value one is also accepted, because copy-initializing it from a const T needs only the copy constructor.

The underlying constant is an object of const type (§ 8 Semantic Model) so whatever the operator does to its object parameter it does to a copy or through a reference to const. Nothing it writes reaches the annotation value. Post-attachment state initialization is the use that wants the model changed and a paper proposing it has to answer where the mutated value goes, which is a design question and not a missing qualifier.

3.3.4. noexcept

An exception specification is not part of overload resolution for a call. The signature therefore names none and detection does not look for one (§ 8.1 Detecting an active annotation). A noexcept operator is detected and invoked like any other.

What it gives up is the diagnostic. An operator reports a violation by throwing (§ 10 Diagnostics) and [except.handle] paragraph 7 calls std::terminate when the search for a handler exits the function body of a function with a non-throwing exception specification. The throw therefore never leaves the operator. The message, the annotation type, and the source location never reach the diagnostic. The program is still ill-formed, because the evaluation cannot complete as a constant expression either way, but nothing in the diagnostic names the rule that was violated.

An operator that only inspects can be noexcept with no observable difference. One that ever rejects should not be. That makes noexcept a bad default without making it an error. This paper therefore leaves it well-formed. Marking the operator noexcept and then throwing still gives a hard error and the mistake does not pass silently. Forbidding it outright would recover the diagnostic named above at the price of rejecting the inspect-only case.

3.4. Context object

annotation_context shows the operator its own value and nothing else. Each member describes the site where the annotation was written:

  • annotation() - the annotation occurrence being invoked.

  • target() - the annotated declaration-like construct.

  • annotation_location() - the source location of the annotation.

  • declaration_location() - the source location of the annotated declaration.

  • is_definition() - whether the invocation is at a defining occurrence.

  • is_exported() - whether the annotated declaration is exported.

  • access() - the reflective access context at the annotation site.

annotation() is what lets an operator find itself. [dcl.attr.annotation] paragraph 3 makes every annotation unique so annotations_of can hand back several reflections whose underlying constants compare equal. Without this member an operator cannot tell which of them is the occurrence it is running for. A rule that should produce a single diagnostic for all of them needs that (§ 6.7 Multiplicity check).

is_definition() reports whether this declaration is the defining one, which is what a rule that must run on a definition needs. It is not a completeness test. An operator that needs the target complete should ask is_complete_type(ctx.target()), because a declaration that defines nothing can still have a complete target (§ 9.1 Incomplete targets). access() is needed because reflective queries can be access-sensitive and should follow the ordinary access model.

The context describes the annotation site. It does not provide mutation or synthesis operations. Those are accessed through their own APIs. Omitted members include enclosing_scope() (derivable from target()), template-argument accessors (duplicated by the reflected target), annotation enumeration (better served by the existing reflection API), and mutation methods (better served by standalone reflection APIs).

3.5. Per-occurrence invocation

Each annotation occurrence is invoked independently, which is the granularity annotations already accumulate at. One occurrence can appertain to more than one construct so the unit is the pair of an annotation and a construct it appertains to. The example in [meta.reflection.annotation] paragraph 4 makes the case concrete with [[=1]] int x, y; and annotations_of(^^x)[0] == annotations_of(^^y)[0]: both variables share one annotation and one reflection. The operator runs once for x and once for y in declarator order, with ctx.target() naming a different variable each time. The parameter and the variable of a parameter-declaration in a function definition are the one pair that does not split, because [dcl.attr.annotation] paragraph 1 makes the annotation apply to both and there is a single construct to report (§ 7.2 target()). Redeclarations and cross-TU ordering already require care without an active annotation in play. Merging occurrences would broaden the design into ordering and ODR. A library can enforce a multiplicity rule within the operator using annotations_of when the annotated entity has one definition, as a class member does. For an entity declared more than once the operator sees only the occurrences reachable at its own invocation point and a rule needing the full set cannot be written this way (§ 9.2 Namespaces and later declarations).

3.6. Manual helpers are insufficient

static_assert and manual helper calls cannot provide a standard semantic point for declaration-relative behavior, automatic invocation tied to the annotation occurrence, or principled diagnostics at the annotation site. The implementation already owns appertainment, formation, and the point at which the annotated construct becomes semantically meaningful. This paper adds one invocation step to that existing machinery.

4. Scope

4.1. Goals

  • Build on adopted annotations.

  • Keep annotations as the sole metadata representation.

  • Add declaration-aware invocation with a small API surface.

  • Define precise invocation timing.

  • Preserve standard reflection as the way annotations are queried.

  • Reuse compile-time diagnostics.

  • Remain compatible with the current annotation materialization model.

  • Introduce no new ABI surface or linker protocol.

  • Remain module-friendly.

4.2. Non-goals

  • New declaration-metadata syntax.

  • A separate library-publication mechanism for named metadata.

  • Runtime registries, discovery tables, or compile-time-to-runtime metadata transport.

  • New declaration injection, token generation, or source rewriting facilities.

  • Replacement of existing standard or vendor attributes.

  • A second metadata query API.

Those are facilities this paper does not add. What it does ask for is that an active annotation be allowed to call the generation facilities the reflection library already provides, which as the draft stands only a consteval block may call (§ 8.5 Invocation contract). Annotation attachment then becomes a trigger for such work without this paper standardizing the work itself (§ 6.6 Reflection-driven synthesis).

5. Relationship to the Existing Design

5.1. Non-ignorability

Annotations are non-ignorable under the existing standard ([P3394R4]): their underlying constants are formed through reflect_constant and are observable through annotations_of. This proposal inherits that property and adds to it. Observability means an annotation cannot be discarded. It does not by itself oblige an implementation to run anything. The rule that the operator must be invoked when present is new wording this paper asks for (§ 15 Wording Impact).

5.2. The callback P3394R4 anticipated

Section 4.5 of [P3394R4], Other Directions We Are Exploring, sketches this facility. It says there is clear value in having an annotation be invoked by the declaration itself and it leaves the shape open. It asks whether the callback runs before the class is complete or after, whether an annotation that is called back needs different syntax from one that is not, whether it may mutate the entity it is attached to, what to name it, and whether it is registered implicitly through a member of the annotation type or explicitly through a registration call. This paper answers each of those. Invocation is after completion for the reasons § 9.5 Alternative: mid-class invocation gives. There is no new syntax, because the operator is detected from the annotation type (§ 8.1 Detecting an active annotation) and an active annotation is written exactly as a passive one is. The operator cannot mutate its target or its own value (§ 3.3.3 const, § 8.5 Invocation contract). It is named operator() (§ 3.2 Why operator()). Registration is implicit. That is the member-based option that section describes and § 3.2 Why operator() gives the case against a registration call.

The two uses that section reaches for first are not served here and that is deliberate. Adding an annotation to only some specializations of a template and composing one annotation out of several both need the callback to add annotations to the declaration it runs on. The context offers no mutation (§ 3.4 Context object) and no operator changes the annotation set it is running on (§ 9.4 Order of invocation) so neither is expressible. The third use is injecting a specialization of std::formatter when the annotated class completes. That needs the callback half and an injection facility beyond define_aggregate. This paper supplies the first and the second stays with [P3294R2].

5.3. Invariant taxonomy

Constructors handle value invariants. The operator handles declaration-relative behavior. Program-global behavior (cross-TU or registry-wide) is outside scope.

Because annotation values must be structural types, the proposal does not claim that every value-level invariant can be enforced through encapsulation.

6. Examples

6.1. Serialization fields

#include <meta>
#include <string>
#include <string_view>

namespace serial
{
    struct Field
    {
        const char* key;

        consteval Field(std::string_view k)
            : key(std::define_static_string(k))
        {
            if (k.empty())
                throw std::meta::exception(
                    u8"serial::Field requires a non-empty key",
                    std::meta::current_function());
        }

        consteval void operator()(std::meta::annotation_context ctx) const
        {
            if (!std::meta::is_nonstatic_data_member(ctx.target()))
                throw std::meta::exception(
                    u8"serial::Field may annotate only non-static data members",
                    std::meta::current_function(),
                    ctx.annotation_location());
        }
    };
} // namespace serial

struct User
{
    [[=serial::Field("user_id")]] int id;
    [[=serial::Field("display_name")]] std::string name;
};

The annotation carries a field key. The constructor rejects an empty key and the operator rejects non-member attachment. The split is the one § 5.3 Invariant taxonomy describes. An empty key is wrong wherever a Field is written and the constructor catches it at formation. Attachment to the wrong kind of declaration is visible only once there is a declaration to look at.

The key is stored as const char* because an annotation value must be a structural type and a pointer into a string literal is not a valid constant template argument. The constructor copies the characters into static storage with define_static_string ([P3491R3]), which yields a pointer that is. Every string-carrying example below uses the same idiom.

6.2. Command signatures

namespace cli
{
    struct Command
    {
        const char* name;

        consteval Command(std::string_view n)
            : name(std::define_static_string(n))
        {
        }

        consteval void operator()(std::meta::annotation_context ctx) const
        {
            if (!std::meta::is_function(ctx.target()))
                throw std::meta::exception(
                    u8"cli::Command requires a function",
                    std::meta::current_function(),
                    ctx.annotation_location());

            auto params = std::meta::parameters_of(ctx.target());
            if (params.size() != 1)
                throw std::meta::exception(
                    u8"cli::Command requires exactly one parameter",
                    std::meta::current_function(),
                    ctx.annotation_location());
        }
    };
} // namespace cli

struct command_context;

[[=cli::Command("build")]]
void build(command_context&);

This rule depends on the annotated declaration’s signature and cannot be expressed by a constructor alone.

6.3. Passive annotation

A type without a matching operator() is passive metadata:

struct Version
{
    int major;
    int minor;
};

[[=Version{2, 1}]]
void api_function();

No invocation happens. The annotation is attached and observable through annotations_of.

6.4. Multi-entity annotation

struct Deprecated
{
    const char* reason;

    consteval Deprecated(std::string_view r)
        : reason(std::define_static_string(r))
    {
    }

    consteval void operator()(std::meta::annotation_context ctx) const
    {
        auto t = ctx.target();
        if (!std::meta::is_function(t) &&
            !std::meta::is_nonstatic_data_member(t) &&
            !std::meta::is_type(t))
            throw std::meta::exception(
                u8"Deprecated may annotate functions, data members or types",
                std::meta::current_function(),
                ctx.annotation_location());
    }
};

struct Widget
{
    [[=Deprecated("use new_field instead")]] int old_field;

    [[=Deprecated("use do_thing_v2 instead")]]
    void do_thing();
};

struct [[=Deprecated("prefer NewWidget")]] OldWidget {};

The operator accepts several entity kinds. The two active annotations inside Widget are invoked at its closing brace and the one on OldWidget at its own (§ 9 Timing Model).

6.5. Class-definition annotation

struct RequireDefaultConstructible
{
    consteval void operator()(std::meta::annotation_context ctx) const
    {
        if (!ctx.is_definition())
            throw std::meta::exception(
                u8"RequireDefaultConstructible requires a class definition",
                std::meta::current_function(),
                ctx.annotation_location());

        if (!std::meta::is_default_constructible_type(ctx.target()))
            throw std::meta::exception(
                u8"annotated class must be default-constructible",
                std::meta::current_function(),
                ctx.annotation_location());
    }
};

struct [[=RequireDefaultConstructible{}]] Config
{
    int timeout = 30;
    int retries = 3;
};

The annotation appertains to the class definition so the operator runs immediately after the closing brace of Config (§ 9 Timing Model) and can query properties that require the full definition.

6.6. Reflection-driven synthesis

#include <meta>
#include <vector>

struct GeneratedLayout;

struct DefineLayout
{
    std::meta::info destination;

    consteval void operator()(std::meta::annotation_context ctx) const
    {
        std::vector<std::meta::info> members;
        for (auto m : std::meta::nonstatic_data_members_of(
                 ctx.target(), ctx.access()))
        {
            if (!std::meta::has_identifier(m))
                throw std::meta::exception(
                    u8"DefineLayout cannot mirror an unnamed member",
                    std::meta::current_function(),
                    ctx.annotation_location());

            members.push_back(std::meta::data_member_spec(
                std::meta::type_of(m),
                {.name = std::meta::identifier_of(m)}));
        }

        std::meta::define_aggregate(destination, members);
    }
};

struct [[=DefineLayout{^^GeneratedLayout}]] User
{
    int user_id;
    bool active;
};

int main()
{
    GeneratedLayout layout{
        .user_id = 7,
        .active = true
    };
}

The operator reads the members of the declaration it is attached to and mirrors them into a second type. define_aggregate ([meta.reflection.define.aggregate]) does the generating. What this paper contributes is the trigger and the declaration context (§ 4.2 Non-goals). The example works because an annotation on a class definition is invoked after the definition is complete (§ 9 Timing Model) so User already has its members when the operator asks for them. It also depends on a change this paper asks for and does not get from the draft as it stands: [expr.const.core] paragraph 2.32 currently lets only a consteval block produce an injected declaration (§ 8.5 Invocation contract).

6.7. Multiplicity check

struct PrimaryKey
{
    consteval void operator()(std::meta::annotation_context ctx) const
    {
        if (!std::meta::is_nonstatic_data_member(ctx.target()))
            throw std::meta::exception(
                u8"PrimaryKey requires a non-static data member",
                std::meta::current_function(),
                ctx.annotation_location());

        std::size_t count = 0;
        for (auto m : std::meta::nonstatic_data_members_of(
                 std::meta::parent_of(ctx.target()), ctx.access()))
            count += std::meta::annotations_of_with_type(m, ^^PrimaryKey).size();

        if (count > 1)
            throw std::meta::exception(
                u8"at most one PrimaryKey annotation per class",
                std::meta::current_function(),
                ctx.annotation_location());
    }
};

struct Record
{
    [[=PrimaryKey{}]] int id;   // ok
    int other_id;
};

struct BadRecord
{
    [[=PrimaryKey{}]] int id;
    [[=PrimaryKey{}]] int other_id;   // ill-formed: two primary keys
};

The operator runs after the closing brace of the enclosing class and sees the annotation set that any other query sees there, including its own occurrence (§ 11 Reflection Integration) so a rule about the whole class is expressible. Each annotation in BadRecord counts two primary keys so either of them failing makes the program ill-formed. Whether an implementation runs the second after the first has failed and so whether the author sees one diagnostic or two is left to the implementation. A library that wants a single diagnostic can narrow it with ctx.annotation(). The operator compares its own occurrence against the first the class carries and stays silent otherwise (§ 7 Proposed Library Interface).

6.8. Thread-safety annotation

struct GuardedBy
{
    const char* mutex_name;

    consteval GuardedBy(std::string_view n)
        : mutex_name(std::define_static_string(n))
    {
    }

    consteval void operator()(std::meta::annotation_context ctx) const
    {
        if (!std::meta::is_nonstatic_data_member(ctx.target()))
            throw std::meta::exception(
                u8"GuardedBy requires a non-static data member",
                std::meta::current_function(),
                ctx.annotation_location());

        bool found = false;
        for (auto m : std::meta::nonstatic_data_members_of(
                 std::meta::parent_of(ctx.target()), ctx.access()))
            if (std::meta::has_identifier(m)
                && std::meta::identifier_of(m) == mutex_name)
                found = true;

        if (!found)
            throw std::meta::exception(
                u8"GuardedBy names a member that does not exist",
                std::meta::current_function(),
                ctx.annotation_location());
    }
};

class Connection
{
    std::mutex mu_;
    [[=GuardedBy("mu_")]] int refcount_ = 0;
    [[=GuardedBy("mu_")]] bool connected_ = false;
};

The operator checks the attachment kind and then checks that the named mutex really is a member of the same class. Because member annotations are invoked after the enclosing class is complete (§ 9 Timing Model), that second check does not depend on whether mu_ happens to be declared before or after the members that name it. The mutex_name field still carries data past the check: a static analysis tool can read it through annotations_of to decide which lock protects which field.

6.9. Export-aware annotation

export module mylib;

struct ApiSurface
{
    int since_version;

    consteval void operator()(std::meta::annotation_context ctx) const
    {
        if (!ctx.is_exported())
            throw std::meta::exception(
                u8"ApiSurface may only annotate exported declarations",
                std::meta::current_function(),
                ctx.annotation_location());

        if (!std::meta::is_function(ctx.target()) &&
            !std::meta::is_type(ctx.target()))
            throw std::meta::exception(
                u8"ApiSurface requires a function or type",
                std::meta::current_function(),
                ctx.annotation_location());
    }
};

export [[=ApiSurface{1}]] void public_api();

// [[=ApiSurface{1}]] void internal_helper();  // would be ill-formed: not exported

This uses ctx.is_exported() to reject attachment to a declaration that is not exported at the annotation site. The check reads the export state at that point and does not account for a declaration that becomes reachable later through export using or public inheritance (§ 7.4 Definition and export state).

6.10. Base-specifier annotation

struct Interface
{
    consteval void operator()(std::meta::annotation_context ctx) const
    {
        if (!std::meta::is_base(ctx.target()))
            throw std::meta::exception(
                u8"Interface must annotate a base-specifier",
                std::meta::current_function(),
                ctx.annotation_location());
    }
};

class Serializable {};
class Printable {};

class Document : [[=Interface{}]] public Serializable,
                 [[=Interface{}]] public Printable
{
    // ...
};

The annotation appertains to each base-specifier. Both annotations are invoked after Document is complete, in base-specifier-list order (§ 9.4 Order of invocation). ctx.target() returns the reflection of the direct base-class relationship, not the base class type itself.

6.11. Function-parameter annotation

struct NonNull
{
    consteval void operator()(std::meta::annotation_context ctx) const
    {
        if (!std::meta::is_function_parameter(ctx.target()))
            throw std::meta::exception(
                u8"NonNull requires a function parameter",
                std::meta::current_function(),
                ctx.annotation_location());

        if (!std::meta::is_pointer_type(std::meta::type_of(ctx.target())))
            throw std::meta::exception(
                u8"NonNull requires a pointer parameter",
                std::meta::current_function(),
                ctx.annotation_location());
    }
};

void process([[=NonNull{}]] const char* input,
             [[=NonNull{}]] char* output);

Each parameter annotation is invoked independently, after the whole declarator, and in parameter-declaration order (§ 9.4 Order of invocation) so a rule relating one parameter to another can be written on either of them. The operator here confirms the parameter has pointer type and downstream tools can use the annotation to drive null-check analysis.

7. Proposed Library Interface

namespace std::meta
{
    struct annotation_context
    {
        annotation_context() = delete;

        consteval info annotation() const;
        consteval info target() const;
        consteval source_location annotation_location() const;
        consteval source_location declaration_location() const;
        consteval bool is_definition() const;
        consteval bool is_exported() const;
        consteval access_context access() const;
    };
} // namespace std::meta

annotation_context is not a structural type ([temp.param]) and its values are consteval-only, the same two properties [meta.reflection.define.aggregate] paragraph 1 gives data_member_options. Non-structural is a choice of its own and it is not inherited from access_context, which [meta.reflection.access.context] paragraph 3 makes structural. A context describes one invocation of one annotation so it should never become an annotation value or a template argument. Making it non-structural is what rules both out.

Consteval-only is the separate property. A consteval-only value makes any object holding it an immediate object. [expr.const.const] paragraph 3 confines an immediate object to a constexpr variable, a template parameter object, or an object whose lifetime begins and ends inside one core constant expression. An operator therefore cannot store the context anywhere that outlives translation and the type needs no lifetime wording of its own.

A class with member accessors is the odd shape for <meta>, where nearly everything is a free consteval function over info. access_context is the precedent and it reads the same way: [meta.reflection.access.context] paragraph 3 takes ac.scope() and ac.designating_class() off the object. A free target_of(ctx) family does not fit, because every free function in [meta.syn] takes info and one taking annotation_context would be the only one that does not. LEWG may still prefer the free-function spelling and the accessors transpose to it without changing anything else in this paper.

Following access_context ([meta.reflection.access.context]) its default constructor is deleted and it declares no constructor of its own. The implicit copy and move constructors remain so an operator can hand its context to a helper. Nothing in the type builds one from scratch and an operator only ever receives one. Implementations may represent it as an opaque handle. All accessors return by value.

7.1. annotation()

Returns the reflection of the annotation occurrence being invoked, which is the element of annotations_of(target()) this invocation belongs to. [dcl.attr.annotation] paragraph 3 makes each annotation unique so the result picks out one occurrence even where several on the same construct carry equal underlying constants. For an annotation on a member injected by define_aggregate it reflects the annotation the injection formed (§ 9.3 Injected members).

7.2. target()

Returns the reflection of the annotated entity or declaration-like construct. A base-specifier is not a declaration. [CWG3092] settled that by rewording [dcl.attr.annotation] paragraph 1 and it is why target() is described as a construct. For base-specifiers, function parameters, and non-static data members, the return value reflects the specific construct. For other entity kinds permitted by [dcl.attr.annotation], including namespaces and enumerators, it reflects that entity.

If an annotation on a function parameter in a function definition also corresponds to the parameter variable, target() denotes the parameter reflection and the operator is invoked once for the pair (§ 3.5 Per-occurrence invocation). variable_of(target()) does not recover the variable. [meta.reflection.queries] paragraph 65.2 makes it throw unless some point in the evaluation context has that function parameter scope as its innermost non-block scope and the point of invocation sits outside the scope (§ 9 Timing Model).

7.3. Locations

annotation_location() returns the source location of the annotation occurrence. declaration_location() returns the source location of the annotated declaration. source_location_of(target()) substitutes for neither. [meta.reflection.names] paragraph 7 makes its result implementation-defined and paragraph 8 recommends only that it correspond to a definition, which is not the annotated declaration when the two are written apart.

An annotation on a member injected by define_aggregate has no annotation site and both accessors report the locus of the injected declaration (§ 9.3 Injected members).

7.4. Definition and export state

is_definition() reports whether the invocation is at a defining occurrence. A base-specifier, a function parameter, an enumerator, and an alias-declaration have no non-defining form. For those it is always true and declaration_location() reports the location of the construct itself. The query means something only where both forms exist, which is a class, a function, or a variable declared without being defined.

is_exported() reports the export status of the annotated declaration at the point of the annotation occurrence. [module.interface] paragraph 2 makes a declaration exported only where an export-declaration contains it and it inhabits a namespace scope, where it is a namespace-definition containing an exported declaration, or where it is a declaration in a header unit that introduces a name. A class member, a function parameter, a base-specifier, and an enumerator are none of those. For them the query reports whether the innermost enclosing namespace-scope declaration is exported. A declaration in a header unit reports true and so does a redeclaration implicitly exported under paragraph 6. The query does not predict whether the declaration may later become observable through other means such as export using or public inheritance. has_module_linkage, has_external_linkage, and has_internal_linkage already cover the linkage half of this and are unaffected.

7.5. Access context

access() returns the reflective access context anchored at the lexical program point of the annotation occurrence, as if by std::meta::access_context::current() evaluated there. The operator uses the ordinary reflective access model and no privileged access is introduced. This query is anchored at the occurrence and the split from the point of invocation is deliberate: an operator should have the access its author wrote for, which for an annotation inside a class body includes that class’s private members and the invocation point sits outside the class (§ 8 Semantic Model).

Calling std::meta::access_context::current() in the operator body is not a substitute. That reports the operator’s own scope and not the annotation site. Every rule an operator writes about its target has to go through ctx.access(), as the examples here do.

The anchor takes one adjustment. [basic.scope.class] paragraph 1 puts only the member-specification in a class scope. A point in the class-head or in the base-clause is therefore not in it and [meta.reflection.scope] paragraph 5 resolves the current scope for such a point outward to the enclosing namespace or enclosing class. Anchoring literally at the occurrence would then give a base-specifier annotation namespace access while the names written beside it are checked with the derived class’s, which is the access the example in [class.access.general] paragraph 7 gives a base-specifier, where checking is deferred until the whole base-specifier-list has been seen. The cost shows up on the first thing a reader tries: write class instead of struct in § 14.3 Rust procedural macros and id is private, nonstatic_data_members_of with a namespace-scope context omits it and MustHaveId rejects the class it was written on. access() for an annotation in a class-head or a base-clause is therefore anchored at a point in the member-specification of the class being defined. Every other annotation is anchored at the occurrence itself.

An annotation on a member injected by define_aggregate has no occurrence to anchor to. There access() returns the context at the locus of the injected declaration (§ 9.3 Injected members), which [meta.reflection.define.aggregate] paragraph 9.2 puts immediately after the core constant expression under evaluation. That point is where the injecting code sits, outside the class being built. [expr.const.reflect] paragraph 3 forbids an injection whose target scope is separated from the point of evaluation by a class scope or a function parameter scope so in any legal case the two share the same enclosing class scopes and the operator is not looking at its target from outside a class that encloses it. An operator that needs more than that should be given what it needs as a value in the annotation instead of reaching for it through access().

8. Semantic Model

After annotation formation, the implementation determines the type T of the underlying constant. If T is a class type and overload resolution for the call expression v(ctx) (where v is an lvalue of type const T and ctx is a prvalue of type std::meta::annotation_context) selects a unique consteval function returning void, the implementation invokes it once at the point the table fixes (§ 9 Timing Model). Overload resolution and the access check on that call are performed in the access context of the annotation occurrence, not of the invocation point (§ 7.5 Access context).

v designates the underlying constant and not a copy of it. There is already an object to name. [temp.param] paragraph 13 makes a template parameter object of class type an object with static storage duration and non-volatile const type and an annotation’s constant is formed the same way through reflect_constant, which leaves an object of type const T for the call to be made on. Naming it settles both value categories, which overload resolution needs and a phrasing in terms of extract<T>(r) would leave open. An operator ref-qualified const && is not viable and one qualified const & is. A parameter of type annotation_context& does not bind to the ctx prvalue and const annotation_context& does.

T is the cv-unqualified type reflect_constant was given under [dcl.attr.annotation] paragraph 2. It is not type_of of the annotation, which can come back const-qualified: annotations_of_with_type compares through remove_const(type_of(e)) ([meta.reflection.annotation] paragraph 5) for that reason and detection uses the same unqualified type.

The invocation needs an entry of its own in [expr.const.defns] paragraph 1. Being an invocation of an immediate function was not enough for a consteval block: [dcl.pre] paragraph 15 already defines its corresponding expression as a call to an immediate function and it was still given its own entry at paragraph 1.3 instead of being left to paragraph 1.4. An annotation invocation is a synthesized call in the same position and wording for this paper should add an entry in the same shape.

It also needs a point of evaluation and the draft gives it none. [expr.const.reflect] paragraph 5 determines the point P for an evaluation of an expression E and its final clause is that "P is the point at which E appears". An annotation invocation appears nowhere. It is synthesized by the implementation and has no lexical position in the source. Every rule that reads P is therefore undefined for it: reachability under [meta.reflection.annotation] paragraph 2 and the locus an injected declaration would be given, which [meta.reflection.define.aggregate] paragraph 9.2 places immediately after a core constant expression that here has no position. The injection restrictions of [expr.const.reflect] paragraph 3 are a separate gap. That paragraph reads a consteval-block-declaration and a P of its own. It does not reach an annotation invocation at all (§ 8.5 Invocation contract).

Wording for this paper has to define P for an annotation invocation and the two candidates behave differently. Setting P to the invocation point from the table (§ 9 Timing Model) is what the rest of this paper assumes. That choice puts the invocation outside the annotated class so the paragraph 3 analysis comes out as described. Setting P to the lexical position of the annotation occurrence would put it inside the class and reverse that outcome. This paper proposes the first. Two things deliberately use the second and the wording should state both splits outright. access() is anchored at the annotation occurrence so that the operator has the access its author wrote for (§ 7.5 Access context). The access check on the synthesized call itself is anchored there too, which is what decides whether a private operator is callable (§ 8.1 Detecting an active annotation).

8.1. Detecting an active annotation

Let T be the type of the underlying constant. T is necessarily a complete structural type at the point of detection because reflect_constant requires it.

If T is not a class type, it has no operator() and the annotation is passive.

If T is a class type, the annotation is active if and only if:

  • overload resolution for the call expression v(ctx), with v an lvalue of type const T and ctx a prvalue of type std::meta::annotation_context, succeeds and selects a unique best viable function

  • the selected function is consteval

  • the selected function returns void

The parameter type need not be annotation_context by value. const annotation_context& or any type to which annotation_context converts is acceptable. A plain annotation_context& is not, since ctx is a prvalue (§ 8 Semantic Model). Detection is by overload resolution, not signature matching.

Nothing in that list mentions const and nothing asks for an implicit object parameter. It does not need to. The call is on a const T. An implicit object parameter therefore has to be const to bind and an explicit object parameter states its own qualification in its type. A by-value explicit object parameter is accepted: it is copy-initialized from the const T so an operator that writes to it writes to a copy (§ 3.3.3 const). static operator() is accepted as well and overload resolution selects it like any other candidate. A static operator sees ctx and not the annotation value, which is what the operators in this paper that read no field of their own are already doing. Rejecting it would mean adding a rule that overload resolution does not need.

A captureless lambda is an active annotation and the design admits it deliberately. [expr.prim.lambda.closure] paragraph 4 makes a closure type structural exactly when the lambda has no lambda-capture and paragraph 7 makes its call operator an immediate function when consteval follows the parameter-declaration-clause. Between them that is enough for

[[= [](std::meta::annotation_context) consteval {} ]] int x;

to satisfy every bullet above. It is the one-off spelling of the facility and it needs no rule of its own. Two consequences want wording. The closure type has no class-specifier for the timing rule to search for (§ 9 Timing Model). And its linkage is unsettled: [basic.link] paragraph 15.1.2 reaches a type introduced by a lambda-expression only within the definition of a TU-local entity, while paragraph 15.2 reaches a type with no name defined outside a class-specifier, function body or initializer without naming lambda-expressions at all. Whether a closure type in a namespace-scope annotation is TU-local under 15.2 is a question the wording has to answer (§ 12.1 Annotation reflections are TU-local).

What is left passive with the first bullet satisfied is a selection that is not consteval, which is the ordinary case of an annotation type that is also a runtime callable. A conversion function to a pointer to function is the form of it worth naming. [over.call.object] paragraph 2 adds a surrogate call function to the candidate set for such a conversion and a surrogate call function is not consteval so the second bullet rejects it and the annotation stays passive. The second bullet reads the candidate overload resolution selected, which is the surrogate so a consteval function at the far end of the pointer does not make the annotation active either.

Two outcomes the bullets would otherwise leave passive are ill-formed instead. If overload resolution for that call is ambiguous and any of the ambiguous candidates is a consteval function returning void, the program is ill-formed. If the selected function is consteval and returns something other than void, the program is ill-formed. Neither has a legitimate passive use. A type that went to the trouble of writing a consteval operator taking a context meant it to run. Treating a near miss as ordinary metadata gives its author no signal at all.

Selecting a deleted function counts as finding the operator and the program is then ill-formed. A deleted consteval void operator()(annotation_context) const is how a type says it must not be used as an active annotation and quietly treating it as passive metadata would defeat that.

An inaccessible one behaves the same way and for the same reason. [class.access.general] paragraph 4 applies access control "only to the function selected by overload resolution" so a private or protected call operator is selected by the bullets above and the access check comes afterward. The annotation is therefore active and the call is ill-formed unless the access context reaches it. That context is the annotation occurrence, not the invocation point (§ 7.5 Access context) so an annotation written inside the class that declares the private operator can call it and the same annotation written elsewhere cannot. Treating inaccessibility as no operator found instead would make an annotation’s meaning depend on where it is written in a way the author did not ask for and would hide a spelling mistake in an access specifier as silently passive metadata.

A signature that is nearly right is the failure mode this invites. The two ill-formed outcomes above catch a near miss that reaches overload resolution. An operator whose parameter type is wrong never becomes a candidate at all and goes through as passive metadata with nothing said. Recommended practice: implementations should warn when lookup finds a consteval operator() on the annotation type that is not a viable candidate for an annotation_context argument. Restricting the recommendation to consteval candidates keeps it off the runtime-callable case.

8.2. Appertainment prerequisite

The operator is considered only for annotations that successfully appertain under [dcl.attr.annotation] and only after the annotated construct has been successfully formed.

8.3. Types without the operator

If the underlying constant’s type does not provide a matching operator(), the annotation behaves as under the existing design.

Compatibility is not total and the exception follows from the design. A type that already carries a consteval call operator viable for an annotation_context argument becomes active when this paper is adopted and starts being invoked at every site where it is used as an annotation. A generic consteval void operator()(auto) const is enough to qualify. That is the half of the break that starts running code. The other half stops compiling: a viable consteval operator returning something other than void is ill-formed under this paper (§ 8.1 Detecting an active annotation). A type in that shape fails at every annotation site instead of changing behavior quietly. Both shapes are legal C++26 today. Only the first changes behavior silently, since nothing at the annotation site has to be edited for the operator to start running. One alternative is an opt-in marker on the annotation type, a base class, or a trait specialization that an annotation author would have to write in addition to the operator. That moves the declaration of intent off the operator and onto a second thing that can be forgotten or mismatched, which is the objection § 3.2 Why operator() already makes to traits and registration. A differently named member such as on_attach escapes that objection, since the name is itself the opt-in and there is no second thing to write. What it costs instead is a reserved name and the narrower scope the name implies (§ 3.2 Why operator()). A narrower detection rule naming annotation_context would shrink the break without removing it, since a call operator taking exactly that type is still legal C++26 today. This paper accepts the break and states it instead. The population at risk is annotation types with a consteval call operator, which are rare because C++26 annotations have only just arrived and the break is loudest at the moment of adoption and does not accumulate later.

8.4. Structural-type restriction

The proposal does not alter annotation formation rules. The underlying value remains subject to the structural-type restriction inherited from reflect_constant. Relaxing that restriction is a separate proposal.

8.5. Invocation contract

The operator is invoked by the implementation, not by user code. Construction of an annotation value in ordinary consteval code does not trigger invocation.

A definition of the operator has to be reachable from the point of invocation. [expr.const.core] paragraph 2.4 makes an invocation of an undefined constexpr function a non-core-constant expression and [module.reach] paragraph 3 says what reaches a given point: a declaration earlier in the same translation unit or one in a translation unit imported before that point. Inside one translation unit that is lexical order. An operator declared in class and defined out of line after an annotated declaration therefore makes that invocation ill-formed. Across a module boundary the import supplies the reachability and nothing further is needed. The common spelling, defined in class beside the data the annotation carries, is unaffected either way. Paragraph 2.4 does not itself say what "undefined" means and CWG should confirm that it reads through reachability.

The operator may return normally (annotation retained) or fail during constant evaluation (program ill-formed). The preferred failure mechanism is throwing std::meta::exception ([P3560R2]). The proposal relies on the same exception-in-consteval model used by the reflection library.

static_assert is usable for context-independent checks. For context-dependent diagnostics, std::meta::exception provides source locations and reflective provenance.

The operator runs in an ordinary constant-evaluation context and may call any available facility. This proposal introduces no new side-effecting facilities and does not prevent use of ones that exist or that future proposals may add. Side effects are the annotation author’s responsibility, as with any consteval code.

Injection is the exception. Everything else in this section follows from the design and this is a request. [expr.const.core] paragraph 2.32 makes an expression that would produce an injected declaration a non-core-constant expression unless it is the corresponding expression of a consteval-block-declaration so under the draft as it stands an active annotation that calls define_aggregate fails and § 6.6 Reflection-driven synthesis does not work. This paper asks for that exception to name an annotation invocation as well. Committee direction against the ask leaves the validation half of the facility intact and removes the synthesis half.

With the exception widened, the restriction on what may be injected should carry over too. [expr.const.reflect] paragraph 3 states its rule in terms of a consteval-block-declaration so it does not reach an annotation invocation as written and wording for this paper should extend it so that the point of invocation (§ 9 Timing Model) plays the part of the block. Where that point sits is what decides the outcome. It is outside the annotated class (§ 9 Timing Model) so Outer’s class scope encloses the scope a class nested in Outer would belong to but not the invocation and paragraph 3.2 makes defining that nested class ill-formed. A class at namespace scope is enclosed by neither that class scope nor a function parameter scope, which is the case § 6.6 Reflection-driven synthesis needs. A parameter annotation comes out the same way. Its point sits outside the function parameter scope (§ 9 Timing Model) so no such scope encloses it and an operator on a parameter may inject at namespace scope. That is the other side of variable_of(target()) throwing (§ 7.2 target()) and one placement decides both. This is the mirror of the paragraph 4 example in which a consteval block inside a class may not define a class outside it.

One further restriction is proposed and unlike the rest of this section it is a choice. The operator shall not define the entity reflected by ctx.target(). [meta.reflection.define.aggregate] paragraph 8.2 already rules the case out wherever the annotated class is complete, since define_aggregate requires a target incomplete from every point in the evaluation context. What is left is the annotation on a class declaration that is not a definition (§ 9.1 Incomplete targets) and there the restriction bites.

The reason is not that the declaration is still being processed. By the table the operator runs after semantic analysis of that declaration (§ 9 Timing Model) and a consteval block written after struct S; may complete S today, since neither clause of [expr.const.reflect] paragraph 3 fires when the block and the class both sit at namespace scope. The reason is that ctx describes one fixed declaration for the length of one invocation. An operator that completes its own target makes two queries in the same body disagree about is_complete_type(ctx.target()) and every later annotation on the same class inherits an ordering question (§ 9.4 Order of invocation) about a definition the annotation itself produced. The cost is that the operator is denied the one thing a consteval block in the same position can do and an author who wants it can write that block instead. EWG may prefer to drop the restriction and accept the change of state mid-invocation.

An operator body is hard to test on its own, because a meaningful annotation_context describes a real annotation site and only the implementation produces one. The testable unit is the check: a library that wants coverage should write it as a consteval function over info and have the operator call that, which also hands users a static_assert-able form of the same rule (§ 3.3.2 void).

9. Timing Model

This paper defines a new program point for each annotated construct and the table below is that definition. [meta.reflection.annotation] paragraph 2 does not already name that point, although it reads at first as though it does. That paragraph makes a declaration’s annotations those reachable from a point in the evaluation context or from a point immediately following the class-specifier of the outermost class for which such a point is in a complete-class context, where "such a point" is the point in the evaluation context. The second alternative therefore fires only when the query itself runs from a complete-class context and [class.mem.general] paragraph 10 limits those to a function body, default argument, default template argument, noexcept-specifier, function-contract-specifier, or default member initializer. An ordinary member annotation sits in none of them so the paragraph names no point for it and the wording this paper needs is its own.

What the paragraph does give is the standard the choice is held to. A query made from outside a class reaches every declaration in its member-specification so invoking a class’s annotations immediately after its class-specifier makes them see exactly what any outside query sees and no view of a class exists that only an active annotation can reach. Code inside the class body reaches an earlier member’s declaration from its own evaluation context and so can see an annotation before its operator has run, which is the cost of choosing this point over an earlier one (§ 9.5 Alternative: mid-class invocation).

One consequence of the choice needs stating outright. The complete-class contexts just listed are processed as though they appeared after the class-specifier and the invocation points of a class’s annotations come before that processing. A consteval block in an in-class member function body therefore sees a class that a member annotation injected. An operator cannot read anything written in a complete-class context of the class it is attached to.

Where each annotated construct is invoked and what is complete at that point.
Annotation written on Invoked Complete at that point
anything in a class member-specification and any base-specifier immediately after the outermost class-specifier that lexically encloses the annotation, searching outward no further than an enclosing function body the bases and members of the annotated construct’s class and of every class enclosing it
a class or union definition outside a class immediately after the closing brace of the class-specifier the definition
an enum definition outside a class immediately after the closing brace of the enum-specifier the definition, including every enumerator
an enumerator immediately after the closing brace of the enclosing enum-specifier every enumerator of that enumeration
a function parameter, the function being declared outside a class immediately after the locus of the declarator, which [basic.scope.param] paragraph 1.1 places outside the function parameter scope the declarator, including parameters written after the annotated one
a function declaration or definition outside a class immediately after the locus of the declarator, before the body if there is one the declarator, not the body
a namespace-definition at the closing brace of that namespace-definition the declarations that namespace-definition contains
any other declaration outside a class after semantic analysis of that declaration the declaration

The point also has to be a position a declaration can occupy, because an operator may inject one there (§ 8.5 Invocation contract). struct [[=X]] S { } s; ends its class-specifier in the middle of a simple-declaration and a locus given immediately after it would sit inside another declaration. Wording has to move such a point to the first position at which a declaration may appear, which for that spelling is the end of the simple-declaration.

The first row wins wherever it overlaps a later one. In struct Outer { enum E { a [[=X]] }; }; the annotation is written on an enumerator that is also something in a class member-specification and the first row puts its invocation after Outer, not after E. The search is over class-specifiers because a class-specifier is the class-head and the member-specification together, which is what brings a base-specifier written in the base-clause under the same rule as a member. The outward search stops at a function body so a class defined inside a member function body starts the search again and its own annotations are invoked after its own class-specifier. A consteval block counts as a function body here. [dcl.pre] paragraph 15 makes its corresponding expression a lambda whose body is the compound-statement. A class defined inside one is therefore a local class in a lambda body and starts its own search.

A lambda’s closure type needs the same treatment and cannot be given it directly, since [expr.prim.lambda.closure] paragraph 1 makes it "a unique, unnamed non-union class type" with no class-specifier for the search to find. Wording for this paper has to treat the closure type as though it had one, the way an injected declaration’s locus stands in for a class-specifier it does not have (§ 9.3 Injected members). With that stand-in the lambda body stops the search wherever the lambda is written, including in a default member initializer or a requires-clause inside a class-specifier. An annotation there is invoked at the end of the stand-in. Every other statement about timing in this paper points here instead of restating the table.

An annotation on a class or union definition belongs in the class-head, after the class-key. On an enum definition it belongs in the enum-head, after the enum-key. struct [[=X]] C { }; annotates C and so does struct Outer { struct [[=X]] Inner { }; }; for Inner. The leading form [[=X]] struct C { }; is ill-formed in both positions, for different reasons. At namespace scope the grammar refuses it: of the simple-declaration alternatives in [dcl.pre] paragraph 1, the one that begins with an attribute-specifier-seq requires an init-declarator-list and a class definition has none. Inside a class it is [class.mem.general] paragraph 18 that refuses it, saying the attribute-specifier-seq in a member-declaration "shall not appear if the optional member-declarator-list is omitted". Every class example in this paper uses the class-head spelling.

An enumeration is the one construct whose completion point is not the place to hang this on. [dcl.enum] paragraph 5 fixes the underlying type of every scoped enumeration and paragraph 6 makes an enumeration whose underlying type is fixed complete immediately after its enum-base, which for enum class [[=X]] E { a, b }; is before a and b have been declared. The table therefore names the closing brace of the enum-specifier and not completeness. The enum-head annotation and the enumerator annotations then share one anchor and can be ordered against each other (§ 9.4 Order of invocation).

The annotation type is a complete structural type at invocation time (reflect_constant requires this) so detection does not depend on the annotated class at all.

9.1. Incomplete targets

A declaration that is not a definition usually leaves ctx.target() incomplete at the point of invocation so only queries well-defined for incomplete types are available and members_of(ctx.target(), ctx.access()) fails. Two cases are not incomplete. An enumeration declared with a fixed underlying type is complete immediately after its enum-base, since [dcl.enum] paragraph 6 says so. That is also why the table anchors enumerations on a brace (§ 9 Timing Model). A redeclaration that follows the definition, as in struct S { }; struct [[=X]] S;, has a complete target although it defines nothing. ctx.is_definition() therefore reports what this declaration is. Whether the target can be queried is a separate question and an operator that wants completeness should ask is_complete_type(ctx.target()).

9.2. Namespaces and later declarations

A namespace has no completion point. namespace N { } can be reopened any number of times, in this translation unit and in others. The operator runs at the closing brace of the namespace-definition the annotation is written on and sees what that definition contains. A later reopening adds declarations the operator already ran without.

[dcl.attr.annotation] paragraph 1 bounds this further than it first looks. An annotation may not be applied where the host scope of the declaration differs from its target scope or to a non-defining friend declaration. That restriction is the resolution of [CWG3124] and it also rules out a block-scope extern, whose host scope is the block and whose target scope is not. An out-of-class member definition and a qualified redeclaration therefore carry none at all. The redeclarations that can contribute one are those written in the same scope.

The same gap is open for any entity declared more than once. [meta.reflection.annotation] paragraph 2 gathers only the declarations reachable at the query point so an annotation on the first declaration of a namespace-scope function is invoked before a later redeclaration contributes its own annotations. annotations_of inside that operator returns only the set visible at that point. A rule that needs the full set cannot be written this way and the alternative is worse: waiting for the end of the translation unit would move every diagnostic to the bottom of the file and would still miss the declarations in other translation units. Class members escape this because a class has exactly one definition, which is why the first row of the table is the useful case and this one is the residue.

9.3. Injected members

Writing an annotation in the source is not the only way to form one. [meta.reflection.define.aggregate] paragraph 9.5.6 gives each member injected by define_aggregate the annotations named in its data_member_options and those annotations have no annotation site anywhere in the program. They are invoked too and the point falls out of the wording that injects them. Paragraph 9.2 puts the locus of the injected declaration immediately after the core constant expression under evaluation and that declaration defines the class. The first row of the table is worded in terms of a class-specifier, which an injected declaration does not have so wording for this paper has to say that its locus stands in for the point immediately after one.

define_aggregate is the only facility in the draft that injects a declaration and this section is written for it. [P4033R1] proposes define_enum with an enumerator_options that carries annotations the same way so an injected enumerator would take the same rule, with the locus of the injected enumeration standing in for the point immediately after an enum-specifier.

The invocations therefore happen after the define_aggregate call has returned and after the evaluation containing it has finished. Whatever made the call, a consteval block or another annotation, cannot catch a failure coming from the annotations it injected and is not reentered by them.

What such an invocation can see needs stating separately, because the locus is not the whole answer. [expr.const.reflect] paragraph 1 gives every injected declaration a synthesized point following the last non-synthesized point in the translation unit. Paragraph 5.5 assembles an evaluation context from the point of evaluation, the synthesized points of its instantiation context, and the synthesized points of injected declarations produced earlier in the same evaluation. The invocation is a separate evaluation from the one that injected. That last clause therefore carries nothing over and wording has to say which synthesized points it gets. [meta.reflection.annotation] paragraph 2 reachability and is_complete_type both answer out of that set, which is why leaving it implicit is not an option.

That leaves a failure mode this paper has to name. Because each invocation is a fresh top-level evaluation and never a nested one, a chain of injections is not bounded by the implementation’s limit on recursive constant evaluation, which only counts depth within a single evaluation. An annotation that injects a class whose member carries the same annotation type produces an unbounded sequence of evaluations and a translation that does not terminate. Reaching that takes a class template. define_aggregate completes a class that is already declared and incomplete. Each round therefore needs a fresh incomplete class to complete and a template is what supplies one every time. Nothing in the current design stops it. One option is an implementation limit on the length of such a chain. That cannot ride on the mechanism the existing limits use. [expr.const.core] paragraph 2.7 works by making an expression that would exceed an implementation limit a non-core-constant expression. A chain of separate top-level evaluations is not one expression, which is the same property that puts the chain out of reach of the recursion limit. A chain limit therefore needs a rule of its own in [dcl.attr.annotation], with an [implimits] entry that lists the quantity and does not supply the rule. The other is a rule that an annotation on an injected member does not itself run its operator, which gives up checking injected annotations and is the trade this section otherwise argues against. This paper does not pick one and EWG should.

The cost is that ctx.annotation_location() has no annotation site to report and can only give the locus of the injected declaration so a diagnostic points at the class that was built, away from the code that asked for the annotation. Exempting injected annotations instead would leave define_aggregate as a way to attach an annotation to a member without running the rule its type defines and an annotation that reaches a declaration should be checked however it got there.

9.4. Order of invocation

The active annotations on one class are invoked in a fixed order, stated recursively over its class-specifier: base-specifier annotations in base-specifier-list order, then every annotation in the member-specification in lexical order, then the annotation on that class’s own definition. An enum-specifier is ordered the same way: the annotations on its enumerators in declaration order, then the annotation on the enum definition itself. A nested class-specifier takes its lexical place among the members and is ordered internally by the same rule. A nested class’s own definition annotation therefore runs after its members and before whatever follows it in the enclosing class. For struct [[=Z]] Outer { struct [[=X]] Inner { [[=Y]] int m; }; }; the order is Y, then X, then Z. Stating the rule recursively is what keeps a class’s internal order independent of where that class is written, since Inner on its own at namespace scope gives Y then X as well.

A class is not the only place several annotations share one point. Annotations on the parameters of one function declarator are invoked in parameter-declaration order, annotations on the enumerators of one enum-specifier in declaration order, the invocations of one annotation across the declarators of one declaration in declarator order (§ 3.5 Per-occurrence invocation), and the annotations produced by one pack expansion in expansion order (§ 9.8 Pack expansions). Each of these needs its own sequence of points for the same reason the class case does.

They do not all run at the same program point. Injection is what makes the difference observable. [meta.reflection.define.aggregate] paragraph 9.2 puts the locus of an injected declaration "immediately after the core constant expression currently under evaluation". If one annotation injects a class and a later one on the same class asks is_complete_type about the injected class, the answer depends on whether that locus precedes the later annotation’s point. A single shared point leaves that undefined and [expr.const.reflect] paragraph 5 does not settle it either, since its clause for injected declarations reaches only evaluations sequenced before the query within one evaluation and these are separate evaluations. The wording therefore needs a sequence of points, one per invocation, in the order above, the way consecutive consteval blocks each get their own.

Order still does not change the annotation set an operator sees. The annotations on a class are fixed by its class-specifier and no operator adds one to the class it is running on so two invocations on the same class agree about that set whatever the order. What the order decides is the side effects and for an annotation that injects a declaration it decides both where that declaration lands and which later ones can see it.

9.5. Alternative: mid-class invocation

An alternative would invoke each member and base-specifier annotation as soon as that construct is semantically meaningful. The violation would then be diagnosed at the member and not at the closing brace. A consteval block or static_assert written later in the same class body could not read an annotation whose operator had not run yet. Under the rule this paper proposes it can: everything inside the class body precedes the invocation point so in-class code sees annotations that have not been validated.

The cost is that an operator could then observe only the part of the class already processed. GuardedBy naming a mutex declared later in the same class would fail (§ 6.8 Thread-safety annotation) and a base-specifier annotation would see only the bases to its left. An operator would also see less of the class than any query made after it so two readers of the same annotation would disagree about the class it is attached to and the rule a library expresses would depend on where in the member-specification its users happened to write the annotation.

Neither point is settled by the existing wording. Both models need a new program point defined for them, since [meta.reflection.annotation] paragraph 2 names one only for queries made from a complete-class context (§ 9 Timing Model). The choice is therefore on the merits and this paper proposes post-completion invocation for the reasons above. Committee feedback on it is welcome.

9.6. Templates

An annotation on a templated entity or on an entity declared within one is invoked once per specialization and not once on the template, whether or not the annotation expression itself is dependent. The template itself is included deliberately, because the draft’s own examples put an annotation there. [meta.reflection.annotation] paragraph 4 spells out template <class T> struct [[=42]] D { }, with annotations_of(^^D<int>)[0] != annotations_of(^^D<char>)[0] and their underlying constants equal. A class template is never complete. Only its specializations are so there is no point at which the table’s rule could fire on the template itself. Deferring every case also avoids asking ctx.target() to denote a templated entity independently of a specialization, which reflection does not offer.

The consequence P3394R4’s example makes concrete is that an identical non-dependent annotation runs its operator once per specialization, on an equal value each time, with only ctx.target() differing. That is what validation wants, since each specialization is a distinct class to check and it is a compile-time cost the paper accepts. Memoizing across specializations is not available to an implementation, because [dcl.attr.annotation] paragraph 3 makes the annotations distinct by construction. The words "or instantiation thereof" in that paragraph came from [CWG3145] and were added for exactly this case.

An annotation on a template that is never instantiated is never checked. That is how every other dependent construct already behaves and the paper accepts it without inventing a separate test for which annotations could have been checked early. An explicit specialization is not instantiated from the template either. The template’s annotation does not run for it and only the annotations the specialization writes for itself do. "Once per specialization" means once per specialization generated from the template.

The recursive order of § 9.4 Order of invocation holds for a class and not for a class template. [temp.inst] paragraph 3.1 instantiates the declarations and not the definitions of member classes and scoped member enumerations. Given

template<class T> struct [[=Z]] Outer { struct [[=X]] Inner { [[=Y]] int m; }; };

instantiating Outer<int> runs Z on its own. X and Y run when Outer<int>::Inner is instantiated, which may never happen. Paragraph 3.2 goes the other way for an unscoped member enumeration. Its definition is instantiated along with the enclosing class so its enumerator annotations do run. Wording has to state both, because the order a reader takes from the non-template case is not the order they get here.

If the same annotation is instantiated in multiple translation units, a well-formed program shall produce identical results, no diagnostic required. Invocation is grounded in the lexical context of the annotation occurrence so an operator that reads only its target and the annotations on it already satisfies this. One that reads a macro or an #include order differing between translation units does not and no implementation can be asked to catch that. This is the requirement [basic.def.odr] places on every inline definition. A consteval member function defined inside its class is implicitly inline so the common spelling of an operator is already covered.

A class template specialization’s annotations are invoked at a point from which the specialization’s definition is reachable so ctx.target() is complete there in the sense of [class.mem.general] paragraph 11. They do not wait for member function definitions to be instantiated.

Which point that is needs saying and the draft offers more than one. [temp.point] paragraph 4 puts a class template specialization’s point of instantiation immediately before the namespace scope declaration or definition that refers to the specialization. Paragraph 1 puts a function template specialization’s immediately after. Paragraph 7 allows a specialization to have points of instantiation in several translation units and allows a class template specialization only one within a translation unit. The difference is observable, because an annotation that injects a declaration lands it relative to whichever point hosts the invocation.

The obvious candidate is the point immediately after the instantiated definition is complete and it does not work. An instantiated definition appears nowhere in the source, which is the same defect that leaves the synthesized call without a point of its own (§ 8 Semantic Model). [expr.const.reflect] paragraph 3.2 then finds no immediate scope and no enclosing scopes to read from it. This paper proposes the point immediately following the namespace-scope declaration or definition that refers to the specialization. That is the shape [temp.point] paragraph 1 already uses for a function template specialization, applied to every specialization. It is a real position at namespace scope, it falls after the code that triggered the instantiation, and the specialization is complete by then. Using paragraph 4’s point for a class template specialization would instead place an injected declaration before the code that triggered the instantiation.

It is a point of invocation and not a point of instantiation. Saying so is what keeps it clear of paragraph 7’s cap of one instantiation point per translation unit for a class template specialization. Wording has to introduce it as a second kind of point.

That also settles the case where a specialization is first needed from inside a constant evaluation, which a consteval block asking is_complete_type or sizeof can do and so can another annotation’s operator. The invocation is not nested in that evaluation. It is deferred to the point above and run as a fresh top-level evaluation like every other one (§ 9.3 Injected members). A failure is attributed to the invocation and the triggering evaluation cannot catch it. Wording has to choose all of this and § 15 Wording Impact lists it.

Invocation failure is a hard error, not substitution failure. Annotations already have that footing: [dcl.attr.annotation] paragraph 4 says "Substituting into an annotation is not in the immediate context" and wording for this paper should put annotation invocation alongside it.

The draft’s own example shows how far a hard error reaches. For

template<class T> [[=T::type()]] void f(T t);
void f(int);
void g() {
  f(0);      // OK
  f('0');    // error, substituting into the annotation results in an invalid expression
}

f(0) is well-formed even though int::type() is not a valid expression, because an annotation is not substituted into while candidates are being formed. Substitution happens once a specialization has been selected. So an annotation on a function template does not remove the overload from consideration and it does not make every call that could have named the template ill-formed. It makes ill-formed the call for which the template is chosen. Invocation failure inherits that shape. The reason to prefer it to substitution-failure semantics is that an annotation whose rule the argument violates would otherwise silently deselect the overload and the caller would get a diagnostic naming some other candidate or none at all.

When "once a specialization has been selected" falls is a date the draft does not give. [temp.inst] paragraph 11 instantiates a declaration of a function template specialization when it is used in a way that involves overload resolution. The example above keeps f(0) well-formed so annotation substitution has to happen later than that declaration. Nothing says how much later. This paper does not depend on the answer, since it hangs its invocation point on the declaration that refers to the specialization, but wording cannot be drafted without it and CWG should be asked.

9.7. Per-occurrence model

Invocation is per occurrence and per construct that occurrence appertains to (§ 3.5 Per-occurrence invocation). No deduplication or merge model is added.

If equivalent annotations appear on multiple declarations of the same entity, each is invoked independently. No reflection-handle identity guarantee is imposed beyond the existing model.

9.8. Pack expansions

Under [dcl.attr.grammar] paragraph 6, an annotation followed by an ellipsis is a pack expansion. Each expanded element produces a unique annotation and each of those is invoked independently.

10. Diagnostics

When an invocation fails, the program is ill-formed and a diagnostic is required.

The from argument of std::meta::exception is a reflection of the function the error came from ([P3560R2]). Inside an operator body that is std::meta::current_function() ([meta.reflection.scope]) and every example here passes it.

Quality-of-implementation guidance:

  • The diagnostic should identify the annotation site.

  • It should include the operator’s message when available.

  • It should note the annotated declaration when useful.

error: serial::Field may annotate only non-static data members
  note: in annotation on member function 'Session::refresh'

An operator has one outcome besides success and it is a hard error. It cannot warn. A rule that only wants to warn has no standard channel today and neither does one that wants to print while it runs. [P2758R5] proposes std::constexpr_warning_str, std::constexpr_error_str, and std::constexpr_print_str for exactly that. It has not been adopted. If it is, an operator can call them like any other consteval code and this paper needs nothing further.

11. Reflection Integration

This paper adds nothing to the metadata query surface:

  • is_annotation(info)

  • annotations_of(info)

  • annotations_of_with_type(info, info)

  • type_of(info)

  • constant_of(info)

Invocation failure makes the program ill-formed before any code outside the enclosing class-specifier can observe the annotation. Two readers see it earlier. Code later in the same class body precedes the invocation point and sees annotations that have not been validated (§ 9.5 Alternative: mid-class invocation). An annotation on an injected member is invoked after the evaluation that injected it has finished. The injecting code sees the annotation formed and cannot catch its failure (§ 9.3 Injected members).

annotations_of inside an operator returns whatever [meta.reflection.annotation] paragraph 2 makes visible at the point of invocation, which is the reason the timing rule picks that point (§ 9 Timing Model) and needs no new rule of its own. For an annotation in a class it is every annotation on every base and member of the class, including the occurrence that triggered the invocation. For an entity declared more than once it is the annotations on the declarations reachable there, which need not be all the entity ends up with (§ 9.2 Namespaces and later declarations). Under [dcl.attr.annotation] paragraph 3 each annotation is unique so repeated annotations appear as distinct reflections and multiplicity rules are expressible (§ 6.7 Multiplicity check).

ctx.annotation() hands back an annotation reflection and not a new kind of thing. is_annotation is true for it and constant_of and type_of answer for it exactly as they do for an element of annotations_of (§ 7.1 annotation()).

12. Modules and Access Control

Two different program points govern an invocation and saying which does what avoids a contradiction. The invocation happens at the point the table fixes (§ 9 Timing Model) and that point supplies reachability and the position an injected declaration is placed relative to (§ 8 Semantic Model). Access is anchored at the annotation occurrence instead (§ 7.5 Access context), not at the module where the annotation type was defined and not at a later importing context. The operator therefore has exactly the access its author granted by writing the annotation where they wrote it: an annotation inside a class body runs with that class’s access and can reach private members and the same annotation type written outside that class cannot. No access is created that the annotation site did not already have.

This paper adds no reachability requirement beyond the one every constexpr call already carries. A definition of the operator has to be reachable from the point of invocation (§ 8.5 Invocation contract) and across a module boundary the import is what supplies that.

12.1. Annotation reflections are TU-local

[dcl.attr.annotation] paragraph 3 says that each annotation or instantiation of one produces a unique annotation, with no qualification on where. [CWG3118] found that this leaves a reflection of an annotation with no feasible mangling, since the same annotation written in a header is a different annotation in each translation unit that includes it and a captured reflection used as a template argument would need a name that is the same in all of them. Modules sharpen it by letting such a reflection cross the boundary directly. [basic.link] paragraph 16 resolves it by making a value TU-local when it "is a reflection value that represents an entity, value, or object that is TU-local, an annotation, a direct base class relationship for which either D or B is TU-local, or a data member description for which T is TU-local".

That rule belongs to annotations and this paper neither restates nor amends it. What matters here is that an active annotation opens no way around it. The operator returns void so nothing it computes leaves by return. annotation_context is not a structural type and its values are consteval-only values (§ 7 Proposed Library Interface) so the context cannot become a template argument or outlive the invocation. The reflections an operator obtains from annotations_of are TU-local exactly where they would be TU-local outside one.

Injection is the case worth naming, because it is the one place an operator hands a reflection to something that persists. data_member_options::annotations does accept an annotation reflection. [meta.reflection.queries] paragraph 1 makes has-type true for an annotation, which is all [meta.reflection.define.aggregate] paragraph 5.6 asks of each element. What stops the reflection from carrying over is paragraph 4.6, which keeps constant_of(r) and discards the rest. An operator therefore cannot move an annotation reflection onto an injected member. It supplies a value and the injected annotation is a new annotation, unique and TU-local on the same terms as one written in the source. If the committee revisits the TU-local rule, an active annotation inherits whatever replaces it and this paper asks for no exception to it.

13. Alternatives Considered

13.1. Not a broader metadata system

A broader system would require surface syntax, ignorability rules ([P2552R3]), lookup machinery, runtime queries, and emission semantics, none necessary for this facility (§ 2.1 Why annotations).

13.2. Not runtime discovery or transport

Runtime tables raise ABI, linker, freestanding/hosted, and cross-TU ordering questions. This facility introduces no such table. The operator returns void and annotation_context is a consteval-only value (§ 12.1 Annotation reflections are TU-local). <meta> is not among the headers a freestanding implementation has to provide ([compliance]) so annotation_context raises no freestanding question of its own.

13.3. Not an annotation the language reads

An annotation can also make the compiler act by having the language itself read it. [P4167R0] takes that route for argument-dependent lookup: an annotation of a type added to <meta> names further associated entities and [basic.lookup.argdep] is changed to consult it. The meaning of that annotation is fixed by the language and the compiler acts on it during lookup. Nothing in this paper expresses it. An operator runs after its declaration is formed, observes it, and changes neither the declaration nor how names are looked up (§ 8.5 Invocation contract) so the two are complementary. An annotation the language reads stays passive under this paper unless its type also provides the operator.

13.4. Not a consteval block

A consteval block ([P3289R1]) already runs arbitrary compile-time code at a point in a class body or at namespace scope and a codebase that owns its own declarations can get much of this paper’s effect by writing one that sweeps annotations_of over the members it cares about. Where that works it works today and needs nothing new, which is the strongest argument against this paper.

What it does not do is carry the trigger with the metadata. Whoever defines serial::Field cannot make its rule apply to a class they do not own so the class author has to remember to write the block and a class that forgets is silently unchecked. An active annotation reverses that: the rule ships with the annotation type and attaching the annotation is what runs it.

A block reaches everything an active annotation reaches. parameters_of, bases_of, and enumerators_of give a block written at namespace scope the same access to a function parameter, a base-specifier, or an enumerator that it has to a data member. Ownership is the only difference.

14. Prior Art

14.1. Python decorators

A Python decorator is a callable applied to a function or class at definition time. The decorator receives the decorated object and may inspect, wrap, or replace it:

def require_one_param(fn):
    import inspect
    if len(inspect.signature(fn).parameters) != 1:
        raise TypeError(f"{fn.__name__} must have exactly one parameter")
    return fn

@require_one_param
def build(ctx):
    pass

The equivalent under this proposal:

struct RequireOneParam
{
    consteval void operator()(std::meta::annotation_context ctx) const
    {
        if (!std::meta::is_function(ctx.target()) ||
            std::meta::parameters_of(ctx.target()).size() != 1)
            throw std::meta::exception(
                u8"function must have exactly one parameter",
                std::meta::current_function(),
                ctx.annotation_location());
    }
};

[[=RequireOneParam{}]]
void build(command_context&);

This proposal shares the core shape: a callable receives the declaration context at the attachment site. The differences are in when the code runs and in what it may do. Python decorators operate on runtime objects and can replace the decorated entity entirely. The operator this paper proposes runs on compile-time reflections, is const, and cannot replace the annotated declaration.

14.2. TypeScript decorators

TC39 decorators, at stage 2.7 in the TC39 proposals index ([TC39-PROPOSALS]) and shipped in TypeScript 5, receive the decorated value together with a context object carrying kind, name, access, and other declaration properties:

function mustBeMethod(_target: any, context: ClassMethodDecoratorContext) {
    if (context.kind !== "method")
        throw new Error("@mustBeMethod can only decorate methods");
}

class Widget {
    @mustBeMethod
    doThing() { }
}

The context object is structurally similar to annotation_context: both describe the attachment site so the receiver can dispatch on declaration properties. Where TypeScript reads named fields off that object, the operator here reaches the declaration through target() and asks the ordinary reflection queries:

struct MustBeMethod
{
    consteval void operator()(std::meta::annotation_context ctx) const
    {
        if (!std::meta::is_function(ctx.target()) ||
            !std::meta::is_class_member(ctx.target()) ||
            std::meta::is_static_member(ctx.target()))
            throw std::meta::exception(
                u8"MustBeMethod requires a non-static member function",
                std::meta::current_function(),
                ctx.annotation_location());
    }
};

The differences are in scope. TypeScript decorators can return a replacement value and participate in a runtime initialization protocol. An active annotation is a compile-time-only facility that cannot replace or modify the annotated declaration.

14.3. Rust procedural macros

Rust’s #[attribute] macros and #[derive(Trait)] macros receive the token stream of the annotated item at compile time and produce a replacement or additional token stream:

use proc_macro::TokenStream;

#[proc_macro_attribute]
pub fn must_have_id(attr: TokenStream, item: TokenStream) -> TokenStream {
    let input: syn::DeriveInput = syn::parse(item.clone()).unwrap();
    if let syn::Data::Struct(data) = &input.data {
        let has_id = data.fields.iter().any(|f|
            f.ident.as_ref().map_or(false, |i| i == "id"));
        if !has_id {
            panic!("struct must have a field named 'id'");
        }
    }
    item
}

#[must_have_id]
struct Record {
    id: i64,
    name: String,
}

The equivalent check here never sees tokens. It interrogates the declaration directly:

struct MustHaveId
{
    consteval void operator()(std::meta::annotation_context ctx) const
    {
        if (!ctx.is_definition())
            throw std::meta::exception(
                u8"MustHaveId requires a class definition",
                std::meta::current_function(), ctx.annotation_location());

        bool found = false;
        for (auto mem : std::meta::nonstatic_data_members_of(
                 ctx.target(), ctx.access()))
            if (std::meta::has_identifier(mem)
                && std::meta::identifier_of(mem) == "id")
                found = true;

        if (!found)
            throw std::meta::exception(
                u8"class must have a member named 'id'",
                std::meta::current_function(), ctx.annotation_location());
    }
};

struct [[=MustHaveId{}]] Record
{
    int id;
    std::string name;
};

Rust proc macros are more powerful, since they operate on tokens and can generate arbitrary code. The operator proposed here works from a typed reflection of the declaration instead of its tokens. Timing also differs. A derive macro receives the whole item so it is not reading a half-built declaration, but it receives it as tokens at expansion time, before the type has a meaning to query. The point this paper defines is a semantic one (§ 9 Timing Model).

14.4. Java annotation processors

Java’s javax.annotation.processing framework allows compile-time inspection of annotated declarations:

@Target(ElementType.METHOD)
@Retention(RetentionPolicy.SOURCE)
public @interface MustReturnVoid { }

// In a separate processor class:
@Override
public boolean process(Set<? extends TypeElement> annotations,
                       RoundEnvironment roundEnv) {
    for (Element e : roundEnv.getElementsAnnotatedWith(MustReturnVoid.class)) {
        ExecutableElement method = (ExecutableElement) e;
        if (method.getReturnType().getKind() != TypeKind.VOID)
            processingEnv.getMessager().printMessage(
                Diagnostic.Kind.ERROR,
                "@MustReturnVoid requires void return", e);
    }
    return true;
}

Here there is no separate processor. The check is a member of the annotation type and runs where the annotation is written:

struct MustReturnVoid
{
    consteval void operator()(std::meta::annotation_context ctx) const
    {
        if (!std::meta::is_function(ctx.target()))
            throw std::meta::exception(
                u8"MustReturnVoid requires a function",
                std::meta::current_function(), ctx.annotation_location());

        if (std::meta::return_type_of(ctx.target()) != ^^void)
            throw std::meta::exception(
                u8"annotated function must return void",
                std::meta::current_function(), ctx.annotation_location());
    }
};

[[=MustReturnVoid{}]]
void process();  // ok

[[=MustReturnVoid{}]]
int compute();   // ill-formed

Java processors are external plugins registered with the compiler. The annotation type itself is passive. This proposal places the operator on the annotation type.

14.5. Summary

Running code named by metadata at the declaration site is established practice. The systems above split on when that code runs. Python and TypeScript decorators run during class definition at run time. Rust procedural macros and Java annotation processors run during compilation. This proposal takes the compile-time half. An active annotation can inspect the declaration it appertains to and reject it. Through the reflection library it can also generate declarations elsewhere. What it cannot do is replace or complete the declaration it is attached to (§ 8.5 Invocation contract). A later proposal can widen that if experience calls for it.

15. Wording Impact

  • In [dcl.attr.annotation], specify detection and invocation: the value categories the synthesized call uses, the unqualified type detection reads (§ 8 Semantic Model), invocation once for each construct the annotation appertains to (§ 3.5 Per-occurrence invocation), and the two near misses that are ill-formed instead of passive (§ 8.1 Detecting an active annotation).

  • In [dcl.attr.annotation], define a new program point of invocation for each annotated entity kind (§ 9 Timing Model), including that such a point moves to the first position at which a declaration may appear when a class-specifier ends mid-declaration and that a lambda’s closure type is treated as though it had a class-specifier of its own.

  • In [dcl.attr.annotation], give a sequence of such points wherever several active annotations share one, covering a class’s bases and members, an enumeration’s enumerators and its own definition, a declarator’s parameters, one declaration’s declarators, and a pack expansion’s elements (§ 9.4 Order of invocation). Say also that the complete-class contexts of [class.mem.general] paragraph 10 are processed after that sequence (§ 9 Timing Model).

  • In [dcl.attr.annotation], require ill-formedness on invocation failure with a diagnostic, place that failure outside the immediate context of any deduction alongside the existing paragraph 4, and state that an operator shall not define the entity its annotation appertains to.

  • In [expr.const.core], extend the paragraph 2.32 exception, which today admits only the corresponding expression of a consteval-block-declaration, to an annotation invocation (§ 8.5 Invocation contract).

  • In [expr.const.defns], add an entry to the manifestly constant-evaluated list for the expression corresponding to an annotation invocation, alongside the one paragraph 1.3 gives a consteval-block-declaration (§ 8 Semantic Model).

  • In [expr.const.reflect], extend the paragraph 3 restrictions on what an injected declaration may define to cover an annotation invocation, then give paragraph 5 a clause fixing the point of evaluation of an annotation invocation, which its existing clauses leave undefined because a synthesized call appears nowhere (§ 8 Semantic Model).

  • In [dcl.attr.annotation], say that overload resolution and access control for the synthesized call are performed in the access context of the annotation occurrence and that an annotation in a class-head or a base-clause is anchored at a point in the member-specification instead (§ 8.1 Detecting an active annotation, § 7.5 Access context). The invocation point sits outside the annotated class and would otherwise decide both.

  • In [dcl.attr.annotation], introduce a point of invocation for an annotation in a template specialization and place it immediately following the namespace-scope declaration or definition that refers to the specialization (§ 9.6 Templates). It is distinct from the point of instantiation so that [temp.point] paragraph 7 does not cap it. Say also that an instantiation first required from within a constant evaluation defers its invocation to that point.

  • In [basic.link], settle whether a closure type introduced by a lambda-expression written as a namespace-scope annotation is TU-local, which paragraph 15.2 leaves open (§ 8.1 Detecting an active annotation).

  • In [meta.reflection.define.aggregate], state that an annotation on an injected member is invoked at the locus of the injected declaration, say what synthesized points its evaluation context contains (§ 9.3 Injected members), and bound a chain of such injections or say that injected annotations are never invoked (§ 9.3 Injected members).

  • In [meta.syn] and a new subclause, add std::meta::annotation_context and specify its members, including annotation() (§ 7 Proposed Library Interface), the per-construct results of is_definition() and is_exported() (§ 7.4 Definition and export state), and that its values are consteval-only values.

  • In [cpp.predefined] and [version.syn], revise the feature-test macros (§ 15.1 Feature-test macro).

No new grammar production or declaration form is required.

This paper proposes no wording and there is no implementation. The open questions below decide what the wording would say so drafting before EWG gives a direction would be drafting to the wrong design. The argument rests on the adopted annotation and reflection wording. The list above is the full size of the ask: the point of invocation, the point of evaluation, and the point that hosts a specialization’s invocation are all things this paper has to define, because no existing rule fixes them.

15.1. Feature-test macro

[P3394R4] minted no macro of its own and [cpp.predefined] carries no __cpp_annotations. Annotations shipped under the reflection macros. The conservative reading is that this paper does the same and bumps __cpp_impl_reflection in [cpp.predefined] for the invocation rule and __cpp_lib_reflection in [version.syn] for annotation_context, both to the value of the plenary that adopts it.

The case for minting __cpp_active_annotations instead is that an implementation can ship reflection and annotations without this facility so a user testing for it is asking a question the reflection macro cannot answer. This paper proposes the bump because it follows what annotations already did and § 18 Open Questions carries the choice.

16. Implementability

Annotation formation and appertainment are specified in [dcl.attr.annotation], the queries that recover annotations in [meta.reflection.annotation], and constant evaluation in [expr.const]. A conforming C++26 implementation already carries that machinery. [P3394R4] reports that the core language feature and the basic query functions are implemented in the EDG front end and in Bloomberg’s P2996 Clang fork. The additional work is:

  • detecting operator()(annotation_context) on the annotation type

  • constructing the opaque annotation_context

  • materializing a program point per invocation at the places § 9 Timing Model names and invoking the operator there

  • diagnosing failure

The third is the one to try first and it is where an implementer will find out whether the design is right. It is also where the compile-time cost lands. The cost model follows from the rules above and this paper offers no measurements. One top-level constant evaluation happens for each pair of an annotation and a construct it appertains to (§ 3.5 Per-occurrence invocation), once per specialization for anything templated (§ 9.6 Templates), and nothing is memoized across specializations because [dcl.attr.annotation] paragraph 3 makes the annotations distinct by construction. An annotation type written in a widely included header therefore pays once per use. Whether that is acceptable is a question for an implementation and it is the second thing worth measuring.

The others reuse machinery that exists. None of that work adds a grammar production, a runtime subsystem, or a linker protocol. Because the design stays within standard annotations, tooling sees no macro-only surface and no vendor syntax. An annotation that calls define_aggregate, which needs the [expr.const.core] change this paper asks for (§ 8.5 Invocation contract), does generate a declaration, but it does so through standard reflection at a trigger written in the source and [meta.reflection.define.aggregate] already gives that declaration a locus so nothing about it is hidden from a tool that reads reflection.

17. Separate Papers

Each of the following is a separate paper and this one stands on its own if none of them is standardized:

  • schema declarations or markers

  • named surface syntax for library-defined metadata

  • a change to the by-value invocation model so post-attachment state initialization has somewhere to write (§ 3.3.3 const)

  • declaration-side constraints on accepted annotation types

  • emission-record or runtime-transport reflection facilities

  • relaxation of the structural-type restriction

Follow-on work on reification or compile-time code generation ([P3294R2]) should consider the interaction with active annotations, since their operators run during constant evaluation and can call such facilities if they exist. This paper provides the invocation mechanism and leaves the available operations to those proposals.

18. Open Questions

  • Member timing. This paper defers member and base-specifier annotations to class completion. Is the earlier diagnostic from mid-class invocation worth the narrower view it gives the operator? See § 9.5 Alternative: mid-class invocation.

  • Injected annotations. This paper invokes the annotations define_aggregate attaches, at the cost of a diagnostic with no annotation site to point at. Is exempting them the better trade? See § 9.3 Injected members.

  • Unbounded injection. Each invocation is a separate top-level evaluation so a chain of injections that keep carrying annotated members is not bounded by the recursion limit and can fail to terminate. Should this be an implementation limit or should injected annotations never be invoked? See § 9.3 Injected members.

  • Instantiation point. This paper gives a template specialization’s annotations a point of invocation of their own, immediately following the namespace-scope declaration or definition that refers to the specialization. It reuses neither [temp.point] point. Is a separate kind of point worth introducing? See § 9.6 Templates.

  • Near misses. Both are ill-formed: an ambiguity that includes a consteval candidate and a selected consteval operator returning something other than void. Is a hard error right for both? See § 8.1 Detecting an active annotation.

  • Access in a class-head. access() is anchored at the annotation occurrence everywhere except a class-head or a base-clause, where the occurrence sits outside the class scope and the anchor moves into the member-specification. Is the exception worth the irregularity? See § 7.5 Access context.

  • Silent adoption break. A C++26 annotation type that already has a consteval call operator viable for an annotation_context becomes active on adoption, with no edit at the annotation site. One returning something other than void stops compiling instead (§ 8.1 Detecting an active annotation). Is either acceptable or is an opt-in marker worth its cost after all? See § 8.3 Types without the operator.

  • Self-definition. This paper forbids an operator from defining its own target, which a consteval block in the same position may do. Should the asymmetry stand? See § 8.5 Invocation contract.

  • Feature-test macro. Annotations minted no macro of their own and this paper follows them. It bumps the reflection macros. Does a facility an implementation can ship separately need a macro of its own? See § 15.1 Feature-test macro.

  • Context surface. annotation() is in because self-identity cannot be expressed without it (§ 7 Proposed Library Interface). Should annotation_context expose anything further? Should the accessors be free functions instead (§ 7 Proposed Library Interface)?

19. Summary

  • Annotations remain the sole metadata representation and reflection the sole query path.

  • Some annotations become active and run compile-time code at the declaration they are attached to.

  • The only library addition is annotation_context.

One operator, plus reflection facilities as they arrive, covers declaration-relative behavior generally. Reflection-driven synthesis comes with it only if the [expr.const.core] paragraph 2.32 request is granted (§ 8.5 Invocation contract). Refusing it leaves validation intact and removes synthesis.
