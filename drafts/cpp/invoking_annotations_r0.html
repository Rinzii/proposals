Abstract

C++26 annotations expose stored values through reflection but leave libraries to arrange declaration-dependent checks and computations separately.

This paper proposes mandatory compile-time annotation callbacks that retain supported results for later retrieval. We request direction on invocation and retained results independently of direct-injection permission, while preserving indirect injection through a specialization’s consteval block. An annotation opts in through a callee’s declared std::meta::annotation_context parameter without body inspection, preserving existing C++26 behavior. Each occurrence is invoked once for each declaration or base-specifier it annotates, changing neither its input nor its target.

Retention adds result associations, publication rules, and module handling. Void callbacks produce no result. Supported by-value results become immutable, reflectable data for the occurrence and target after invocation, capture, and cleanup succeed. Later queries retrieve those results without repeating the computation.

Scheduling for declarations that define both a type and an object, annotated lambdas, and dependent specializations remains unresolved, as does correspondence across translation units and imports.

1. Revision History

2. Introduction

We propose invoking an annotation once for each construct it applies to: a declaration or a base-specifier. The annotation opts in when the type of its value declares a callee with a std::meta::annotation_context parameter. Each invocation is a mandatory constant evaluation that can validate the construct, derive a result from it, or do both. A successful supported non-void return supplies immutable, reflectable data associated with that occurrence/target pair (semantics). A call operator is one such callee. These alternative signatures support validation and derived data respectively:

consteval void operator()(std::meta::annotation_context) const;

consteval FieldInfo operator()(std::meta::annotation_context) const;

FieldInfo is a library-defined result type, as in the descriptor example, not a type supplied by <meta>. Neither validation nor producing a result is mandatory.

Other callable forms opt in the same way when the callee declares the parameter.

The working draft provides typed annotations and queries that recover them ([P3394R4]) through a compile-time metadata model based on std::meta::info ([P2996R13]). It provides no way for an annotation to observe its annotated construct and act on that information during translation. [P3394R4] anticipated this gap but left the facility open (callback questions).

The target is C++29, building on C++26 annotations and reflection and the revised constant-evaluation model in [N5054]. Stable names and paragraph numbers refer to that draft (the disclosure). The value-based rules from [P4101R1] are incorporated in [N5054], as recorded by [N5055].

Related proposals take different approaches. [P3385R8] reflects attributes, [P4167R0] has the language act on one annotation directly, and [P3289R1] supplies consteval blocks that run at a point the author chooses. The motivation and the alternatives compare them.

The proposal comprises:

  1. An opt-in rule. An annotation with such a callee is active and any other is passive. A near miss that declares the parameter is an error. It cannot fall back to passive.

  2. The invocation contract. For each occurrence/target pair of an active annotation, the synthesized full-expression is manifestly constant-evaluated and required to be a core constant expression. A void return produces no result. A supported by-value return is captured through reflect_constant, including its materialization requirements. Reference returns and failed capture are errors.

  3. Proposed processing points and an order over occurrence/target pairs. Newly required specializations can be processed nested in a constant evaluation. A pair already awaiting a processing point keeps that point on a later encounter. Members injected by define_aggregate are processed inside the injecting evaluation. Ordering between type and object callbacks in one declaration, annotated lambda processing, dependent-specialization ordering, and cross-translation-unit correspondence still need decisions.

  4. std::meta::annotation_context, supplying occurrence-specific reflection handles, locations, definition and export state, and an access anchor. The proposed annotation_result_of(annotation, target) retrieves a completed pair’s retained result without invoking it again (the interface). Publication, persistence, and module handling extend the metadata model.

  5. A separate request that [expr.const.core] paragraph 2.32 admit the corresponding expression of an active annotation’s invocation. The annotation’s position determines where it may inject directly. The base protocol already permits indirect injection through a specialization’s consteval block (the semantic delta).

  6. Polls that let a later request be declined while earlier ones stand.

We assume C++26 annotations and reflection as adopted, including the structural-type restriction on annotation values. Under the [N5054] value rules, a pointer to an immediate function is a consteval-only value. The declared-parameter opt-in is a policy choice. Poll 1 asks about the alternative.

3. Applying an active annotation schedules its library-defined callback

Applying an active annotation schedules its library’s callback at a defined processing point. The declaration’s author need not arrange a separate call or consteval block (the block alternative). The callback can validate the annotated construct or derive data from it. These validation uses need declaration-aware checks:

  • A serialization-field annotation must reject being applied to anything other than a non-static data member with a non-empty key.

  • A thread-safety annotation must reject a declaration that is not a non-static data member.

  • A command annotation must require a function with a specific signature.

  • A language-binding annotation, marking a declaration for exposure to another language’s runtime, must require an exported declaration or a complete type.

Reflection and a consteval block can already express these checks. Libraries, vendor extensions, macros, and external tools can arrange checks that diagnose the offending declaration. But a separately arranged check can be omitted even when the annotation is present.

A library can also derive a descriptor from the annotated declaration at that processing point. A field annotation can supply a default name from its member’s identifier and return that name with the reflected type. Consumers retrieve the retained descriptor without arranging the computation separately or repeating it at each query. A manually arranged helper could compute the same value. The proposal adds the automatic trigger, defined processing point, and retained occurrence/target association (the descriptor example).

The processing point determines when the callback runs and what it can observe (consumer guarantees). The supplied source location lets diagnostics identify the annotation site (diagnostics). The trigger also supports the separate direct synthesis request.

3.1. Annotations already supply what an invocation needs

Annotations ([P3394R4]) supply declaration-local syntax and standard reflection visibility ([P2996R13]) without runtime requirements. The input reuses their formation, identity, and query rules, including non-ignorability ([P2552R3]). Retained results extend that model with a derived association, a query, publication rules, and module handling. Existing std::meta::info and constant materialization supply the representation but do not supply those semantics.

Reflecting attributes is a separate C++29 proposal ([P3385R8]). At Sofia in June 2025, EWG preferred that paper without the ability to appertain an attribute to an entity ([P3385R8] section 6.1.4). It encouraged work to expose attributes' details for querying but did not reach consensus to encourage further work in the paper’s direction ([P3385R8] section 6.1.4). The appertain metafunction has since been removed. The current revision keeps attributes on members defined by define_aggregate, as SG7 supported at that meeting ([P3385R8] sections 1, 4.2.5, and 6.1.4). Annotations already have reflections and apply to declarations, which is all an invocation needs.

3.2. Current tools separate the rule from the metadata

Current systems interpret declaration metadata through compiler analysis, external tools, or library code. Clang’s thread safety analysis reads annotations such as GUARDED_BY(mu) on a data member and diagnoses violations under -Wthread-safety. Its mutex.h example notes that the attributes are enabled only with Clang ([CLANG-TSA]). Visual Studio code analysis reads Microsoft’s source-code annotation language (SAL), including _In_ and _Out_ from <sal.h> ([MS-SAL]).

Qt’s meta-object compiler (moc) reads headers and generates C++ source for classes containing Q_OBJECT. That source must be compiled and linked with the class implementation ([QT-MOC]). Boost.Describe uses BOOST_DESCRIBE_STRUCT(Name, Bases, Members) with manually supplied, parentheses-enclosed lists of bases and public members ([BOOST-DESCRIBE]). Adopted reflection removes that listing: nonstatic_data_members_of enumerates members without a macro.

4. Terms the design introduces

  • Annotated construct: what an annotation applies to under [dcl.attr.annotation] paragraph 1, a base-specifier or a declaration of one of the kinds that paragraph lists, with each declarator counted as its own declaration ([dcl.decl.general] paragraph 3). A base-specifier is not a declaration, so construct below means either.

  • Occurrence/target pair: one annotation occurrence, unique under [dcl.attr.annotation] paragraph 3, with one construct it applies to. A parameter-declaration in a function definition is one construct although the annotation applies to both the parameter and its variable.

  • Opt-in: an annotation that opts in, by the type of its value declaring a callee with a std::meta::annotation_context parameter, is active. One that does not is passive.

  • Processing point: the program point assigned to an occurrence/target pair, at which an active annotation’s invocation for that pair is evaluated. A pair processed during another constant evaluation (specializations, injected members) has no point of its own and is evaluated during that evaluation.

  • Annotation site: where an annotation occurrence is written.

  • Retained result: the reflection captured from a successful non-void invocation. Its result payload is the returned value, distinct from the input annotation payload recovered through constant_of(annotation).

  • Publication: successful completion of the entire invocation full-expression makes its retained result available to later queries under the specified processing and evaluation order.

  • Access anchor: the program point that supplies access checking for an invocation and the value ctx.access() returns. It is a point inside the class for an annotation on a class definition or a base-specifier, and the occurrence for every other annotation (the injected declaration’s locus for an injected member).

5. Scope stays within existing annotations

The design reuses annotation inputs and constant materialization and adds derived result metadata. Mutation and an automatic runtime transport protocol remain outside scope.

5.1. Existing annotations, reflection, and diagnostics are reused

  • Preserve annotations as the input metadata and retain derived results separately for occurrence/target pairs.

  • Use standard reflection representations and extraction operations, with one proposed result query.

  • Reuse compile-time diagnostics.

  • Remain compatible with the current annotation materialization model.

  • Introduce no new application binary interface (ABI) surface or linker protocol.

  • Preserve an already completed pair’s state and retained result on import when its annotation/target association is observable.

5.2. Syntax, mutation, and runtime transport are out of scope

  • New declaration-metadata syntax.

  • Changes to the annotated construct itself, including members, bases, signatures, and bodies.

  • Adding, removing, or changing annotations on a declaration after it is formed (related work).

  • A separate library-publication mechanism for named metadata.

  • Automatic runtime registries, discovery tables, or a new compile-time-to-runtime transport protocol. Extracted ordinary values remain usable through ordinary language mechanisms.

  • New declaration injection, token generation, or source rewriting facilities.

  • Replacement of existing standard or vendor attributes.

  • A parallel extraction system or a result setter.

The direct-injection request permits existing facilities in a new context. [expr.const.core] paragraph 2.32 admits injected declarations when the enclosing required expression corresponds to a consteval block. We ask that it also admit an active annotation’s invocation (the invocation contract, the synthesis example). Without that permission, the base protocol can still reach a specialization’s own consteval block under that block’s injection and scope rules (the indirect route).

6. The design extends P3394R4’s annotations without changing them

6.1. Non-ignorable does not mean invoked

Annotations are non-ignorable ([P3394R4]): their underlying constants are formed through reflect_constant and observable through annotations_of. Under current rules, an implementation cannot discard an annotation but need not invoke it. Mandatory invocation needs new wording and provides the consumer guarantees below.

6.2. The design answers P3394R4’s questions about a callback

[P3394R4] section 4.5 (Other Directions We Are Exploring) sketches a callback invoked by the annotated declaration. It asks about completion timing, separate syntax, mutation, naming, and registration. It compares the callback to [P0707R4]: annotations on classes that run at class completeness and allow mutation. We choose post-completion processing for class-related targets, existing annotation syntax, and a declared std::meta::annotation_context parameter as the opt-in. The parameter type identifies the callback without registration (the opt-in rule). Unlike [P0707R4], an invocation cannot change its annotated declaration.

That section first considers an annotation added only for selected specializations and one that applies both clap::Short and clap::Long to a declaration. Both need annotations added after the fact, which we do not propose. A library accessor can derive the answer when queried. A callback can instead compute and retain derived data at its processing point, varying it per specialization or reading clap::Short and clap::Long as one. Neither changes the input annotations (related work). The third use, injecting a std::formatter specialization at class completion, needs generation facilities beyond define_aggregate, such as those considered by [P3294R2]. For a class template it also needs a callback on the template definition, which per-specialization invocation does not provide (specializations).

6.3. Invocations check stored values as well as declarations

Constructors can reject invalid initial class-type metadata. But structural types expose their non-static data members, so values can change before use as annotations. The invocation can validate the final stored value and the annotated construct.

A consumer may rely on a callback’s checks only when ordered after the relevant occurrence/target pair’s invocation succeeds. annotations_of establishes presence, not completed validation. Code inside a class can observe an earlier member’s annotation before callbacks run after the class. A callback can also observe annotations whose callbacks come later in the invocation order. Neither observation guarantees that the pending checks will succeed.

The guarantee covers only what the completed invocation checked and successfully captured. The result query distinguishes completed absence from an invocation that has not completed. It does not validate annotations contributed by later redeclarations or recompute an earlier result when those declarations become reachable (reachability).

Program-global behavior across translation units or registries is outside scope.

7. The examples show rules that read the annotated construct

The examples use the proposed invocation protocol and result query. They are not compiled active-annotation examples. They cover validation, retained descriptors, different targets, and synthesis under the separate direct-injection request. The controls test supported facilities explicitly.

7.1. A field checks its key and its target

A Field carries a serialization key and checks the construct it applies to.

#include <meta>
#include <string>
#include <string_view>

namespace serial
{
    struct Field
    {
        const char* key;

        consteval Field(std::string_view k)
            : key(std::define_static_string(k))
        {
            if (k.empty())
                throw std::meta::exception(
                    u8"serial::Field requires a non-empty key",
                    std::meta::current_function());
        }

        consteval void operator()(std::meta::annotation_context ctx) const
        {
            if (key == nullptr || std::string_view(key).empty())
                throw std::meta::exception(
                    u8"serial::Field requires a non-empty key",
                    std::meta::current_function(),
                    ctx.annotation_location());

            if (!std::meta::is_nonstatic_data_member(ctx.target()))
                throw std::meta::exception(
                    u8"serial::Field may annotate only non-static data members",
                    std::meta::current_function(),
                    ctx.annotation_location());
        }
    };
} // namespace serial

struct User
{
    [[=serial::Field("user_id")]] int id;
    [[=serial::Field("display_name")]] std::string name;
};

The constructor rejects an empty key but public key can change before use as an annotation. The operator checks the stored key again, rejecting null and empty keys, and requires a non-static data member (consumer guarantees).

An annotation value must be a structural type. Field stores its key as const char* but a pointer into a string literal is not a valid constant template argument. define_static_string ([P3491R3]) copies the characters into static storage and yields a pointer usable as a constant template argument. The string-carrying examples below use the same idiom.

A serializer for User needs only adopted facilities: nonstatic_data_members_of ([P2996R13]), annotations_of_with_type ([P3394R4]), a splice, and an expansion statement ([P1306R5]). After the relevant invocations succeed, it can assume every Field it finds is on a non-static data member and has a non-null, non-empty key. Earlier queries cannot infer that from presence alone. Applying Field schedules the checks even if no serializer is instantiated.

7.2. A field retains a derived descriptor without changing its input

This complete example uses the proposed context and result query. The callback supplies a default name from the member’s identifier at its processing point. FieldInfo is structural and its name uses existing static-storage materialization ([meta.reflection.names], [meta.reflection.result], [basic.compound], [P3491R3]).

#include <meta>
#include <string>
#include <string_view>

namespace schema
{
    struct FieldInfo
    {
        const char* name;
        std::meta::info type;
    };

    struct Field
    {
        const char* name = nullptr;

        consteval FieldInfo operator()(std::meta::annotation_context ctx) const
        {
            if (!std::meta::is_nonstatic_data_member(ctx.target())
                || !std::meta::has_identifier(ctx.target()))
                throw std::meta::exception(
                    u8"Field requires a named non-static data member",
                    std::meta::current_function(), ctx.annotation_location());

            auto key = name == nullptr
                ? std::define_static_string(std::meta::identifier_of(ctx.target()))
                : name;
            if (std::string_view(key).empty())
                throw std::meta::exception(
                    u8"Field requires a non-empty name",
                    std::meta::current_function(), ctx.annotation_location());

            return {key, std::meta::type_of(ctx.target())};
        }
    };
}

struct Record
{
    [[=schema::Field{}]] int id;
};

constexpr auto member = ^^Record::id;
constexpr auto annotation =
    std::meta::annotations_of_with_type(member, ^^schema::Field)[0];
constexpr auto retained = std::meta::annotation_result_of(annotation, member);
constexpr auto descriptor = std::meta::extract<schema::FieldInfo>(retained);
static_assert(std::string_view(descriptor.name) == "id");
static_assert(descriptor.type == ^^int);
static_assert(std::meta::extract<schema::Field>(
    std::meta::constant_of(annotation)).name == nullptr);

The result query returns a reflection of the computed FieldInfo. constant_of(annotation) still represents the original Field{} with its null name. Repeated result queries retrieve the same captured result without another call. A read-time accessor could derive the same descriptor but would arrange that computation at its query points (result alternatives).

7.3. A class callback collects completed member results

Continuing the preceding example, the class-definition callback consumes the members' retained descriptors. The constituent-before-whole order supplies their completed results. No direct-injection permission is needed.

#include <cstddef>

namespace schema
{
    struct CountIntegerFields
    {
        consteval std::size_t operator()(std::meta::annotation_context ctx) const
        {
            std::size_t count = 0;
            for (auto member : std::meta::nonstatic_data_members_of(
                     ctx.target(), ctx.access()))
                for (auto annotation : std::meta::annotations_of_with_type(
                         member, ^^Field))
                {
                    auto descriptor = std::meta::extract<FieldInfo>(
                        std::meta::annotation_result_of(annotation, member));
                    if (descriptor.type == ^^int)
                        ++count;
                }
            return count;
        }
    };
}

struct [[=schema::CountIntegerFields{}]] Row
{
    [[=schema::Field{}]] int id;
    [[=schema::Field{}]] bool ready;
};

constexpr auto collector = std::meta::annotations_of_with_type(
    ^^Row, ^^schema::CountIntegerFields)[0];
static_assert(std::meta::extract<std::size_t>(
    std::meta::annotation_result_of(collector, ^^Row)) == 1);

The member invocations finish before CountIntegerFields begins. Its scalar result requires no persistent container. A collector earlier than its producers would get an unavailable-result exception, even if their input annotations were already observable. Lazy template members retain their separate instantiation rules (member processing).

7.4. A present result can contain false or a null reflection

The result query does not interpret the returned value. This proposed example also uses a helper written before the callbacks' processing points but evaluated after them.

#include <cstddef>
#include <meta>

consteval std::meta::info retained_at(std::meta::info target, std::size_t index)
{
    return std::meta::annotation_result_of(
        std::meta::annotations_of(target)[index], target);
}

struct NoResult
{
    consteval void operator()(std::meta::annotation_context) const {}
};

struct FalseResult
{
    consteval bool operator()(std::meta::annotation_context) const { return false; }
};

struct TypeResult
{
    consteval std::meta::info operator()(std::meta::annotation_context) const
    {
        return ^^int;
    }
};

struct NullResult
{
    consteval std::meta::info operator()(std::meta::annotation_context) const
    {
        return {};
    }
};

[[=NoResult{}, =FalseResult{}, =TypeResult{}, =NullResult{}]] int subject;

static_assert(retained_at(^^subject, 0) == std::meta::info{});
constexpr auto boolean = retained_at(^^subject, 1);
static_assert(boolean != std::meta::info{});
static_assert(!std::meta::extract<bool>(boolean));
static_assert(std::meta::extract<std::meta::info>(
    retained_at(^^subject, 2)) == ^^int);
constexpr auto null_value = retained_at(^^subject, 3);
static_assert(null_value != std::meta::info{});
static_assert(std::meta::extract<std::meta::info>(null_value) == std::meta::info{});

NoResult publishes completed absence. NullResult publishes a reflection representing an info value whose value is null. The query does not flatten that extra level of reflection. FalseResult likewise supplies a present Boolean result, not a validation failure. Existing extract recovers each payload ([meta.reflection.extract]).

7.5. A command checks its function’s parameter shape

Command requires one declared parameter of type command_context&. Its constructor cannot check the parameter list because the annotated declaration is unavailable when the value is formed.

struct command_context
{
    std::span<const std::string_view> arguments;
    std::ostream& out;
};

namespace cli
{
    struct Command
    {
        const char* name;

        consteval Command(std::string_view n)
            : name(std::define_static_string(n))
        {
        }

        consteval void operator()(std::meta::annotation_context ctx) const
        {
            if (!std::meta::is_function(ctx.target()))
                throw std::meta::exception(
                    u8"cli::Command requires a function",
                    std::meta::current_function(),
                    ctx.annotation_location());

            auto params = std::meta::parameters_of(ctx.target());
            if (params.size() != 1
                || std::meta::type_of(params[0]) != ^^command_context&)
                throw std::meta::exception(
                    u8"cli::Command requires one command_context& parameter",
                    std::meta::current_function(),
                    ctx.annotation_location());
        }
    };
} // namespace cli

[[=cli::Command("build")]]
void build(command_context&);

[[=cli::Command("clean")]]
void clean(command_context&);

// [[=cli::Command("version")]]
// void version();   // ill-formed: missing command_context& parameter

The invocation validates the declared parameter count and type (consumer guarantees). These checks do not establish a common function-pointer type or guarantee that a dispatcher can call every accepted function.

7.6. An annotation on a class definition sees the whole class

struct RequireDefaultConstructible

7.7. Direct injection lets an annotation generate a type

The annotation copies the names, types, and order of the class’s direct non-static data members into a second aggregate. Matching object layout and C compatibility are not guaranteed.

#include <meta>
#include <vector>

struct OrderRow;

struct DefineLayout
{
    std::meta::info destination;

    consteval void operator()(std::meta::annotation_context ctx) const
    {
        std::vector<std::meta::info> members;
        for (auto m : std::meta::nonstatic_data_members_of(
                 ctx.target(), ctx.access()))
        {
            if (!std::meta::has_identifier(m))
                throw std::meta::exception(
                    u8"DefineLayout cannot mirror an unnamed member",
                    std::meta::current_function(),
                    ctx.annotation_location());

            members.push_back(std::meta::data_member_spec(
                std::meta::type_of(m),
                {.name = std::meta::identifier_of(m)}));
        }

        std::meta::define_aggregate(destination, members);
    }
};

struct [[=DefineLayout{^^OrderRow}]] Order
{
    int order_id;
    bool shipped;
};

int main()
{
    OrderRow row{
        .order_id = 7,
        .shipped = true
    };
}

define_aggregate ([meta.reflection.define.aggregate]) generates the type. This proposal supplies the trigger and declaration context (non-goals). The invocation runs after Order is complete so its members are available to the operator (processing points).

The example needs our change to [expr.const.core] paragraph 2.32, which currently permits only a consteval block to produce an injected declaration. The annotation sits in the class-head, outside Order’s class scope ([basic.scope.class] paragraph 1). That position permits the namespace-scope definition of OrderRow (the invocation contract).

7.8. The occurrence/target pair selects which invocation rejects duplicate keys

PrimaryKey checks the whole class. The operator sees the same annotation set as an outside query, including its own occurrence (processing points), and knows its occurrence/target pair. The first invocation can observe the second key’s annotation before its invocation runs. Seeing the set does not mean every invocation has succeeded.

struct PrimaryKey
{
    consteval void operator()(std::meta::annotation_context ctx) const
    {
        if (!std::meta::is_nonstatic_data_member(ctx.target()))
            throw std::meta::exception(
                u8"PrimaryKey requires a non-static data member",
                std::meta::current_function(),
                ctx.annotation_location());

        std::vector<std::pair<std::meta::info, std::meta::info>> keys;
        for (auto m : std::meta::nonstatic_data_members_of(
                 std::meta::parent_of(ctx.target()), ctx.access()))
            for (auto key : std::meta::annotations_of_with_type(m, ^^PrimaryKey))
                keys.emplace_back(m, key);

        if (keys.size() > 1
            && keys[1].first == ctx.target()
            && keys[1].second == ctx.annotation())
            throw std::meta::exception(
                u8"at most one PrimaryKey annotation per class",
                std::meta::current_function(),
                ctx.annotation_location());
    }
};

struct Invoice
{
    [[=PrimaryKey{}]] std::int64_t invoice_id;   // ok
    std::string customer;
};

struct LedgerEntry
{
    [[=PrimaryKey{}]] std::int64_t entry_id;
    [[=PrimaryKey{}]] std::int64_t batch_id;   // ill-formed: two primary keys
};

struct Batch
{
    [[=PrimaryKey{}]] std::int64_t batch_id, sequence;   // ill-formed: one annotation, two keys
};

Both invocations in LedgerEntry find two primary keys. ctx.annotation() alone cannot always distinguish them: in Batch, one occurrence applies to both declarators. annotations_of(^^Batch::batch_id)[0] and annotations_of(^^Batch::sequence)[0] are the same reflection (occurrence/target pairs) so both invocations receive equal ctx.annotation() values.

The operator compares the member and annotation together, throwing only for the class’s second key. The exception identifies the annotation on batch_id in LedgerEntry and the shared annotation in Batch (the annotation accessor). This selects one failing invocation per class without prescribing the number of compiler diagnostics.

7.9. A guard annotation finds its named member anywhere in the class

GuardedBy validates declaration-level metadata, inspired by the Clang facility in existing practice. It checks the target and whether the named member exists.

struct GuardedBy
{
    const char* mutex_name;

    consteval GuardedBy(std::string_view n)
        : mutex_name(std::define_static_string(n))
    {
    }

    consteval void operator()(std::meta::annotation_context ctx) const
    {
        if (!std::meta::is_nonstatic_data_member(ctx.target()))
            throw std::meta::exception(
                u8"GuardedBy requires a non-static data member",
                std::meta::current_function(),
                ctx.annotation_location());

        bool found = false;
        for (auto m : std::meta::nonstatic_data_members_of(
                 std::meta::parent_of(ctx.target()), ctx.access()))
            if (std::meta::has_identifier(m)
                && std::meta::identifier_of(m) == mutex_name)
                found = true;

        if (!found)
            throw std::meta::exception(
                u8"GuardedBy names a member that does not exist",
                std::meta::current_function(),
                ctx.annotation_location());
    }
};

class Connection
{
    [[=GuardedBy("mu_")]] int refcount_ = 0;
    [[=GuardedBy("mu_")]] bool connected_ = false;
    std::mutex mu_;
};

The operator requires the name to denote a non-static data member of the same class. It checks neither that member’s type nor locking in function bodies. mu_ is declared after the members that name it but is visible when the annotations run after class completion (processing points).

7.10. An annotation can check export status

7.13. Callees other than a call operator can opt in

struct FunctionOnly

[[=FunctionOnly{}]] void another_action();

constexpr void accept_context(std::meta::annotation_context) {}

8. The library adds a context and a result query

An active annotation receives an annotation_context. This schematic synopsis omits the implementation-defined representation.

namespace std::meta
{
    struct annotation_context
    {
        annotation_context() = delete;

        consteval info annotation() const;
        consteval info target() const;
        consteval source_location annotation_location() const;
        consteval source_location declaration_location() const;
        consteval bool is_definition() const;
        consteval bool is_exported() const;
        consteval access_context access() const;
    };

    consteval info annotation_result_of(info annotation, info target);
} // namespace std::meta

annotation_context is a literal class type with public constexpr copy and move operations and a constexpr destructor. It is non-structural ([temp.param]) and its values are consteval-only, as [meta.reflection.define.aggregate] paragraph 1 specifies for data_member_options. The non-structural choice rules out by-value annotation payloads and class-type constant template arguments. This is a separate choice: [meta.reflection.access.context] paragraph 3 makes access_context structural.

The default constructor is deleted. No user-accessible constructor fabricates a context from arbitrary inputs. The implementation supplies a context prvalue for each invocation (semantics).

Member accessors follow access_context. Free functions would also work, since reflection functions need not take info. The interface choice remains open to LEWG.

8.1. A context describes one occurrence and one target

annotation_context describes one occurrence and one target through reflection handles and occurrence-specific information. It neither replaces stored metadata nor synthesizes declarations or changes annotations. The reflected target already provides the enclosing scope and template arguments. Existing reflection queries enumerate annotations, so the context adds no accessors for these.

8.2. annotation() identifies the invoked occurrence

Returns the element of annotations_of(target()) being invoked. Under [dcl.attr.annotation] paragraph 3, each annotation is unique even when others on the same construct carry equal underlying constants. For a member injected by define_aggregate, the result represents the annotation formed by injection (injected members).

8.3. target() reflects the annotated construct

Returns a reflection of the annotated construct. A base-specifier is not a declaration, as [CWG3092] clarified in [dcl.attr.annotation] paragraph 1. Its reflection represents the direct base class relationship it introduces ([class.derived.general]). For a function parameter or non-static data member, the result represents that parameter or member. For other constructs allowed by [dcl.attr.annotation], including namespaces and enumerators, it represents the annotated entity.

An annotation on a parameter-declaration in a function definition applies to both the parameter and its variable ([dcl.attr.annotation] paragraph 1). They form one occurrence/target pair, invoked once with target() reflecting the parameter (occurrence/target pairs). The target accessor does not return the variable reflection. Under [meta.reflection.queries] paragraph 65.2, variable_of(target()) throws unless a point in the evaluation context has that function parameter scope as its innermost non-block scope. The processing point is outside that scope.

8.4. The context locates the annotation and the declaration

annotation_location() returns the annotation occurrence’s source location. declaration_location() returns the annotated construct’s source location. source_location_of(target()) replaces neither: [meta.reflection.names] paragraph 7 makes its result implementation-defined and paragraph 8 recommends only that it correspond to a definition. That can differ from the annotated declaration.

An annotation on a member injected by define_aggregate has no annotation site and both accessors report the locus of the injected declaration (injected members).

8.5. The context reports definition and export state

is_definition() reports whether the annotated declaration is a definition ([basic.def]). A parameter-declaration is one only in a function-definition’s declarator and an alias-declaration never is. For a base-specifier it returns true and declaration_location() reports the base-specifier’s location. Completeness is a separate query: is_complete_type(ctx.target()) (incomplete targets).

is_exported() reports export status at the annotation site. [module.interface] paragraph 2 makes a declaration exported if it inhabits namespace scope within an export-declaration, is a namespace-definition containing an exported declaration, or introduces a name in a header unit. For class members, function parameters, base-specifiers, and enumerators, the query reports the export status of the innermost enclosing namespace-scope declaration. It also returns true for redeclarations implicitly exported under paragraph 6. It does not predict later visibility through an exported using-declaration, permitted for a type alias or an entity with external linkage by [module.interface] paragraph 5.

8.6. access() reflects the class the annotation describes, or else the annotation site

access() returns a reflective access context as if std::meta::access_context::current() were evaluated at the access anchor. For an annotation on a class definition or base-specifier, the anchor is a point in the class’s member-specification. For every other annotation it is the occurrence’s lexical program point, or the injected declaration’s locus for an injected member. This uses ordinary reflective access without introducing privileged access.

Class-head and base-specifier annotations describe the class being defined. A validator enumerating its members needs that class’s access. But those positions lie outside class scope ([basic.scope.class] paragraph 1) and [meta.reflection.scope] paragraph 5 resolves their current scope to the enclosing namespace or class. An occurrence anchor would therefore give a base-specifier annotation namespace access and leave a class-head validator unable to see the annotated class’s private members.

The names written in a base-specifier already use the derived class’s access ([class.access.general] paragraph 7). An anchor inside the class gives both annotations that same access.

The anchor is separate from the processing point. An annotation inside a class body runs outside the class but retains the annotation site’s access, including private members.

Calling std::meta::access_context::current() in the callback body reports that body’s context. Queries using the annotation’s access anchor should receive ctx.access(). Non-reflective accesses retain the callback body’s lexical access rules.

An operator should receive anything else it needs as an annotation value.

8.7. annotation_result_of retrieves the result for an observable pair

annotation_result_of is proposed here, not an existing reflection API. Its arguments identify the annotation occurrence and the construct to which it applies. A valid association is one for which annotations_of(target), evaluated at the query’s point with its reflective evaluation context, would include annotation under [meta.reflection.annotation]. This includes that query’s complete-class-context rule. Invalid argument kinds or an association not observable in that context cause std::meta::exception to be thrown.

For a member, callers supply its reflection, for example ^^Record::id or an element of nonstatic_data_members_of. For a parameter, they supply the corresponding element of parameters_of. For a base relationship, they supply an element of bases_of for the derived class, not a reflection of the base class type. Other supported constructs use their entity reflections, as the target accessor specifies. The existing query requirements and reachability rules still apply ([meta.reflection.member.queries], [meta.reflection.queries], [meta.reflection.annotation]).

For an annotation on a parameter-declaration in a function definition, the parameter reflection is the canonical target. A reflection of its associated parameter variable is an alternate name for that same pair, with no second invocation, completion state, or retained result. Association is checked against the supplied target before this normalization. When both supplied targets pass that check at the same evaluation point, they have identical availability and return the same retained reflection after non-void publication. Normalization does not bypass annotation visibility. A prototype’s annotation does not become associated with a later definition’s parameter variable, and an unrelated variable is not an alias ([dcl.attr.annotation], [meta.reflection.annotation]).

Result query outcomes at the query’s semantic evaluation point. Association validity is checked before invocation state.
Situation Outcome
Invalid or unobservable annotation/target association Throws std::meta::exception
Valid association with a passive annotation Returns the null reflection
Active pair with no available preceding completion, including a pending or running invocation, capture, and cleanup Throws std::meta::exception
Available successful invocation returning void Returns the null reflection
Available successful invocation with a retained non-void result Returns that retained reflection

Availability follows the publication rule. A pending void invocation also throws. Its return type does not establish successful absence. A failed required invocation makes the program ill-formed and supplies no recoverable failed-result value.

The query neither calls A(C) nor reconstructs C. It does not instantiate a callback body on demand, advance a pending invocation, wait, retry, or repair a dependency. Ordinary formation of its arguments can still require instantiation under existing rules. An unavailable-result exception can be caught where constant evaluation permits, unlike failure of another independently required invocation (failure boundaries).

Both arguments are necessary. One occurrence can apply to multiple declarators and produce different results. Annotation type, input-value equality, source location, and target alone cannot identify the pair. Only language-scheduled invocation publishes this association. A manual call or independent reflect_constant call neither creates nor overwrites it.

8.7.1. A parameter variable names the defining parameter’s result

This proposed-language example compares the two query forms after their one callback has completed:

#include <meta>

struct ParameterData
{
    consteval int operator()(std::meta::annotation_context) const
    {
        return 7;
    }
};

consteval bool same_parameter_result([[=ParameterData{}]] int value)
{
    constexpr auto parameter =
        std::meta::parameters_of(^^same_parameter_result)[0];
    constexpr auto variable = ^^value;
    auto annotation =
        std::meta::annotations_of_with_type(variable, ^^ParameterData)[0];
    auto retained = std::meta::annotation_result_of(annotation, parameter);
    return retained == std::meta::annotation_result_of(annotation, variable)
        && std::meta::extract<int>(retained) == 7;
}

static_assert(same_parameter_result(0));

The function body obtains value’s variable reflection where the name is in scope ([expr.reflect]). Its local constant initializers form reflection handles, not result queries. The ordinary calls to annotation_result_of are evaluated by the later namespace-scope assertion, after the function definition and its parameter callback’s processing point. They therefore return the same retained reflection. Writing an assertion containing these queries inside the definition would impose a requirement at that earlier point instead.

Obtaining a variable through variable_of(parameter) has an additional evaluation-context scope requirement ([meta.reflection.queries]). This example needs no such call, either in the callback or in a helper evaluated from namespace scope. The supporting controls verify the handles and associations separately from the proposed query. A prototype-only annotation queried with this variable, or this definition’s annotation queried with an unrelated variable, fails association checking before normalization.

9. An invocation calls the annotation’s value with a context

An annotation first forms under [dcl.attr.annotation], then undergoes the opt-in test. Each active occurrence/target pair requires a constant evaluation at its processing point. Invocation neither replaces nor repeats formation.

The callable operand uses the existing underlying input constant. Invocation does not re-evaluate the annotation expression or copy that input into a second annotation object. A successful non-void invocation separately retains its result.

Let R be the annotation’s underlying constant, that is, the reflection produced by the reflect_constant expression required during formation. Define the exposition-only operands:

  • A has the meaning, type, and value category of an expression splice [:R:]. If R represents an object, A is an lvalue designating that object. Otherwise R represents a value and A is a prvalue computing that value ([meta.reflection.result], [expr.prim.splice]).

  • C is an implementation-provided prvalue of type std::meta::annotation_context, describing this annotation occurrence and this target. When evaluated, its result object is created within the invocation full-expression. No user-visible constructor call is involved.

Let F denote the direct-call expression A(C). Ordinary overload resolution selects its callee. A selected reference return is ill-formed in this revision. Otherwise define the corresponding expression E according to the selected return type, after any return-type deduction required to form the call. For a void result, including cv-qualified void, E is:

static_cast<void>(A(C))

For a supported non-void result, E is:

std::meta::reflect_constant(A(C))

These are alternative exposition-only expressions, not consecutive evaluations. For a class-type annotation, A designates the existing const T template parameter object rather than extract<T>(R) or a freshly constructed copy. Its storage and identity follow from [temp.param] and [meta.reflection.result]. Function-pointer annotations use the existing reflected pointer value without another lookup of the pointed-to function.

We propose that E be a corresponding expression in [expr.const.defns], be manifestly constant-evaluated, and itself be in an immediate function context. It is evaluated as one full-expression whose success includes its required destruction. The non-void alternative retains the reflection computed by reflect_constant only after that full-expression completes successfully (capture requirements, publication).

The rule for E itself is an additional core-language provision. In [N5054], [expr.const.imm] paragraph 1 puts potentially evaluated subexpressions of a manifestly constant-evaluated expression in an immediate function context. An expression is not its own subexpression ([intro.execution]). The outer capture call returns a non-null reflection and the immediate-constant-expression and immediate-escalation rules also apply ([expr.const.const], [expr.const.imm]). Giving E itself that context makes the literal library-call formulation usable without a synthetic lambda, helper function, or separately constant-evaluated local variable.

No new lexical scope or separate reflective evaluation context is introduced. The callback need not be declared consteval. Its body’s lexical access and immediate-function-context rules remain those of an ordinary call. Capture does not create a second permission boundary for injection: the required corresponding expression remains E throughout the call, capture, and cleanup.

A synthesized invocation has no source spelling from which [expr.const.reflect] can derive a point of evaluation. Its processing point supplies that point for reflective evaluation and the locus of permitted injected declarations (the invocation contract). The call checks access from the access anchor.

9.1. An annotation opts in by declaring the context parameter

An annotation opts in when its value’s type supplies a call operator or pointed-to function with a parameter declared as std::meta::annotation_context, possibly cv-qualified or a reference to it. The eligible callees are:

  • the call operators found by a search for operator() in the scope of the class type ([over.call.object] paragraph 1), which admits a closure type’s operator and one inherited from a base class or introduced by a using-declaration

  • for a pointer-to-function type, the function type it points to

Conversion functions and surrogate call functions do not establish participation. A conversion-only value stays passive even if its conversion function is explicit or non-const. A non-const call operator does count, because paragraph 1’s search finds it. Its later call on the const object fails (failed invocations). A function pointer’s opt-in depends on its function type’s parameters, regardless of which function, if any, it designates.

A parameter declared with a placeholder such as auto, or whose type depends on the callee’s own template parameters, does not count. A type depending only on an enclosing class template’s parameters counts by its instantiated declaration ([temp.inst] paragraph 3.1). This test reads declarations. It forms no expression and instantiates no function body.

An annotation that opts in is active. Otherwise it is passive. For an active annotation, F shall be well-formed and overload resolution shall select an eligible callee that declares the context parameter. Its return must satisfy the result policy and E shall be well-formed. E is then a mandatory constant evaluation. Overload resolution still considers surrogate call functions where [over.call.object] requires them, but selecting one fails the eligibility requirement. An active annotation never falls back to passive (outcomes).

This is the working scope for the next revision and prototype. Conversion-based participation would require rules for which conversion declarations opt in and which near misses are errors.

9.1.1. The parameter type names the protocol

A callee written for it already mentions std::meta::annotation_context so no marker, trait, registration, specially named member, or argument-dependent customization function is needed. [P3394R4] section 4.5 also suggests a reserved member name such as annotate_declaration. That would exclude function pointers and captureless lambdas, which the declared parameter admits (callable forms). The new type preserves C++26 behavior (compatibility).

Poll 1 also offers direct-call validity as the opt-in. Under that alternative, a callee taking auto can accept the context without naming its type. A C++26 generic predicate such as Positive (example) would become active and have its body instantiated with the context. A body written for payload values would then make the program ill-formed. Conversely, an annotation_context& parameter or non-const call operator would make the call invalid and leave the annotation passive without a diagnostic. The declared-parameter rule keeps the predicate passive and diagnoses the near miss.

9.1.2. Call operators and function pointers can opt in

Pointers to functions, static and non-static call operators, explicit object member functions, and captureless lambdas opt in when the eligible callee declares the parameter. The examples show the pointer and static forms, alongside a conversion-only value that stays passive. A closure type is structural if and only if the lambda has no lambda-capture ([expr.prim.lambda.closure] paragraph 4) so a captureless lambda yields an admissible annotation value without being declared consteval. Function pointers are already admissible annotation values when [meta.reflection.result] and [temp.arg.nontype] permit their formation. [N5054] [expr.const.const] treats pointers to immediate functions as consteval-only values rather than rejecting them ([P4101R1], [N5055]).

The context argument is the prvalue C. A parameter of type annotation_context, const annotation_context&, or annotation_context&& binds it. A plain annotation_context& still opts in but cannot bind it, which is an error. For a class-type value the object expression is the const template parameter object. A call operator with an implicit object parameter therefore has to be const. An explicit object parameter has to be taken by value or by reference to const. A static call operator needs neither. Default arguments, constraints, and conversions follow ordinary expression semantics. No implicit conversion to annotation_context or from it is added.

A generic overload beside the declared one can still win. For the prvalue C, template<class V> void operator()(V&&) const is a better match than void operator()(const annotation_context&) const ([over.ics.rank] paragraph 3.2.3). The call is then an error.

An annotation whose value is a std::meta::info or a pointer to member does not opt in, even when the reflected function or the pointer’s function type declares the parameter. Neither value is a callee of a direct call. The protocol does not adopt the INVOKE rules of std::invoke for pointers to members ([func.require]). A directly callable wrapper can supply that adaptation itself.

9.1.3. The opt-in tests only the parameter type

The opt-in tests only the declared parameter type, not consteval, the return type, or the exception specification. A deduced return type does not cause this participation test to instantiate a callback body. Call formation, return-type deduction, and result admissibility belong to the required invocation stage, where ordinary semantics may require that body.

Requiring consteval would reject constexpr callees that already satisfy mandatory constant evaluation. Neither specifier affects function type ([dcl.constexpr]) and immediate escalation can make a function immediate without the specifier ([expr.const.imm]). A manifestly constant-evaluated call does not move the callback body into an immediate function context. A non-immediate constexpr callback using the context’s consteval accessors may need if consteval or a consteval declaration.

Ordinary call syntax admits more return types than can be retained as persistent metadata. A void return has no result. A supported by-value return is captured under the materialization rules. A reference return is rejected explicitly, even when ordinary by-value deduction for reflect_constant could copy its referent. This scoped restriction leaves reference-result semantics for separate consideration. A callback that wants to provide identity can return an appropriate reflection by value, subject to its ordinary restrictions.

Required destruction remains part of the full-expression ([intro.execution], [class.temporary]). A deleted or inaccessible destructor makes E ill-formed. Destruction that violates [expr.const.core] makes its required evaluation fail. Returning normally from the callback is insufficient in either case.

An exception that escapes a function with a non-throwing exception specification invokes std::terminate ([except.handle]). That yields neither a successful constant evaluation nor the escaping-exception diagnostic. A validator that rejects by throwing should omit noexcept.

9.1.4. Every failed invocation is an error

The outcome depends on the value’s type and the resulting call. Access is checked from the access anchor, so a private call operator can be valid at an annotation site inside its class and inaccessible elsewhere.

9.2. Only a well-formed annotation can opt in

The opt-in test applies only after the annotation forms and applies under [dcl.attr.annotation] and its construct is formed to the extent the processing point requires. Malformed expressions and annotations that cannot apply remain ordinary errors. Existing formation and substitution rules remain in force.

9.3. No C++26 annotation changes behavior

A passive annotation remains observable metadata and nothing is invoked for it. Passive does not mean ignorable.

No C++26 annotation opts in, because std::meta::annotation_context does not occur in [N5054]. A C++26 generic predicate annotation, one whose type declares template<class V> constexpr bool operator()(const V&) const, stays passive (the opt-in rule). Every C++26 annotation therefore keeps its C++26 behavior.

9.4. Annotation values stay structural

We do not alter annotation formation rules. An annotation’s value remains subject to the structural-type restriction inherited from reflect_constant. Relaxing that restriction is a separate proposal.

9.5. Capture uses the existing constant-materialization requirements

[N5054] [meta.reflection.result] declares:

template<class T>
consteval info reflect_constant(T expr);

Paragraph 1 requires T to be a cv-unqualified structural type, not a reference type, with is_copy_constructible_v<T> true. Deducing T for the by-value parameter uses ordinary [temp.deduct.call] rules, which ignore top-level argument cv-qualification. [expr.type] also removes top-level cv-qualification from non-class, non-array prvalues. A cv-qualified by-value return therefore needs no separate normalization or conversion scheme. The ordinary initialization requirements still apply.

The type requirements are necessary but not sufficient. [meta.reflection.result] paragraphs 2 through 5 describe a value V and require validity of an invented specialization TCls<V> with a constant template parameter of type T. For class T, V is a template-argument-equivalent object. Otherwise it is the value of expr. The return is the reflection of that specialization’s template argument. An invalid TCls<V> causes std::meta::exception to be thrown. These are existing capture rules, not new persistence capabilities.

[temp.arg.nontype] governs constant initialization, the class-type template parameter object’s copy initialization, and template-argument equivalence. Relevant conversions and copies must succeed and preserve the required value. Structural objects containing inadmissible pointers or references still fail, including forbidden pointers to string literals or temporaries. Returning a pointer to invocation-local storage does not extend its lifetime. Strings, containers, and allocations are not promoted to persistent storage automatically. Existing facilities such as define_static_string can prepare an admissible value (the descriptor example).

For a class result, the retained reflection represents the const T template parameter object with static storage duration under [temp.param]. For a scalar result, it represents a value ([meta.reflection.result], [meta.reflection.queries]). The pair’s association is unique but the underlying reflected constant need not be. Different pairs can yield equal values and, where existing reflection rules permit, equal reflections. That equality does not identify their annotations or invocations. There is no guarantee of fresh allocation, distinct addresses, or a particular copy count.

Every supported result is data. false is a Boolean value, an integer is not a status code, and returning an active-annotation object does not invoke it. Returning std::meta::info uses the same capture rule: the retained reflection represents that info value. extract<std::meta::info> recovers it, including info{} (null and false results). It does not request injection, attachment, or mutation. Later explicitly forming an annotation from an extracted admissible value is a separate annotation formation.

Existing template<class T> consteval T extract(info r) and splicing recover values under their own requirements ([meta.reflection.extract], [expr.prim.splice]). For by-value extraction from a retained result, extract uses constant_of(r) and the existing type-match and pointer, array, or closure conversion conditions. It does not provide arbitrary numeric conversions. Failure of those conditions throws std::meta::exception. No parallel extraction system is proposed.

The retained value is immutable, but a reflection within it can refer to an entity whose observable properties later change with the evaluation context. Retention does not freeze that entity or every object reached through a pointer.

9.6. An invocation changes neither annotation nor declaration

An invocation changes neither the annotation’s value nor the construct it applies to. Modifying the copy that a by-value explicit object parameter receives leaves the annotation unchanged. A retained result is a separate association, not a replacement or additional annotation, a declaration, or an editing instruction. It changes neither annotations_of nor constant_of(annotation). Adding or changing annotations is outside this proposal (related work).

9.7. Invocation is a mandatory constant evaluation

The implementation evaluates each active occurrence/target pair’s full-expression E once in the abstract semantics. The callback is not evaluated first for inspection and then again for capture. E is manifestly constant-evaluated, is itself in an immediate function context, and shall be a core constant expression with all required full-expression cleanup succeeding. A pair processed during another constant evaluation (specializations, injected members) has the same capture rule and its own required expression, evaluated within that evaluation. Constructing or retaining a value of an annotation’s type elsewhere schedules nothing.

Every operation that evaluation requires must satisfy the ordinary constant-evaluation rules: argument initialization and default arguments, the callback body, conversions and copies, result materialization, and destruction needed to finish the full-expression ([expr.const.core], [class.temporary]). User-defined capture or cleanup operations can have dependencies of their own. They run before publication and cannot retrieve their pair’s unfinished result.

Capture is required even when no result query occurs. An escaping reflection exception from capture or a failure of required cleanup makes the invocation fail. The implementation may optimize under the as-if rule but cannot make validity depend on whether anyone consumes the result. Independently required evaluations retain their own success requirements even when nested (failure boundaries).

Definitions needed by the call must be available at the processing point under ordinary definition and reachability rules ([expr.const.core], [module.reach]). This applies equally to a pointed-to function and a call operator. The declaration-only opt-in test cannot supply a missing body or make a later definition available retroactively. Core wording must specify how module reachability applies at the new program point.

Direct injection has its own poll. [expr.const.core] paragraph 2.32 permits injected declarations only when the enclosing required expression corresponds to a consteval-block-declaration. We propose also admitting an active annotation’s corresponding expression E. Without that change, validation keeps its meaning but direct synthesis cannot succeed.

[expr.const.reflect] paragraph 3 uses the annotation’s position in place of the consteval-block-declaration. An invocation may inject only where a consteval block at that position could. A member annotation therefore cannot inject at namespace scope. A class-head lies outside class scope ([basic.scope.class] paragraph 1), so DefineLayout still works (the synthesis example).

The injected declaration’s locus remains immediately after the invocation at its processing point ([meta.reflection.define.aggregate] paragraph 9.2). An invocation on a member injected by define_aggregate is part of the injecting evaluation and uses the injecting construct’s position (injected members). A specialization’s invocation nested in constant evaluation uses its own annotation’s position.

An invocation, including its nested evaluations, shall not define the entity represented by target(). define_aggregate already excludes complete classes ([meta.reflection.define.aggregate]), so this restriction matters for a non-defining class declaration that a separate consteval block could complete. The working scope retains this restriction.

9.7.1. Direct injection adds permission and an annotation-position scope rule

The base protocol needs processing points, invocation order, and nested-evaluation rules even without direct injection. A specialization required by a callback can inject through its own consteval block, with that block’s required expression, permission, and permitted scopes. Annotations on the generated members then run nested (injected members). These generation dependencies remain in the base protocol. Earlier injections must be visible at later processing points and the own-target prohibition covers all nested evaluation. The nested case illustrates this route.

Direct injection adds permission for E under [expr.const.core] paragraph 2.32 and uses the annotation’s position for permitted scopes under [expr.const.reflect] paragraph 3. That position differs from the processing point used for evaluation and reachability, the access anchor used for access checking, and the injected declaration’s locus. Generation facilities retain their own target and generation requirements. Direct permission does not allow modifying the annotated construct or its existing annotations.

These provisions support DefineLayout without arranging a specialization’s consteval block. Their incremental implementation cost remains unmeasured. The prototype configurations must test both routes and advertise direct support separately.

10. Post-construct processing leaves dependency ordering unresolved

The working schedule processes annotations after their constructs, except for newly required invocations nested in another constant evaluation (specializations, injected members). A pair already assigned a processing point retains it on later encounters. The schedule preserves ordinary lookup, reachability, and definition availability. Ordering between type and object callbacks in one declaration, lambda placement, dependent-specialization ordering, and cross-translation-unit correspondence remain open.

Annotation formation, construct formation or instantiation, opt-in detection, call resolution, invocation evaluation, and result publication are distinct steps. Forming a construct does not complete its callbacks. Once it is formed to the required extent, the opt-in test reads declarations. The active pair’s call is resolved and evaluated at its assigned point or nested evaluation. A consumer can rely on its checks and retrieve its result only after the required full-expression succeeds (consumer guarantees).

[meta.reflection.annotation] paragraph 2 gathers annotations after the outermost enclosing class for a query from a complete-class context ([class.mem.general] paragraph 10). It does not schedule member or base-specifier callbacks. We choose post-class processing so callbacks can inspect the whole member-specification, including later members. Code inside the class can still observe an earlier member’s annotation before its callback runs (mid-class invocation).

The outermost-class choice follows annotation queries. [meta.reflection.annotation] paragraph 2 considers declarations reachable after the outermost class specified there. At a post-class processing point, a callback may call an in-class constexpr function whose definition is ordinarily available there. Class completeness alone does not supply an unavailable definition or instantiate every lazy member. Bodies, default arguments, default member initializers, and exception specifications retain their ordinary requirements ([class.mem.general], [temp.inst], [except.spec]). The callback does not postpone an earlier semantic check until its effects are available.

This does not prohibit later reflective observations from earlier-written code. If a callback defines Generated after the class, a body calling std::meta::size_of(^^Generated) can observe that definition through the evaluation context of a call made after the callback. Default arguments and default member initializers retain the evaluation-point rules of [expr.const.reflect] paragraphs 5.1 and 5.2. An exception specification needed before generation cannot use that later context. Reflective visibility and ordinary source-point availability remain distinct ([module.reach]). The examples show the distinction.

An enumeration with a fixed underlying type is complete immediately after its enum-base ([dcl.enum] paragraph 6). All scoped enumerations have a fixed underlying type (paragraph 5), so enum class [[=X]] E { a, b }; is complete before either enumerator is declared. Processing instead follows the closing brace, with enumerator annotations processed in declaration order before annotations on the enumeration definition (constituent-before-whole order).

A lambda-expression introduces a closure type without a class-specifier ([expr.prim.lambda.closure] paragraph 1). The table therefore assigns no point to annotations on lambda parameters or call operators. Their point and order relative to body annotations remain undecided, including for a templated call operator. The opt-in rule already admits captureless lambda values as annotations.

Call resolution can depend on other declarations. A constraint such as requires { sizeof(Subject); } depends on Subject’s completeness, which an earlier injection can change. Resolution therefore occurs once at the processing point. The constraint-stability requirements of [temp.constr.atomic] still apply.

10.1. A target can still be incomplete

For a non-defining declaration whose class is still incomplete at the processing point, ctx.target() represents an incomplete type. Queries requiring its members cannot succeed. Completeness belongs to the type, as the enumeration case shows. A redeclaration after the definition, such as struct S { }; struct [[=X]] S;, has a complete target but defines nothing. ctx.is_definition() reports whether the declaration is a definition. A callback requiring completeness uses is_complete_type(ctx.target()).

10.2. An invocation sees what is reachable at its processing point

A namespace can be reopened in this or another translation unit, so it has no completion point. An annotation on a namespace-definition runs at its closing brace and sees that definition’s declarations, not later additions.

[dcl.attr.annotation] paragraph 1 bars annotations on non-defining friend declarations and declarations whose host and target scopes differ ([CWG3124]). This excludes block-scope extern declarations. A qualified redeclaration inhabits namespace scope ([dcl.meaning.general] paragraph 3.1), making its host and target scopes the same ([basic.scope.scope] paragraph 2). An out-of-class member definition can therefore carry its own annotations, processed at its own point after the class’s invocations.

Any redeclarable entity has the same reachability limit. [meta.reflection.annotation] paragraph 2 gathers only declarations reachable at the query point. A function’s first declaration is processed before later redeclarations contribute their annotations (occurrence/target pairs). Waiting until the translation unit ends would include those declarations but delay validation beyond earlier consumers. The diagnostic could still identify the annotation site and the check would still lack a view across translation units. Non-static data members and base-specifiers have no later redeclarations.

A retained result remains the value computed for its particular occurrence/target pair. Later declarations neither recompute it nor attach it to their new occurrences. A reflection contained in the result is still interpreted under the later query’s ordinary reflective context.

10.3. Annotations on injected members run inside the injection

[meta.reflection.define.aggregate] paragraph 9.5.6 gives injected members the annotations in data_member_options. We propose processing them inside define_aggregate after the class is complete. Each invocation is its own required constant expression within the injecting evaluation (the invocation contract), as for a nested specialization.

The injecting evaluation sees declarations injected earlier in it ([expr.const.reflect] paragraph 5.5). The invocation must share that context, so wording must exclude it from paragraph 5.4’s separate context for nested manifestly constant-evaluated expressions. Chained injections nest these expressions. Exceeding an implementation-defined evaluation limit is an error ([expr.const.core] paragraph 2.7).

An escaping exception makes the invocation fail its own constant-expression requirement. The injecting code cannot catch that error (failed invocations). Skipping injected members would let define_aggregate apply active annotations without invoking them.

Each newly formed injected annotation has its own pair and applies the same capture and publication rules. Copying an input annotation value into data_member_options does not transfer a result computed for another target. After a nested member invocation completes, the injecting evaluation can retrieve its result under the publication rule.

[P4033R1] proposes define_enum with an enumerator_options that carries annotations the same way. An enumerator it injects would take the same rule.

10.4. Declarators run in order, with each target’s annotations together

When processing the annotations of any covered construct, order its active occurrences by the lexical order of the applicable attribute-specifiers containing annotation-lists and, within each specifier, the left-to-right order of its annotation-list ([dcl.attr.grammar] paragraph 1). An expansion occupies its source position and contributes its elements in pack expansion order. Only applicable occurrences assigned to that construct’s processing participate. This per-target rule covers class and enum definitions and base-specifiers as well as declarator targets. It does not combine separate redeclarations' processing points.

For an ordinary simple-declaration with an init-declarator-list, or a member-declaration with a member-declarator-list, process the declarators in their declared order. For each target, process all its assigned active occurrences in the order above before moving to the next declarator.

Thus, for active A and B, this member-declaration has the sequence below:

struct S { [[=A{}, =B{}]] int x, y; };
Declarator-first processing after S is complete. Each step completes its full-expression, including capture and cleanup, and publishes any retained result before the next starts.
Step Occurrence/target pair
1 A on x
2 B on x
3 A on y
4 B on y

The A occurrence is shared by x and y, as is the B occurrence. Neither is cloned. Each occurrence/target pair has its own invocation and result (identity). This orders already scheduled pairs at their assigned post-construct processing points. It does not run a callback between formation of x and y: both members are declared and S is complete before step 1. An ordinary namespace-scope declaration likewise finishes before its callbacks start.

Leading specifiers apply to each entity in these declaration forms ([dcl.pre] paragraph 4, [class.mem.general] paragraph 18). A specifier immediately following a declarator-id applies to that entity ([dcl.meaning.general] paragraph 1). For active A, B, X, and Y, the following therefore orders A(x), B(x), X(x), A(y), B(y), Y(y):

[[=A{}]] [[=B{}]] int x [[=X{}]], y [[=Y{}]];

This is not a rule that every specifier written in a declarator annotates its entity. Appertainment follows the existing grammar. [dcl.decl.general] paragraph 3 separately analyzes each init-declarator and member-declarator, which motivates the proposed order but does not already prescribe delayed callbacks. Nor does the order returned by annotations_of prescribe their execution.

The constituent-before-whole rule still applies. A class-specifier processes base-specifier annotations in base-specifier-list order, then member-declarations in lexical order using the declarator-first rule, then annotations on the class definition. An enum-specifier processes enumerator annotations in declaration order before its own. A nested class occupies its lexical place among the members and follows the same internal rule. For struct [[=Z]] Outer { struct [[=X]] Inner { [[=Y]] int m; }; };, the order is Y, X, then Z. Inner at namespace scope still processes Y before X.

A function declarator processes its parameters in parameter-declaration order, with each parameter’s applicable annotations in the order above, then its own annotations. In a multi-declarator declaration this finishes that function’s pairs before proceeding to the next declarator. These local rules order covered constructs at their assigned points. They do not flatten a translation unit into one sequence or choose the unresolved order between dependent specializations or imported occurrences.

Order is observable through result dependencies even without injection. A later callback can consume an earlier pair’s completed result. Reversing those callbacks makes that query unavailable. The class-definition collector in § 7.3 A class callback collects completed member results uses this order to read member results.

Injection also makes order observable. [meta.reflection.define.aggregate] paragraph 9.2 places an injected declaration "immediately after the core constant expression currently under evaluation". If one callback generates a class, directly or through a specialization’s consteval block, a later callback’s is_complete_type query depends on whether that locus precedes its point. A shared point would not establish this order. [expr.const.reflect] paragraph 5.5 carries injections only within one evaluation. Wording therefore needs a processing point for each pair, ordered as above, with earlier injections visible at later points.

10.4.1. Defining a type and an object together still needs an order

The relative order between a class or enum definition in a declaration’s decl-specifier-seq and that declaration’s declarator targets remains unresolved when their processing points coincide. Using ProduceResult and ReadResult:

struct [[=ProduceResult{}]] S {} object [[=ReadResult{^^S}]];

Both callbacks follow the entire declaration. The rules above order neither S’s callback before object’s nor the reverse. They therefore supply no preceding producer completion for the result query, which throws under the publication rule. Choosing definition-first processing would make this dependency succeed, but that would be an additional local scheduling rule. This revision leaves the choice open, separately from ordering between dependent specializations.

10.4.2. A first-declarator consumer cannot read a later-declarator result

This independent example makes the combined order observable without injection:

#include <meta>

struct A
{
    consteval int operator()(std::meta::annotation_context) const
    {
        return 7;
    }
};

struct B
{
    consteval void operator()(std::meta::annotation_context ctx) const
    {
        if (std::meta::identifier_of(ctx.target()) == "x") {
            auto members = std::meta::nonstatic_data_members_of(
                std::meta::parent_of(ctx.target()), ctx.access());
            auto y = members[1];
            auto producer = std::meta::annotations_of_with_type(y, ^^A)[0];
            static_cast<void>(std::meta::annotation_result_of(producer, y));
        }
    }
};

struct S { [[=A{}, =B{}]] int x, y; };

A(x) completes first. During B(x), y and its input annotations are observable, but A(y) is still pending. The query throws and its uncaught exception fails B(x)’s required invocation. The program is ill-formed, so this is not a successful trace continuing through steps 3 and 4. Catching that exception within B(x) could allow it to finish, but would neither run A(y) early nor retry the query.

The occurrence-first alternative A(x), A(y), B(x), B(y) would satisfy this dependency. The proposed declarator-first order deliberately does not.

10.5. A result is published only after its full-expression succeeds

Publication is a proposed semantic event at successful completion of a pair’s entire full-expression, after capture and all required cleanup. A void invocation has the same completion event but no retained reflection. The events are ordered by the abstract processing schedule and the ordinary evaluation order. Compiler execution order, speculative evaluation, and internal caches do not publish results.

For a query Q, a completed pair is available only if its association is observable in Q’s reflective evaluation context and its successful completion precedes Q under the following rules:

  1. Each non-nested processing point has an end after that pair’s full-expression. Its completion precedes later points in the specified processing order and subsequent program points. This includes capture, cleanup, and publication for each pair before the next pair in a declarator-first sequence starts. It does not move invocation into declaration formation. A query’s evaluation context carries completions preceding the points in that context. The extra point used by annotations_of to gather annotations in a complete-class context does not itself carry completed callbacks.

  2. Within an evaluation, a completed invocation precedes operations sequenced after that completion. A nested invocation starts with the completed associations carried by its specified evaluation and instantiation contexts. Its completion precedes subsequent operations in the resumed enclosing evaluation. It does not precede earlier operations or the enclosing invocation’s still-unreached completion.

  3. The propagation follows the existing formation of reflective evaluation contexts in [expr.const.reflect], with the proposed context rules for nested specializations and injected members. An ordinary helper body can use completions carried by a later call’s context, regardless of where the body was written. A separately manifestly constant-evaluated expression keeps its own context under paragraph 5.4 except for the explicit nested-invocation extensions.

  4. A reachable imported completed pair carries its completion and retained result under the proposed import rule. No other rule infers completion from an observed annotation or a computed equal value.

The precedence relation is the transitive closure of these rules. If the specified order supplies no preceding completion, the query throws. This does not choose a trigger or an order in cases the schedule leaves unresolved (combined type and object declarations, dependent specializations, selected uses, lambda constructs).

A pair is unavailable throughout its callback, capture, and cleanup. This includes self-queries through helpers, copy operations, destructors, or nested evaluations. A completed child can be read after control returns to its parent, but the child cannot read the unfinished parent’s result. Repeated queries after publication retrieve the retained reflection without recomputing it.

An unavailable-result exception is an ordinary reflection exception. Catching it can let the current required evaluation succeed. Leaving it uncaught fails that evaluation. Catching outside a separately required nested invocation cannot repair that invocation’s failure. A producer needed before completion, a cycle through unpublished results, or a reversed producer/consumer order receives no reordering, fixed-point computation, waiting, or retry.

Publication is not a transaction over callback effects. An injection visible before callback completion remains visible according to [expr.const.reflect] and the proposed nested-context rules. Result capture neither delays that injection until publication nor rolls it back when capture later fails. Such failure still makes the program ill-formed.

10.6. Invoking mid-class would miss later members

Invoking each member or base-specifier annotation as soon as its construct forms would complete validation earlier. A later consteval block or static_assert in the class could rely on those checks. Either schedule can identify the annotation site in a diagnostic.

However, each callback would see only the preceding part of the class. GuardedBy would fail when its mutex is declared later (the guard example) and base-specifier annotations would see only bases to their left. The rule’s result would depend on annotation placement within the member-specification. Post-class processing supports these checks while retaining earlier source-point requirements.

10.7. Specializations are processed where first required

We propose invoking annotations on or within templated entities once per specialization. A specialization first required outside constant evaluation is processed after the referring namespace-scope declaration. A newly required invocation during constant evaluation nests within it. An already scheduled pair keeps its assignment. Order between dependent specializations remains open.

10.7.1. Each specialization has its own annotation pairs

The unit is the specialization, whether or not the annotation’s expression is dependent. That holds for an annotation on the template itself, which is where the draft’s own example puts one. [meta.reflection.annotation] paragraph 4 spells out template<class T> struct [[=42]] D { };, binds a1 and a2 to annotations_of(^^D<int>)[0] and annotations_of(^^D<char>)[0], and asserts that the two differ while their constant_of results are equal. Each specialization’s pair is invoked separately. [dcl.attr.annotation] paragraph 3 requires their identities to be preserved, which leaves memoization to the as-if rule. The words "or instantiation thereof" in that paragraph came from [CWG3145] and were added for this case. We specify no template-definition callback.

No invocation happens only because an annotation appears in an uninstantiated template. The ordinary template-definition and annotation-formation rules still apply to it. An explicit specialization is not generated from the template. Only the annotations it writes for itself are processed for it.

Each instantiated occurrence/target pair captures its own result under the same policy. Equal captured values do not merge pairs. Result queries do not instantiate arbitrary callbacks for otherwise unrequired specializations.

10.7.2. The first requirement determines the invocation point

"Required" means required by language semantics. [temp.inst] paragraph 2 requires class instantiation when completeness is needed or affects semantics. Paragraph 10 permits unnecessary instantiation during overload resolution. Neither that optional work nor speculative evaluation schedules callbacks. The source use must require the specialization.

The semantic requirement that first schedules a pair determines whether invocation is deferred or nested. Nesting covers an ongoing abstract constant evaluation and instantiation of a definition it needs. Merely naming a specialization inside a consteval block or constexpr function is insufficient, because expression formation can require instantiation before evaluation. Function-specialization uses and requirements with no language-defined order still need classification.

A template specialization first required outside a constant evaluation, including a class template specialization named in a base-clause, has its annotations processed at the point immediately following the namespace-scope declaration or definition that refers to it. A derived class in the curiously recurring template pattern is therefore complete when its base’s annotations run, because a base-clause is not an evaluation. [temp.point] paragraph 1 gives a function template specialization’s point of instantiation this shape. Paragraph 4 puts a class template specialization’s point of instantiation immediately before that declaration instead, which would place an injected declaration ahead of the code that required the specialization. The processing point is not a point of instantiation. Paragraph 7’s limit of one point of instantiation per translation unit for a class template specialization does not apply to it.

A specialization first required during constant evaluation, including another invocation, processes its annotations during instantiation within that evaluation, like an instantiated class’s consteval blocks. Each invocation has its own required constant expression. Its evaluation point combines the annotation’s position and the specialization’s instantiation context. [expr.const.reflect] paragraphs 5.3 and 5.5.1 supply these for a consteval block but not for the synthesized invocation. A failed invocation is an error at the evaluation requiring the specialization.

For such an implicit instantiation, [module.context] paragraph 6 includes the enclosing evaluation context in the instantiation context. We propose that the assigned invocation point retain that instantiation context. Earlier synthesized injection points can then be observed under [expr.const.reflect] paragraph 5.5.1. This does not move the annotation’s access anchor or permitted injection scope. Injected-member invocations use the separately stated shared evaluation context. Each invocation still has its own required-expression success condition.

template<int N> struct T;

template<int N> struct Next
{
    consteval void operator()(std::meta::annotation_context) const
    {
        static_cast<void>(sizeof(T<N + 1>));
    }
};

template<int N> struct T { [[=Next<N>{}]] int m; };

T<0> t;

T<0> t; requires T<0> by declaration, so Next<0> runs immediately afterward. Its evaluation requires T<1> and every later link nests. This needs no injection. Like other template recursion, it falls under [temp.inst] paragraph 18, which leaves this infinite case undefined.

10.7.3. A repeated encounter keeps the assigned schedule

Once assigned, a pair’s processing point does not advance on a later encounter, even during constant evaluation. An encounter neither re-enters a running invocation nor repeats a completed one. These states describe abstract semantics, not a public state API. Reflection queries do not flush pending callbacks. In particular, annotation_result_of throws while the active pair remains pending or running, even if its declared return type is void.

#include <meta>

struct RequireComplete
{
    std::meta::info type;

    consteval void operator()(std::meta::annotation_context) const
    {
        if (!std::meta::is_complete_type(type))
            throw 0;
    }
};

template<class T> struct [[=RequireComplete{^^T}]] Base {};

struct Derived : Base<Derived>
{
    static_assert(std::meta::size_of(^^Base<Derived>) > 0);
};

The specialized RequireComplete{^^Derived} occurrence and Base<Derived> form one pair under the base protocol. The base-clause requires the specialization outside constant evaluation, scheduling its callback after Derived. The assertion can inspect the complete base without completing its callback. Keeping the assigned point lets RequireComplete observe complete Derived and succeed. Advancing it to the assertion would expose incomplete Derived and fail.

A pending or running pair permits inspection of input metadata without guaranteeing successful validation or providing a result. Uses requiring a definition the callback has not produced follow ordinary lookup, completeness, and constant-evaluation rules. There is no wait, retry, or second invocation to supply it.

Effects can be observed before a callback completes. A nested evaluation can see an earlier injection when its context includes the synthesized point. On resumption, earlier sequenced effects remain observable under [expr.const.reflect] paragraph 5.5.2. This does not make injected definitions available to ordinary syntax at earlier source points. Later invocations see earlier injections under the processing-point rule.

10.7.4. A class template’s members are processed when they are instantiated

The recursive order does not carry over to a class template. [temp.inst] paragraph 3.1 instantiates the declarations and not the definitions of member classes and scoped member enumerations. Given

template<class T> struct [[=Z]] Outer { struct [[=X]] Inner { [[=Y]] int m; }; };

instantiating Outer<int> processes Z alone. X and Y are processed when Outer<int>::Inner is instantiated, which may never happen. Under paragraph 3.2 the definition of an unscoped member enumeration is instantiated with the enclosing class, which processes its enumerator annotations too. Both cases belong in the wording.

10.7.5. A failed invocation in a specialization is a hard error

Annotation formation remains governed by [dcl.attr.annotation], including the rule in paragraph 4 that substituting into an annotation is not in the immediate context. The draft’s own example shows the extent of that hard error.

template<class T>
  [[=T::type()]] void f(T t);

void f(int);

void g() {
  f(0);         // OK
  f('0');       // error, substituting into the annotation results in an invalid expression
}

f(0) is well-formed despite invalid int::type(), because candidate formation does not substitute into annotations. Substitution follows selection, so only the call choosing the template is ill-formed. Invocation has the same failure model. The opt-in test forms no expression and a failed invocation is a hard error, never a substitution failure for the enclosing template. Otherwise a violated rule could silently deselect an overload and leave a diagnostic naming another candidate or none.

Forming an unselected function-template candidate does not itself schedule that function’s callbacks. [temp.inst] paragraph 11 instantiates declarations for overload resolution, but the example separates that from required annotation processing. Independently required class instantiations for forming or comparing candidates remain unaffected. Selected uses that need no function definition, such as unevaluated address expressions or selected calls, still need a trigger rule.

10.7.6. The working rules leave dependent specialization semantics unresolved

The order for a specialization referenced from a dependent context in another specialization ([temp.point] paragraphs 1 and 4) remains undecided. The opposing result-only dependencies distinguish the candidate orders without injection. The accompanying injection cases expose the same choice through definition availability. Both candidate orders preserve each specialization’s internal order but reject one acyclic dependency in each set.

Cross-translation-unit correspondence is also unresolved. The same specialization may first be required by a declaration in one translation unit and during a constant evaluation in another. The intended policy retains occurrence-local results subject to existing consistency obligations. Wording must classify the synthesized callback/capture expressions for the corresponding-expression requirements of [basic.def.odr], as the Observe case demonstrates. Comparing TU-local annotation reflections cannot establish that correspondence. The interaction with candidate formation under [temp.inst] paragraph 11 remains open as described above.

10.8. Each active occurrence/target pair is invoked once

An occurrence can apply to multiple constructs, so the invocation unit is the occurrence/target pair. [meta.reflection.annotation] paragraph 4 illustrates shared identity with [[=1]] int x, y; and annotations_of(^^x)[0] == annotations_of(^^y)[0]. The integer annotation is passive. An active annotation in its place opts in for both variables and runs once for each, with ctx.target() representing each in turn. The combined declarator-first rule orders these pairs together with any other applicable occurrences without changing their identities.

An annotation on a parameter-declaration in a function definition is one pair, as specified by the target accessor. There is no second invocation for its variable.

Equivalent annotations on more than one declaration of an entity are each processed independently. Merging them would make the design depend on cross-translation-unit ordering and the ODR. A library can enforce a multiplicity rule in the operator through annotations_of only when the entity cannot be redeclared, as with a non-static data member (the primary-key example, reachability).

10.9. Expanded active annotations are invoked independently

Under [dcl.attr.grammar] paragraph 6, an annotation followed by an ellipsis is a pack expansion. Each expanded element produces a unique annotation. Each active occurrence/target pair among them is invoked independently. Under the combined order, the expansion’s elements occupy its source position, in expansion order, among the ordinary annotations for one target before processing the next declarator. An expanded occurrence shared by multiple declarators keeps its identity across those targets.

10.10. The cases distinguish proposed rules from open choices

These independent traces apply the proposed rules, not compiler execution. Replacements and shared-header cases are identified. The base protocol includes indirect injection. Cases needing direct permission say so. The evidence table distinguishes compiled controls from proposed outcomes.

10.10.1. Queries can inspect a pending, running, or completed pair

This case uses the base protocol.

#include <meta>

struct Inspect
{
    consteval void operator()(std::meta::annotation_context ctx) const
    {
        if (std::meta::annotations_of(ctx.target()).size() != 1)
            throw 0;
    }
};

struct Subject
{
    [[=Inspect{}]] int member;
    static_assert(
        std::meta::annotations_of(^^Subject::member).size() == 1);
};

static_assert(
    std::meta::annotations_of(^^Subject::member).size() == 1);

The Inspect{} occurrence and Subject::member form a pair scheduled after Subject. The in-class assertion queries it while pending, the callback while running, and the later assertion after completion. All succeed under the repeated-encounter rule, without promotion, re-entry, or repetition. The unchanged annotation count does not indicate completion. Only the last query follows the completed check.

Replacing these metadata observations with annotation_result_of for the pair makes the first two queries throw and the last return the null reflection. Inspect returns void but completed absence cannot be reported while it is pending or running. Catching the exception inside Inspect would permit its invocation to finish. An uncaught self-query would fail the required invocation.

10.10.2. An unavailable generated definition does not cause waiting

This case requires direct injection.

#include <meta>

struct Generated;

struct Generate
{
    consteval void operator()(std::meta::annotation_context) const
    {
        std::meta::define_aggregate(^^Generated, {});
    }
};

struct [[=Generate{}]] Subject
{
    static_assert(!std::meta::is_complete_type(^^Generated));
};

static_assert(std::meta::size_of(^^Generated) > 0);

Generate{} and Subject form a pair processed after the class definition. The in-class assertion sees incomplete Generated without flushing the callback. The callback then defines Generated, using the namespace injection permitted at its class-head annotation. Its target remains Subject. The final assertion sees the definition and succeeds.

Replacing the in-class assertion with static_assert(std::meta::size_of(^^Generated) > 0); fails because that evaluation needs the unavailable definition. It does not wait or retry after injection. Existing metadata can be inspected before a pending callback produces its effects. The same availability rule applies to indirect injection.

10.10.3. Post-class processing need not instantiate unused bodies

This case uses the base protocol.

#include <meta>

template<class T>
struct Check
{
    consteval void operator()(std::meta::annotation_context) const
    {
        if (T::value() != 42)
            throw 0;
    }
};

template<class T> struct Subject;

template<class T>
struct [[=Check<Subject<T>>{}]] Subject
{
    static constexpr int value() { return 42; }
    static constexpr int unused() { return T::absent; }
};

Subject<int> subject;

The object declaration requires complete Subject<int> outside constant evaluation. Its specialized occurrence/target pair runs after that declaration and calls the available Subject<int>::value, which returns 42. The invocation succeeds without instantiating unused’s definition ([temp.inst] paragraph 3.1).

Calling T::unused() instead requires its definition. For Subject<int>, int::absent makes the body invalid and the required invocation fails with a hard error.

10.10.4. Later reflective evaluation does not repair an earlier source-point requirement

This case requires direct injection.

#include <meta>

struct Generated;

struct Generate
{
    consteval void operator()(std::meta::annotation_context) const
    {
        std::meta::define_aggregate(^^Generated, {});
    }
};

struct [[=Generate{}]] Subject
{
    int bytes = std::meta::size_of(^^Generated);

    static constexpr int argument(
        int n = std::meta::size_of(^^Generated))
    {
        return n;
    }

    static consteval int size()
    {
        return std::meta::size_of(^^Generated);
    }
};

constexpr Subject object{};
static_assert(object.bytes == sizeof(Generated));
static_assert(Subject::argument() == sizeof(Generated));
static_assert(Subject::size() == sizeof(Generated));

The Subject pair runs after its definition and completes Generated before the uses below it. The initializer’s reflective query uses the later initialization point ([expr.const.reflect] paragraph 5.1), the default argument uses the later call point (paragraph 5.2), and the body uses the later call’s evaluation context. All three assertions succeed under these existing reflective rules and the proposed schedule.

Replacing the initializer with int bytes = sizeof(Generated); is ill-formed because ordinary sizeof needs completeness at its source point. A nondependent ordinary sizeof(Generated) in the earlier body or default argument fails likewise. Generation does not depend on these expressions, so this is an acyclic dependency the proposed schedule deliberately rejects.

A reflective query can also be required too early. Adding this function definition inside Subject needs its exception specification before the callback’s point ([except.spec] paragraph 13):

static void operation()
    noexcept(std::meta::size_of(^^Generated) > 0)
{}

The query then fails on incomplete Generated. Being a complete-class context does not postpone that requirement until annotation processing.

A cycle is distinct from those earlier requirements. This independent direct-injection case requires the generated type before producing it:

#include <meta>

struct Generated;
struct Subject;

template<class T>
struct GenerateFor
{
    consteval void operator()(std::meta::annotation_context) const
    {
        static_cast<void>(T::template size<Generated>());
        std::meta::define_aggregate(^^Generated, {});
    }
};

struct [[=GenerateFor<Subject>{}]] Subject
{
    template<class U>
    static consteval int size() { return sizeof(U); }
};

GenerateFor<Subject>{} runs after Subject, but first needs Subject::size<Generated>. Instantiating that body needs the definition the callback has yet to produce and fails. The schedule neither retries nor moves injection before the call. Reordering the callback would change the program.

10.10.5. Dependent specializations can need opposite orders

These result-only cases use no direct or indirect injection. Each producer returns an admissible integer and each consumer queries the unique producer annotation on the identified class specialization:

#include <meta>

struct ProduceResult
{
    consteval int operator()(std::meta::annotation_context) const { return 7; }
};

struct ReadResult
{
    std::meta::info producer_target;

    consteval void operator()(std::meta::annotation_context) const
    {
        auto producer = std::meta::annotations_of_with_type(
            producer_target, ^^ProduceResult)[0];
        if (std::meta::extract<int>(std::meta::annotation_result_of(
                producer, producer_target)) != 7)
            throw 0;
    }
};

namespace base_result
{
    template<class T>
    struct [[=ProduceResult{}]] Base {};

    template<class T>
    struct [[=ReadResult{^^Base<T>}]] Derived : Base<T> {};

    Derived<int> object;
}

namespace derived_result
{
    template<class T>
    struct [[=ReadResult{^^T}]] Base {};

    template<class T>
    struct [[=ProduceResult{}]] Derived : Base<Derived<T>> {};

    Derived<int> object;
}

In each namespace, object requires complete Derived<int>, which requires its dependent base specialization, outside constant evaluation ([temp.inst] paragraph 2). Reflecting a class type into an annotation’s payload does not itself require its definition. There is no earlier nondependent completeness query hidden in the callbacks. Both callback bodies are available before either object declaration.

In base_result, the producer targets Base<int> and the consumer targets Derived<int>. In derived_result, the producer targets Derived<int> and the consumer targets Base<Derived<int>>. These are annotations on the class specializations, not on base-specifiers. After the object declaration both types are complete and the indicated input annotation/target association is observable. Only the order of their deferred invocations is unresolved.

Conditional result-only outcomes after the referring object declaration. Both orders preserve each specialization’s internal order.
Candidate order base_result derived_result
All base pairs before all derived pairs The base publishes 7. The derived consumer retrieves it and succeeds. The base consumer queries the unfinished derived producer. Its uncaught unavailable-result exception fails the required invocation.
All derived pairs before all base pairs The derived consumer queries the unfinished base producer. Its uncaught unavailable-result exception fails the required invocation. The derived specialization publishes 7. The base consumer retrieves it and succeeds.

[temp.point] paragraph 4 orders instantiation points, not these post-declaration invocation points. Both dependencies are acyclic and either fixed order rejects one. This revision selects neither order nor dependency-directed scheduling. The open question is whether a fixed order’s restriction is acceptable and, if so, which order to use. A failing consumer does not wait or get retried.

10.10.5.1. Injection exposes the same ordering choice

These separate cases require direct injection. Each producer defines a separate namespace-scope type, without changing its annotated target.

#include <meta>

struct Complete
{
    std::meta::info type;
    consteval void operator()(std::meta::annotation_context) const
    {
        std::meta::define_aggregate(type, {});
    }
};

struct RequireComplete
{
    std::meta::info type;
    consteval void operator()(std::meta::annotation_context) const
    {
        if (!std::meta::is_complete_type(type))
            throw 0;
    }
};

namespace enclosing_produces
{
    struct Generated;

    template<class T>
    struct [[=RequireComplete{^^Generated}]] Base {};

    template<class T>
    struct [[=Complete{^^Generated}, =RequireComplete{^^Generated}]]
        Derived : Base<Derived<T>> {};

    Derived<int> object;
}

namespace base_produces
{
    struct Generated;

    template<class T>
    struct [[=Complete{^^Generated}, =RequireComplete{^^Generated}]] Base {};

    template<class T>
    struct [[=RequireComplete{^^Generated}]] Derived : Base<Derived<T>> {};

    Derived<int> object;
}

In each namespace, object requires complete Derived<int>, whose dependent base requires Base<Derived<int>>. Both requirements occur outside constant evaluation. The proposed schedule puts their invocations after object’s declaration but leaves the order between specializations open.

In enclosing_produces, the base’s pair checks completeness. The derived specialization’s pairs produce and then check the definition. In base_produces, the base owns the producer and following check, while the derived specialization owns the remaining check. Each pair targets its own specialization.

Candidate orders for the dependent-specialization cases. Both preserve the order within each specialization.
Order after the referring declaration enclosing_produces base_produces
All base pairs before all derived pairs The base check fails before generation. The base produces and checks the definition, then the derived check succeeds.
All derived pairs before all base pairs The derived specialization produces and checks the definition, then the base check succeeds. The derived check fails before generation.

The same undecided order therefore affects both retained-result availability and injected-definition availability. The result-only cases establish that this issue remains even if direct injection is declined and no indirect injection occurs.

10.10.6. Nested invocations can see effects but must succeed independently

This case uses the base protocol. A specialization’s own consteval block produces the declarations.

#include <meta>

struct NeedComplete
{
    std::meta::info dependency;
    consteval void operator()(std::meta::annotation_context) const
    {
        if (!std::meta::is_complete_type(dependency))
            throw 1;
    }
};

template<class T>
struct Generator
{
    struct Earlier;
    struct Product;

    consteval {
        std::meta::define_aggregate(^^Earlier, {});
        std::meta::define_aggregate(^^Product, {
            std::meta::data_member_spec(^^int, {
                .name = "value",
                .annotations = {
                    std::meta::reflect_constant(NeedComplete{^^Earlier})
                }
            })
        });
    }
};

struct Generate
{
    consteval void operator()(std::meta::annotation_context) const
    {
        auto specialization = std::meta::substitute(^^Generator, {^^int});
        static_cast<void>(std::meta::size_of(specialization));
    }
};

struct [[=Generate{}]] Subject {};

The Generate{} occurrence and Subject form a pair processed after Subject. Its evaluation reflectively requires complete Generator<int>. The specialization’s consteval block defines Earlier, then Product, both within its permitted scope.

The generated NeedComplete occurrence and Generator<int>::Product::value form a nested pair. It runs inside define_aggregate after Product is complete. The proposed shared evaluation context includes the earlier definition of Earlier, so the check succeeds. No callback directly injects. [meta.reflection.define.aggregate] supplies the member and annotation. Invocation and the shared context are proposed extensions.

[module.context] paragraph 6 carries the requiring evaluation’s points into the instantiation context and [expr.const.reflect] paragraph 5.5.1 uses them for reflective evaluation. Neither supplies a point or schedule for the new invocation. A nondependent sizeof(Generator<int>) trigger would not establish this case, because forming the expression can require instantiation before the callback runs.

If NeedComplete instead returns int{1} after its check, that nested pair publishes a retained integer before size_of returns to Generate. The resumed callback can reflect the generated member and retrieve that pair’s result. The nested callback cannot retrieve the still-running Generate pair’s result, including while Generate later captures or destroys temporaries. These availability rules do not depend on whether either callback directly injects.

10.10.6.1. An outer catch cannot satisfy a failed nested invocation

In the preceding example, replace NeedComplete with Reject below, change the generated annotation value to Reject{}, and surround Generate’s two operations with try { ... } catch (...) {}.

struct Reject
{
    consteval void operator()(std::meta::annotation_context) const
    {
        throw 1;
    }
};

The generated occurrence and Generator<int>::Product::value form a pair processed inside the injection. Its exception escapes its own required expression, making the program ill-formed even if the enclosing evaluation has a handler. An outer handler cannot satisfy the nested expression’s requirement.

Replacing Reject and its annotation value with Recover instead succeeds:

struct Recover
{
    consteval void operator()(std::meta::annotation_context) const
    {
        try {
            throw 1;
        } catch (...) {
        }
    }
};

Here the exception is handled inside the expression that must succeed. Sharing reflective context does not merge independent constant-expression requirements. Both variants use the base indirect route. The same distinction applies when a callback directly injects the annotated member.

10.10.7. Translation units can require the same specialization differently

This base-protocol case has the following shared header, shared.hpp:

#include <meta>

struct Marker;

struct Observe
{
    consteval bool operator()(std::meta::annotation_context) const
    {
        return std::meta::is_complete_type(^^Marker);
    }
};

template<class T>
struct [[=Observe{}]] Subject {};

One translation unit first requires Subject<int> through a declaration:

#include "shared.hpp"

struct Marker {};
Subject<int> object;

Another first requires it during evaluation:

#include "shared.hpp"

consteval {
    auto specialization = std::meta::substitute(^^Subject, {^^int});
    static_cast<void>(std::meta::size_of(specialization));
}

Both translation units pair a specialized Observe{} occurrence with Subject<int>. In the first, invocation follows the declaration and sees complete Marker. In the second, it nests when size_of requires completeness during the block’s evaluation and sees incomplete Marker. Under the proposed occurrence-local policy, the invocations capture Boolean values true and false respectively. Each later query of its local pair retrieves that value.

Those different results are now observable. The intended policy permits distinct occurrences to retain different values subject to existing ODR, reachability, exposure, and consistency requirements. It does not establish that this whole program is well-formed. [basic.def.odr] paragraph 16 requires corresponding non-value-dependent manifestly constant-evaluated expressions in repeated definitions to have the same value. Whether these synthesized callback/capture expressions correspond within the repeated specialization definitions needs an explicit wording decision. TU-local annotation identity does not settle it.

There is a separate, definite violation if both translation units append this definition after their respective processing points:

inline constexpr bool shared_observation =
    std::meta::extract<bool>(std::meta::annotation_result_of(
        std::meta::annotations_of(^^Subject<int>)[0], ^^Subject<int>));

Its corresponding constant initializers produce different values, violating [basic.def.odr] paragraph 16. Occurrence-local results do not waive that obligation or agreement required by template arguments, constraints, or injected definitions. No global schedule or once-per-program result record is proposed.

10.10.7.1. Conflicting injected definitions already have a consistency requirement

For the direct-injection variant, replace the header with:

#include <meta>

struct Marker;
template<class T> struct Layout;

struct MakeLayout
{
    std::meta::info destination;
    consteval void operator()(std::meta::annotation_context) const
    {
        auto member_type = std::meta::is_complete_type(^^Marker)
            ? ^^int : ^^char;
        std::meta::define_aggregate(destination, {
            std::meta::data_member_spec(member_type, {.name = "value"})
        });
    }
};

template<class T>
struct [[=MakeLayout{^^Layout<T>}]] Subject {};

In the same translation units, each specialized MakeLayout occurrence targets Subject<int> at the points above but defines separate Layout<int>. The first injects an int member and the second a char member. [basic.def.odr] requires injected definitions of the same entity to have the same characteristic sequence across translation units. These differ, making the program ill-formed, ordinarily with no diagnostic required. This existing obligation does not settle correspondence between synthesized invocations.

10.10.8. An imported completed pair preserves its result

This direct-injection case places an explicit instantiation definition in a module interface:

module;
#include <meta>
export module scheduled;

export template<class T> struct Layout;

struct MakeLayout
{
    std::meta::info destination;
    consteval int operator()(std::meta::annotation_context) const
    {
        std::meta::define_aggregate(destination, {
            std::meta::data_member_spec(^^int, {.name = "value"})
        });
        return 1;
    }
};

export template<class T>
struct [[=MakeLayout{^^Layout<T>}]] Subject {};

template struct Subject<int>;

The importer encounters that specialization during constant evaluation:

#include <meta>
import scheduled;

consteval {
    auto specialization = std::meta::substitute(^^Subject, {^^int});
    static_cast<void>(std::meta::size_of(specialization));
    auto layout = std::meta::substitute(^^Layout, {^^int});
    static_cast<void>(std::meta::size_of(layout));
    auto annotation = std::meta::annotations_of(specialization)[0];
    if (std::meta::extract<int>(
            std::meta::annotation_result_of(annotation, specialization)) != 1)
        throw 0;
}

In the interface, the explicit instantiation definition requires Subject<int>. Its specialized MakeLayout occurrence is paired with that specialization and runs after the instantiation declaration, defining Layout<int>. The importer then encounters an already processed specialization.

The proposed import policy preserves the pair’s completed state and retained integer where its association is observable. The importer retrieves 1 without another callback and can use the generated definition if reachable. Re-invoking with that definition reachable would attempt to complete an already complete Layout<int>, violating define_aggregate’s requirements. Completion elsewhere cannot make an unreachable declaration or definition reachable.

Requiring Subject<char> in the importer instead creates that specialization’s own instantiated occurrence and result, following the existing proposed specialization schedule. Completed Subject<int> state does not process it. Cases with an unresolved specialization trigger retain that gap.

The general correspondence problem remains when two module units independently require the same specialization before either completed state is reachable, then a downstream importer reaches both. Wording must decide which instantiated occurrences correspond and which associations are observable after combining those imports. Neither existing declaration reachability nor TU-local annotation equality supplies that decision. The single preserved-state policy above is proposed behavior, not evidence that the general module case is already solved.

10.10.9. Selected declaration-only uses still need a trigger rule

This base-protocol case separates selecting a declaration from requiring a function definition:

#include <meta>

struct Audit
{
    consteval void operator()(std::meta::annotation_context) const {}
};

template<class T>
[[=Audit{}]] int inspect(T) { return 0; }

using Result = decltype(inspect(0));

The potential pair is specialized Audit{} with inspect<int>. Overload resolution selects the declaration without needing its body. The open choice is whether that assigns a point after the alias-declaration or waits for a use requiring the definition. Excluding unselected candidates does not answer it. Explicit instantiation declarations and lazily instantiated member declarations also need classification. Optional frontend instantiation cannot serve as the trigger and required invocation failures remain hard errors.

10.10.10. Annotated lambdas still need a processing boundary

These base-protocol cases annotate lambda constructs, not lambda values used as annotations:

#include <meta>

struct Audit
{
    consteval void operator()(std::meta::annotation_context) const {}
};

auto plain = [] [[=Audit{}]] ([[=Audit{}]] int x) {
    [[=Audit{}]] int y = x;
    return y;
};

auto generic = []<class T> [[=Audit{}]] ([[=Audit{}]] T x) {
    [[=Audit{}]] T y = x;
    return y;
};

constexpr int first = plain(1);
constexpr int second = generic(2);
constexpr int third =
    [] [[=Audit{}]] ([[=Audit{}]] int x) { return x; }(3);

The front annotations apply to call operators. Parameter and local-declaration annotations form separate pairs. Non-generic operator and parameter pairs need a boundary after closure formation or the containing declaration. The immediately invoked case distinguishes checks before and after initializer evaluation. These no-op callbacks return void. A result query would still distinguish pending invocation from completed absence, so result semantics do not remove the need to choose that boundary.

The generic operator needs a specialization trigger and may be required by evaluation. Its schedule must order its pairs relative to callbacks on instantiated body declarations. A non-generic lambda in a templated entity also has the enclosing instantiation context. [expr.prim.lambda.closure] supplies the closure and operator, but the table gives their annotations no processing point. These choices remain open and none invokes callbacks once per runtime call.

11. Reporting violations

The outcome rules define invocation failures. Formation errors keep their ordinary treatment.

The preferred way to report a violation is to let std::meta::exception escape the evaluation. An exception caught within an otherwise valid constant evaluation is not a failure under [N5054]. The from argument supplies diagnostic provenance ([P3560R2]). The examples use std::meta::current_function() ([meta.reflection.scope]). A plain throw also fails the evaluation but lacks that structured context.

static_assert requires a constant expression where the assertion is written. A function parameter does not become one because its function is evaluated at compile time.

The examples pass ctx.annotation_location() as the exception’s where argument ([meta.reflection.exception]). It identifies the occurrence regardless of when invocation runs. A separately invoked validator can likewise pass a retained or reflected source location. Validation timing determines when a failure is detected without limiting its diagnostic location.

Diagnostic presentation remains a quality-of-implementation matter. A diagnostic should identify the annotation site, include the callback’s message when available, and note the annotated construct when useful.

error: serial::Field may annotate only non-static data members
  note: in annotation on member function 'Ledger::rebuild'

A callback has no standard warning or printing channel today. [P2758R5] proposes std::constexpr_warning_str, std::constexpr_error_str, and std::constexpr_print_str but has not been adopted. If adopted, these facilities would be callable from a callback like any other consteval code.

12. Modules preserve completed results subject to reachability

A function pointer supplied by annotation formation undergoes no second name lookup at invocation. A definition the evaluation needs must be available at the processing point. Import gives no visibility to declarations a module has not made reachable.

We propose that importing an already completed pair preserve its completed state and retained result when the annotation/target association is observable. Its originating completion precedes importer queries after the relevant declaration becomes reachable. Importing that pair creates no new invocation. This is new result-association wording: [module.reach] describes reachable declarations and their accumulated properties, not an existing callback-result association.

The compiler must serialize completed state and retained reflections as needed for modules and remap them consistently on import. The representation is an implementation choice. No runtime registry or linker protocol is added. Importing a template does not process every specialization. A specialization newly required by an importer needs its own processing under the specialization rules with its instantiation context ([module.context]). Correspondence between independently processed specializations remains unresolved. Neither association locality nor preserved state creates a program-global result for an entity.

12.1. Annotation reflections are TU-local

[dcl.attr.annotation] paragraph 3 makes each annotation or instantiation unique regardless of where it occurs. [CWG3118] found that exporting an annotation reflection across a module boundary and using it as a template argument would require infeasible mangling. An annotation in a header is also distinct in each translation unit that includes it. [basic.link] paragraph 16.4 therefore makes every annotation reflection TU-local.

Active annotation reflections follow the same rule. annotation_context is non-structural with consteval-only values (the interface). Reflections from annotations_of retain their normal TU-local and exposure rules.

The result association’s occurrence locality is distinct from payload locality. A returned ordinary integer does not become TU-local because an annotation computed it. A result containing an annotation reflection or other restricted material retains the applicable TU-local and exposure restrictions of [basic.link]. Retention supplies no exemption and no new lifetime extension. Ordinary admissible extracted values may reach runtime code through existing language mechanisms. Reflection-bearing values retain their consteval-only restrictions ([expr.const.const]).

TU-local identity does not settle correspondence between synthesized invocations across translation units. The occurrence-local policy is subject to existing ODR obligations. [basic.def.odr] requires injected definitions of the same entity to have the same characteristic sequence and imposes agreement on corresponding constant expressions in repeated definitions. The Observe case separates differing local results from a conflicting inline definition and identifies the synthesized-expression correspondence decision.

Injection accepts an annotation reflection through data_member_options::annotations ([meta.reflection.queries] paragraph 1, [meta.reflection.define.aggregate] paragraph 5.6). Only its constant_of(r) persists in that member description ([meta.reflection.define.aggregate] paragraph 4.6). The injected annotation is new, unique, and TU-local on the same terms as a source annotation. If active, its new pair computes its own result. Copying the underlying input value does not copy the earlier pair’s result. Active annotations would follow any revision of the TU-local rule.

13. Alternatives

13.1. Existing annotations supply the input model

The input model explains the choice to reuse existing annotations.

13.2. No runtime table is needed

Runtime tables raise ABI, linker, freestanding/hosted, and cross-translation-unit ordering questions. This facility introduces no automatic table or transport protocol. Results remain compile-time associations, with ordinary admissible extracted values usable in runtime code and reflection-bearing values subject to their existing restrictions (payload locality). Freestanding implementations need not provide <meta> ([compliance]) so these library additions raise no separate freestanding requirement.

13.3. Retained results trade additional state for scheduled derived data

The preferred design retains supported non-void results. The alternatives differ in when derived data is computed and what state the implementation must preserve.

A retained result lets a library publish a descriptor computed at the invocation’s defined point while preserving the input value. A manually arranged helper can compute the same descriptor. Automatic attachment or replacement belongs to a separate editing protocol and is not required for meaningful results.

13.4. An annotation the language reads is complementary

[P4167R0] has the language read an annotation to control argument-dependent lookup. For a type annotated with its proposed <meta> type (provisionally associated_entities_override), [basic.lookup.argdep] obtains associated entities only by iterating the annotation object. The language fixes that annotation’s meaning. An invocation instead observes a formed declaration and changes neither the annotated declaration nor the language’s name-lookup rules (the invocation contract). Permitted injection can still make declarations available to later lookup. The mechanisms are complementary. An annotation the language reads stays passive under this proposal unless it also opts in.

13.5. A consteval block has to be written wherever the rule applies

A consteval block ([P3289R1]) already runs arbitrary compile-time code in a class body, at namespace scope, or in a block. A codebase that owns its declarations can perform the same checks by applying annotations_of to the relevant members. This needs no new facility and is the strongest argument against this proposal.

Defining serial::Field does not arrange for a block to check every class that uses it. The declaration’s author must arrange the invocation, directly or through another facility, or risk leaving the annotation unchecked. The same applies to computing and storing a descriptor. An active annotation’s type opts in and supplies the callback. Applying it schedules invocation and supported result capture at a defined processing point with the occurrence’s context and access anchor.

14. Other languages run code at annotated declarations

These languages differ in when the code runs and what it can change.

14.1. Python decorators run at definition time

A Python decorator is a callable applied to a function or class at definition time ([PEP318], [PEP3129]). It receives the decorated object and may inspect, wrap, or replace it.

14.2. TypeScript decorators receive a context object

TC39 decorators are at stage 2.7 in the proposals index ([TC39-PROPOSALS]) and shipped in TypeScript 5.0 ([TS5]). They receive a context object describing the declaration, comparable to annotation_context. Their first argument is the decorated value, except for class fields, which receive undefined ([TC39-DECORATORS]). A decorator can return a replacement value or write into the runtime object through the context’s addInitializer ([TS-LIB]).

14.3. Rust procedural macros run on tokens

Rust procedural macros run at compile time on tokens: an #[attribute] macro returns a token stream that replaces the annotated item and a #[derive(Trait)] macro can only add items after it ([RUST-PROCMACRO]). They can generate arbitrary code but see the item before its type has a meaning to query.

14.4. Java processors run outside the annotation type

Java’s javax.annotation.processing framework lets processors inspect annotated declarations at compile time ([JAVAC]). The compiler loads the processors separately from the annotated code. The annotation type stays passive.

14.5. An active annotation checks at compile time and replaces nothing

Python and TypeScript decorators execute at run time. Rust procedural macros and Java annotation processors execute during compilation. An active annotation runs at compile time, carries its callback in its type, and uses typed reflection at a semantic processing point. It can inspect and reject its target, retain derived data, and reach generation through the indirect route or the separately requested direct permission. Its return is data rather than a replacement value or token stream. It cannot replace or complete the annotated declaration (the invocation contract).

16. Scheduling is the principal implementation risk

No active-annotation implementation is reported here. Existing facilities supply annotation formation ([dcl.attr.annotation]), annotation queries ([meta.reflection.annotation]), constant evaluation ([expr.const]), and result materialization ([meta.reflection.result]). An implementation must additionally test the opt-in, form the call with the specified access anchor, construct the context prvalue, assign the processing point, capture the result, and enforce evaluation and diagnostics. It must retain the pair’s association and completion, answer the new query, and preserve reachable completed state across modules.

Scheduling and publication interact with complete-class contexts, templates, declaration reachability, capture operations, and injection order. These interactions need a prototype. Constant materialization can execute user-defined operations whose dependencies must use the same invocation context and unpublished-pair rule.

Template specializations and injected annotations multiply invocations and result associations. Detecting a passive annotation reads only its value’s type, without deducing a return type by instantiating its body. Implementations may cache or reuse work if they preserve identity, evaluation context, publication order, diagnostics, and other observable effects. Equivalent captured constants can share existing materialization. This proposal has no compile-time performance or storage measurements.

The initial prototype tests cover static, non-static, and inherited call operators, explicit object member functions, captureless lambda annotation values, and function pointers. Each form needs tests with by-value, const reference, and rvalue reference parameters. Callees taking auto and conversion-only values, including explicit and non-const conversions, must stay passive. Negative tests cover each near miss, an opted-in call selecting a surrogate, and a null function pointer whose type declares the parameter (the opt-in rule).

The tests also cover multiple annotations on one target, one occurrence applying to multiple targets, nested classes, function definitions, explicit and implicit template instantiation, result admissibility, exception propagation, and full-expression cleanup before publication. Direct injection needs a separate prototype configuration. Both configurations retain results and must test injection through a specialization’s consteval block and annotations on the injected members (injection dependencies). The eventual feature-detection mechanism must distinguish the configurations. The base configuration must reject direct injection while allowing the indirect route.

The working issue table separates proposed behavior from remaining choices. A prototype must test pending encounters, post-class definition availability, nested failure boundaries, and module state. Ordering for combined type and object declarations, lambda placement, remaining specialization triggers and ordering, and cross-translation-unit correspondence also need semantic decisions.

17. Objections

Some objections remain partly unresolved (open questions).

17.1. "Without an implementation, nobody knows this is implementable"

Without a prototype, a direction poll can assess the model but cannot establish its implementation cost.

17.2. "The design admits a translation that does not terminate"

A chain of injections nests each invocation in the evaluation that injected its class. Exceeding an implementation’s evaluation limits is an error ([expr.const.core] paragraph 2.7). Infinite recursion through specializations has the undefined result specified by [temp.inst] paragraph 18. These are the existing termination limits of consteval blocks and templates.

17.3. "The template scheduling rule is the hardest part to specify"

Specialization invocation has no precedent in annotation wording. [meta.reflection.annotation] gathers annotations per specialization and runs nothing. Existing identity, point-of-instantiation, and nested-evaluation rules motivate the baseline but leave dependent specialization ordering and cross-translation-unit consistency unresolved. Both need decisions and prototype cases. A callback on a template definition could not test a specialization’s dependent type so the working scope retains per-specialization invocation.

17.4. "Granting the injection request turns an annotation into a supply-chain hazard"

An annotation opts in through its type without a marker at the annotation site. Writing [[=Foo{}]] authorizes its callback within the protocol’s limits. Poll 2 alone permits injection through a specialization’s consteval block, with scopes determined by the block’s position (the indirect route). Widening [expr.const.core] paragraph 2.32 would also permit direct injection at scopes determined by the annotation’s position. No spelling applies the metadata while declining its behavior.

Ordinary constant-evaluation rules prevent an invocation from reaching the file system, the network, or state the translation does not own. Injection scopes follow the block’s or annotation’s position, including when library code supplies the block. The generation facility’s requirements and the prohibition on defining the annotated target also apply (the invocation contract).

Header-supplied templates and their consteval blocks ([P3289R1]) already run in a consumer’s translation unit with its types. Given a reflection, they can inspect private members through access_context::unchecked() ([P2996R13]). An active annotation adds an automatic trigger where the consumer writes an annotation whose type opts in.

18. Related work stays outside this proposal

None of the following is a prerequisite for this proposal:

  • schema declarations or markers

  • named surface syntax for library-defined metadata

  • editing metadata before reading it. A library accessor can derive a field name, apply a prefix, fold markers into one value, or count members at read time. A retained callback result can supply derived data at the scheduled processing point. Neither changes the input annotations

  • changes to the annotated construct itself

  • declaration-side constraints on accepted annotation types

  • emission-record or runtime-transport reflection facilities

  • relaxation of the structural-type restriction

Facilities such as [P3294R2]’s token sequences could add operations under their own rules. Annotating newly generated members does not edit an existing declaration’s annotations.

19. The working scope leaves scheduling semantics unresolved

The working scope retains the declared-context opt-in, ordinary direct calls, meaningful by-value results, and a separate decision on direct injection. Conversion-only values remain passive. Mutation, registration, and specially named customization functions remain outside this revision.

20. The polls ask about the opt-in, the protocol, results, and injection

Poll 1 is a preference. Poll 2 reads as the declared-parameter opt-in unless poll 1 carries. Poll 3 assumes poll 2 and requests retained non-void results. Poll 4 assumes poll 2 and requests direct injection. Poll 3 does not depend on poll 4. Declining direct injection leaves retained results and the indirect route available.

The preferred design combines the invocation protocol with the result policy in poll 3. The separate polls collect direction. They do not permit implementations advertising the same facility to choose different return meanings. A different committee direction would require a revised specification and feature-detection contract.

  1. EWG prefers that an annotation opt in by the validity of a direct call alone over requiring a callee that declares a std::meta::annotation_context parameter (the opt-in rule).

  2. EWG encourages further work on an annotation invocation protocol in which an annotation that opts in, through a callee that declares a std::meta::annotation_context parameter or through the validity of a direct call if poll 1 carries, is invoked for each construct it applies to, a declaration or a base-specifier, with a std::meta::annotation_context describing that construct, in a mandatory constant evaluation whose failure is an error (semantics).

  3. EWG encourages further work on retaining supported by-value non-void callback results as immutable, reflectable data for each occurrence/target pair, with required capture and a query available after successful full-expression completion, as specified in this paper (result semantics, the query).

  4. EWG encourages further work on admitting the invocation of an active annotation under [expr.const.core] paragraph 2.32 so that it may produce an injected declaration where a consteval block at the annotation’s position could (the invocation contract).

SG7 may take the polls first. The library surface (annotation_context and annotation_result_of) goes to LEWG with the direction on the protocol and retained results.

21. Conclusion

Applying an active annotation schedules its library-defined callback and captures a supported non-void result for later retrieval. The declaration’s author need not arrange the invocation or descriptor computation separately. Void callbacks produce no result. The required full-expression includes capture and cleanup, so failed materialization is an error even when nobody queries the result.

Under the consumer guarantees, serial::Field rejects invalid targets and schema::Field retains a descriptor without changing its input (validation, derived data). A class callback can collect completed member results under the existing proposed order. The result is data, including a returned reflection, and creates no implicit mutation or injection request.

Every C++26 annotation keeps its behavior (compatibility). Retention adds association state, publication rules, a query, and module-preservation work. Core and library review and a prototype remain necessary, including decisions on the identified scheduling and correspondence questions. The polls request direction on meaningful retained results independently of direct-injection permission.
