2. Introduction

This paper proposes function parameter packs with a single element type. If the committee permits us to reclaim the comma-less syntax, we could use the following form:

template <class T> // T is not a parameter pack...
void foo(T... vs); // ...but vs is a parameter pack.

C++ already permits a homogeneous template parameter pack:

// Legal since C++11: T is not a parameter pack, but vs is.
template <class T, T... vs>
void foo();

The first pack would contain ordinary function parameters initialized at the call. The second contains constant template arguments. [CXX-VARIADIC] A homogeneous function parameter pack deduces its length at compile time while accepting values computed at runtime.

This revision proposes a single homogeneous pack at the end of a function’s parameter list. The pack could be named or unnamed. The function would implicitly be a template and its specializations would be distinguished in part by the pack length. The named spelling is unambiguous. The unnamed spelling int... requires committee approval of the comma-less C-varargs change in § 7.6 The Oxford variadic comma. The examples and wording below use this syntax subject to that approval.

  1. A declarator ellipsis introduces a new homogeneous pack only when its parameter pattern has no remaining unexpanded pack after ordinary placeholder processing.

  2. Existing indexed selection and nested expansions retain their meanings, including in lambdas.

  3. Calls, target function types, and declarations identifying particular specializations deduce the implicit length. Ordinary redeclarations preserve the same homogeneous declaration.

4. Definitions

A homogeneous parameter pack (or homogeneous pack) contains values of one type and its declaration introduces an independent count. A heterogeneous parameter pack (or heterogeneous pack) permits values of different types.

These terms apply to both function parameter packs and template parameter packs.

A homogeneous function parameter pack’s parameter pattern contains no unexpanded pack after placeholder processing. An ordinary expansion remains an ordinary expansion even when every resulting parameter type is the same.

The work-arounds suffer from a lack of clarity in the interface.

  • The recursion approach advertises a function that can take variadic arguments of any type, but any attempt to call the function with a non-T will either cause the program to fail to compile, or lead to potentially unwanted implicit conversions.
  • The std::initializer_list approach correctly advertises the accepted type, but is inflexible with respect to mutability and requires the user to enclose its arguments in braces. In the min example above, the precondition could be removed if an explicit argument preceded the std::initializer_list, but the syntactic separation remains, resulting in calls such as min(a, { b, c, d }).
  • The SFINAE approach achieves the goal of constraining all arguments to be of the same type, but at the expense of readability, and the application of the is_same_v trait can disable desired conversions when constraining to a non-dependent parameter type.
  • The Concepts approach is more readable than the SFINAE approach, but is otherwise interchangeable.

Explicitly specifying T also permits ordinary argument conversions in the proposed form. The SFINAE and Concepts forms still deduce each Args and reject a different type. For example, their min<int>(1, 2.5) calls fail the equal-type requirement. [CXX-DEDUCTION-CALL] [CXX-EXPLICIT-ARGS]

If the committee permits us to reclaim the comma-less syntax, we could use this form for a fixed element type without an explicit template head. Each argument would initialize an int parameter:

int sum(int... values) {
    return (0 + ... + values);
}

int use_sum(int runtime_value) {
    return sum(runtime_value, 2.5);
}

Unnamed packs require committee approval to reclaim the comma-less syntax. [dcl.init.aggr] [temp.deduct.call]

Homogeneous function parameter packs are not intended as a replacement for std::initializer_list. A std::initializer_list provides access to an array of const elements and is passed as a single argument. A function parameter pack accepts separate arguments. [CXX-INITIALIZER-LIST] [CXX-VARIADIC] List-initialization gives initializer-list constructors priority under [over.match.list], which can prevent selection of a constructor taking a parameter pack. public:
    MyContainer(std::initializer_list<T> elems);

7. Design Decisions

7.1. Pack declarations

A homogeneous function parameter pack is declared in exactly the same way as any other function parameter pack. The difference is that its parameter pattern contains no unexpanded pack after placeholder processing:

// heterogeneous function parameter pack
template <class... T> void f(T... v);

// homogeneous function parameter pack
template <class T>    void f(T... v);

In fact, the pattern does not have to mention any template parameters at all:

// homogeneous function parameter pack
void f(int... v);

Any function declaration that includes a homogeneous function parameter pack implicitly declares a function template.

Confirm and address the objection to implicit templates, then decide whether an explicit template introducer is needed.

The size of a homogeneous function parameter pack is deduced from function arguments at the call site. This requires the pack to be placed in a deduced context, which means that a function template can have at most one homogeneous function parameter pack, and the pack must appear at the end of the function parameter list. Once its parameters have been formed, a homogeneous function parameter pack behaves no differently from any other function parameter pack.

7.1.1. Abbreviated syntax

Since C++20, a function template that needs no template parameter names can use abbreviated syntax, with placeholders such as auto in its parameter list. [P1141R2] [CXX-FUNCTIONS]

Under this proposal, the presence of a homogeneous parameter pack in a function signature also indicates that a function declaration is an abbreviated function template declaration:

void foo(int... v); \

If the parameter pack is the only part of the function declaration requiring it to be a template and the pattern of the parameter pack does not contain any dependent names, then the template has no formal template parameters and the template-head must be omitted. To avoid confusion with explicit specializations, this proposal does not allow an empty template-head on a template declaration, even though the syntax is unambiguous in the presence of a function parameter pack declaration:

template <class T> void foo(T... v);     // #1 OK
void foo(int... v);                      // #2 OK, declares a template with an empty template parameter list
template <> void foo(float... v);        // Error: function parameter pack in explicit specialization
template <> void foo(int a);             // OK, declares an explicit specialization of #2
template <> void foo<>(int a, int b);    // OK, declares an explicit specialization of #2
template <> void foo<int>(int a, int b); // OK, declares an explicit specialization of #1
template <> void foo(float a);           // OK, declares an explicit specialization of #1

If the committee approves reclamation, the proposed rules would make both declarations below templates:

void a(auto...) {}
void b(int...) {}

The first already declares an abbreviated function template in C++26. Ordinary placeholder processing invents a type parameter pack, allowing different deduced argument types. The second declares one int parameter followed by C varargs in C++26, using a deprecated comma-less spelling. With that approval, the second would declare a homogeneous pack with a fixed element type and an independently deduced count. [CXX-FUNCTIONS] [CXX-VARARGS-DEPRECATION]

The function template, its ordinary template arguments, and the pack length determine the specialization. Converting arguments to a fixed element type does not add their original types to the specialization’s identity. These proposed uses therefore select the same two-parameter specialization:

void use_b() {
    b(1, 2);
    b(1.0, 2.0);
    void (*callback)(int, int) = b;
    callback(3, 4);
}

The programmer cannot name or explicitly supply the implicit count as a constant template parameter. The count does not make every expression in the function body dependent.

7.2. Lambdas

auto a = [](int... v) { return (1 * ... * v); };

A homogeneous function parameter pack makes a lambda generic.

An ordinary expansion of an enclosing pack does not by itself make a lambda generic. This distinction also applies when the element type uses pack indexing. [CXX-LAMBDA]

7.3. Pack indexing

The expansion pattern of pack indexing is the pack name alone. In Ts...[Is], the indexed occurrence of Ts belongs to that expansion while Is remains available to an enclosing expansion. These C++26 rules apply to the proposed declarations as well. [CXX-VARIADIC] [CXX-PACK-INDEX]

The following is valid C++26. Each lambda has one unnamed parameter:

template<class... Ts, std::size_t... Is>
void indexed(std::index_sequence<Is...>) {
    (..., [](Ts...[Is]) {});
}

int main() {
    indexed<int, double, char>(std::index_sequence<2, 0, 2, 1>{});
}

The four indices select char, int, char, and double from the three types. Each indexed type is replaced in full by the selected type, with no ellipsis or bracket suffix left over.

Each row below is independent and assumes an appropriate enclosing declaration of Ts and Is, with valid selected indices. The proposed column assumes committee approval of the comma-less varargs change in § 7.6 The Oxford variadic comma.

7.3.1. Pairwise and Cartesian expansion

Pairwise expansion places both packs in one expansion pattern. The following current-language fragment pairs each type with one index constant and requires equal pack lengths:

(..., [](Ts, std::integral_constant<std::size_t, Is>) {});

This does not index Ts. By contrast, a Cartesian product requires separate nested expansions. This current-language fragment fixes one type before expanding all index constants:

template<class... Ts, std::size_t... Is>
void cartesian(std::index_sequence<Is...> indices) {
    (..., []<class T>(std::index_sequence<Is...>) {
        (..., [](T, std::integral_constant<std::size_t, Is>) {});
    }.template operator()<Ts>(indices));
}

With three types and four index entries, the nested expansions form twelve pairings. Equal-length packs or repeated identical types can conceal the distinction between selection and pairing. The existing equal-length requirement and innermost-expansion rule account for each operation without changing the meaning of indexing. [CXX-VARIADIC]

7.3.2. Homogeneous packs of indexed types

A second declarator ellipsis can introduce the proposed homogeneous pack when the index is a scalar. The indexed type is selected before the new pack’s independent count is deduced:

template<class... Ts>
auto selected_counter() {
    return [](Ts...[1]... values) {
        return sizeof...(values);
    };
}

For selected_counter<int, double, char>(), the proposed lambda accepts a deduced number of ordinary double parameters. That count is unrelated to the length of Ts.

To create homogeneous lambdas selected by different indices, pass each index to a helper as a scalar. The following example uses the proposed syntax:

template<class... Ts>
struct selectors {
    template<std::size_t I>
    static auto make() {
        return [](Ts...[I]... values) {
            return sizeof...(values);
        };
    }
};

template<class... Ts, std::size_t... Is>
auto make_selected(std::index_sequence<Is...>) {
    return std::tuple{selectors<Ts...>::template make<Is>()...};
}

Each resulting call operator has its own homogeneous count. The expansion of Is in make_selected supplies a scalar index to each specialization of make.

7.3.3. Array parameters

In C++26, the named declaration int... values[Is] expands Is into array bounds. The resulting array parameters undergo ordinary pointer adjustment. Positive extents 1, 2, and 3 therefore produce a function pointer taking three int* parameters. Zero extents are independently invalid. [CXX-FUNCTIONS] [CXX-ARRAYS]

The C++26 [dcl.name] grammar has no array-suffix production for an abstract pack declarator. P2662R3 removed that production when introducing pack indexing. The named array declaration remains valid. [CXX-DECLARATORS] [P2662R3]

An enclosing fold around the named array-pack declaration has no unexpanded Is left. The inner parameter declaration already expands it.

The proposal retains the C++26 abstract-declarator grammar. If the committee approves reclamation, an array alias could supply an unnamed homogeneous parameter type with ordinary adjustment. Its array extent remains separate from the homogeneous count.

7.3.4. Empty packs and return types

An empty outer expansion over Is need not instantiate an indexed selection. A fixed index still needs to designate an element when its type is required. In the proposed homogeneous form, calling a lambda with zero arguments does not repair an invalid fixed selection in its declaration. [CXX-VARIADIC] [CXX-PACK-INDEX]

The body { Ts...[Is]{}; } discards the constructed value and returns void. For the scalar types above, { return Ts...[Is]{}; } deduces the selected scalar type under the C++26 return-deduction rules. [CXX-LAMBDA] [CXX-AUTO]

7.4. Captures

Constant template parameters can supply values inside a lambda without capturing automatic function parameter objects. This current-language program prints abc without a newline:

template<char... C, std::size_t... I>
void print_constants(std::index_sequence<I...>) {
    (..., [] { std::putchar(C...[I]); }());
}

int main() {
    print_constants<'a', 'b', 'c'>(std::make_index_sequence<3>());
}

The fold expands I and value pack indexing selects from C. Repeated indices 2, 0, 2, and 1 produce cacb. The proposed homogeneous declaration rule does not apply to this program and leaves its meaning unchanged. [CXX-VALUE-PACK-INDEX] [CXX-VARIADIC]

In the proposed counterpart, characters names function parameter objects:

void print_characters(char... characters) {
    (..., [&] { std::putchar(characters); }());
}

These function parameter objects require capture. Value capture follows the ordinary copying rules. [CXX-CAPTURES]

The lambda can be omitted:

(..., std::putchar(characters));

Nested lambdas retain ordinary capture propagation. Reference capture does not extend a parameter’s lifetime. [CXX-CAPTURES]

7.5. Alternatives

7.5.1. Empty template heads

An alternative is to allow empty template parameter lists in template declarations:

template <> void foo(float... v); // OK, declares a template with a homogeneous parameter pack

Although this alternative does not introduce a true syntactic ambiguity with explicit specializations, the forms are similar enough that there is significant potential for programmer confusion. In an e-mail conversation with Richard Smith following the San Diego meeting in 2018, he indicated that he would be against the adoption of homogeneous function parameter packs under this model. EWGI had the same opinion in Kona in 2019: [P1219R2]

EWGI Poll: This should be valid and declare a template: template <> void foo(int... v);

SF F N A SA
0 4 7 2 3

Homogeneous function parameter packs introduce a form of function template that has no formal template parameters. Without this option, these templates cannot be declared with the template keyword; the abbreviated syntax must be used instead. For consistency with other declarations, the idea of permitting the template keyword here is appealing; along with the next option, this could actually improve the overall consistency of the syntax surrounding template (and non-template) declarations.

7.5.2. Alternative specialization syntax

Explicit specialization declarations are inconsistent with the rest of the language. These declarations are prefixed with template <>, giving the appearance of a template declaration. The function, class, and variable template specializations considered in this alternative are ordinary non-template entities that provide the definition for a particular specialization of a template, and the template specialization must be named in (or deducible from) the declaration. Explicit specialization declarations can name the specialization with a template-id. This makes the template <> introducer both misleading and redundant for the declarations considered here. [CXX-SPECIALIZATION]

The template <> introducer can be dropped without any reduction in expressivity:

template <class T> class C; // class template
template <> class C<int>;   // ok, explicit specialization (proposed: not deprecated)
class C<int>;               // proposed: explicit specialization

template <int V> constexpr int v = V; // variable template
template <> constexpr int v<1> = 0;   // ok, explicit specialization (proposed: deprecated)
constexpr int v<1> = 0;               // proposed: explicit specialization

template <class T, class U> void f(T t, U u);     // function template
template <> void f<int, double>(int i, double d); // ok: explicit specialization (proposed: deprecated)
template <> void f<>(int i, double d);            // ok: explicit specialization (proposed: deprecated)
template <> void f(int i, double d);              // ok: explicit specialization (proposed: deprecated)
void f<int, double>(int i, double d);             // proposed: explicit specialization
void f<>(int i, double d);                        // proposed: explicit specialization
void f(int i, double d);                          // ok: ordinary function declaration (proposed: no change)

The declarations illustrate alternative spellings independently. In particular, the two definitions of v<1> are not to be used together.

R2 assessed this alternative as follows in 2019: [P1219R2]

Under this approach, the misleading part of the syntax is removed, and the result is a more consistent language. Non-template entities no longer look like templates. For explicit specializations of function and variable templates, the old syntax can be deprecated. (The old syntax for explicit specializations of class templates probably cannot be deprecated at this time, as their use is very common.) Anecdotally, explicit specializations of function templates are rare and their use is generally discouraged due to subtleties around overloading.

EWGI in Kona in 2019 opted not to poll this option, but the general sentiment of the room was that a separate paper exploring this idea would be welcome. This revision retains the existing explicit-specialization syntax. [P1219R2]

7.5.3. Explicit template markers

An alternative is to require a sigil in the template parameter list to indicate that a homogeneous pack will be present in the function declaration:

template <...> void foo(int... v);
template <class T, ...> void bar(T... v);

R2 reported the following implementation experience and discussions after the San Diego meeting in 2018: [P1219R2]

This idea, including the use of the ellipsis as the sigil, was suggested by Richard Smith in an impromptu conversation during the San Diego meeting. He and David Vandevoorde both indicated that this requirement would make the feature simpler to implement across a broad range of compilers. This notion is not directly supported by the experience of implementing the feature in Clang, but there is as yet no implementation experience with any other compiler. In Clang, the presence of an unparenthesized ellipsis in a declarator causes the compiler to treat the declaration as having a particular dependent type corresponding to a parameter pack, and the presence of a parameter of that type is enough to differentiate a function declaration as a template declaration instead of an explicit specialization or ordinary function declaration.

P1141R2, adopted in San Diego, adds support for function template declarations that lack a template head entirely; in this case, the presence of the auto keyword in the function parameter list indicates that the function declaration declares a function template. Any implementation that can handle these new declarations should also be able to handle homogeneous packs without added syntax. In a follow-up conversation with Richard over e-mail, he agreed with this conclusion. [P1141R2]

The corresponding lambda form would be []<...>(int... values) {}. A marker could declare the independent count and opt into revised unnamed-ellipsis parsing. Those are separate effects. Making a lambda generic alone does not change indexing or move Is between expansions.

If retained, specify the marker’s grammar, count deduction, and ellipsis disambiguation. Neither []<...>(...){} nor template<void> is an existing marker for this feature and the former does not declare a typed homogeneous parameter.

7.5.4. Bare template introducer

An alternative is to allow the angle brackets to be omitted when no template parameters are needed:

template void foo(int... v);

This removes the apparent conflict with explicit specialization syntax, but introduces the same apparent conflict with the syntax for explicit instantiations. In both cases, there is no actual conflict for this homogeneous declaration; the compiler can tell that the function is a template by the presence of the homogeneous parameter pack. This approach was considered and rejected because it introduces an irregularity into the grammar. Currently, all templates introduced with the template keyword must include a parameter list enclosed in angle brackets; removing them would be akin to removing the parentheses on a parameterless function declaration. The declaration form that uses the template keyword without angle brackets as an introducer is the explicit instantiation declaration, and those do not declare templates. [CXX-INSTANTIATION]

7.5.5. Explicit lengths

An alternative is to allow or require a template parameter for the size of the pack. The spelling considered in R2 predates pack indexing:

template <std::size_t Len> void foo(int...[Len] v);

A formal length parameter would allow callers to specify the pack length and make its role in specialization explicit. The proposed implicit count can only be deduced.

The drawback to this approach is a matter of regularity. While the language allows the user to query the size of a pack using the sizeof... operator, it does not currently allow the size to be explicitly specified. If this facility were added, it could reasonably be applied to homogeneous template parameter packs as well as homogeneous function parameter packs. It would make little sense to try to apply this to heterogeneous packs, since the size must match the number of arguments passed to the template parameter pack. Since this facility would necessarily be optional for homogeneous template parameter packs, consistency demands that it should also be optional for homogeneous function parameter packs.

A type-pack variant conflicts with indexed type selection. An explicit marker does not resolve that conflict by itself.

Calls and target function types determine the count. Constraints on sizeof... can restrict it. Explicit lengths, multiple homogeneous packs, and non-trailing homogeneous packs are deferred. Restoring removed abstract array-pack grammar would be a separate change.

7.5.6. Trivial templates

An alternative is to allow empty angle brackets even when there is no homogeneous parameter pack:

template <> void foo(int n);

Under the first alternative to the proposed rules, the template-parameter-list is optional in a template-head in order to permit homogeneous packs with non-dependent types. The alternative rules also add semantic constraints requiring at least one template parameter whenever there is no homogeneous pack. The semantic constraints could be relaxed, allowing trivial templates that only permit vacuous specialization. This would not be very useful; these trivial templates would behave like normal non-template entities in almost every way imaginable, aside from syntactic minutiae (for instance, a trivial function template could be defined in a header file without using the inline keyword).

This alternative also gives rise to a genuine ambiguity with explicit specializations:

template <> void f(int v);     // #1: trivial function template
template <> void f(int... vs); // #2: function template with homogeneous pack
template <> void f(int v);     // #3: redeclaration of #1 or explicit specialization of #2?

Apart from minor simplifications in the language specification, about the only "benefit" of this approach would be to make the token sequence []<>(){} well-formed for the amusement of language nerds.

7.6. The Oxford variadic comma

Kona EWGI poll, March 2019. [P1219R2]
Poll SF F N A SA
Make vararg declaration comma mandatory. 10 6 1 0 0

A varargs ellipsis is a C-style ellipsis rather than a parameter-pack ellipsis. C requires an intervening comma when a parameter list precedes it. C23 also permits an ellipsis alone: [N3096]

parameter-type-list:
    parameter-list
    parameter-list , ...
    ...

C++26 also permits a standalone varargs ellipsis. Unlike C, it additionally permits a varargs ellipsis after a parameter list without an intervening comma. The comma-less alternative is deprecated in C++26: [CXX-FUNCTIONS] [CXX-VARARGS-DEPRECATION]

parameter-declaration-clause:
    ...
    parameter-declaration-listopt
    parameter-declaration-list , ...
    parameter-declaration-list ...

The varargs ellipsis was originally introduced in C++ along with function prototypes. At that time, the feature did not permit a comma prior to the ellipsis. When C later adopted these features, the syntax was altered to require the intervening comma, emphasizing the distinction between the last formal parameter and the varargs parameters. To retain compatibility with C, the C++ syntax was modified to permit the user to add the intervening comma. Users therefore can choose to provide the comma or leave it out. [P1219R2]

When paired with function parameter packs, this creates a syntactic ambiguity that is currently resolved via a disambiguation rule: When an ellipsis that appears at the end of a function parameter list might be part of an abstract (nameless) declarator, it is treated as a pack declaration if the parameter’s type names an unexpanded template parameter pack or contains auto; otherwise, it is a varargs ellipsis. [CXX-FUNCTIONS]

For example, these declarations have different meanings in C++26:

template <class... T>
void f(T...); // declares a variadic function template with a function parameter pack

template <class T>
void f(T...); // same as void f(T, ...)

If the committee approves reclamation, the second declaration would instead declare a homogeneous function parameter pack. Requiring a comma between a parameter list and a varargs ellipsis would remove the need for the disambiguation rule while preserving C-compatible declarations.

Reusing the spelling would be a breaking change. An unnamed homogeneous pack would use the same spelling as an existing comma-less varargs declaration. The current declaration void send(int...) takes one int followed by C varargs. Its proposed homogeneous meaning would change accepted calls, initialization, function types, address-taking, and template linkage consequences. The explicit comma spelling void send(int, ...) retains its meaning. [CXX-FUNCTIONS]

R2 made the following migration argument in 2019: [P1219R2]

This is a breaking change, but likely not a very impactful one. In the parlance of P0684R2, this would be a "Very Good Change": Compilers can issue warnings in C++20 mode (or earlier) whenever the disambiguation rule is resolved in favor of a varargs ellipsis, and the warning can be resolved without any change in meaning by the addition of a single character. Moreover, the number of instances should be vanishingly small. In modern C++ code, the varargs ellipsis has largely been superseded by function parameter packs. Today, apart from SFINAE uses where the disambiguation rule doesn’t apply, the varargs ellipsis can mainly be found in header files that are intended to be consumed by both C and C++ code, in order to facilitate interoperability between the two languages. In these cases, the declarations must conform to the rules imposed by C syntax, and so they will already conform to the rules proposed here. Lastly, personal experience suggests that the vast majority of C++ users aren’t even aware that the comma preceding a varargs ellipsis is optional. [P0684R2]

Jan Schultke’s P3176R1, The Oxford variadic comma, continued the comma-separation work from P1219R2. It deprecated the comma-less spelling while retaining its meaning and standalone ellipsis parameters. If the committee approves reclamation, this proposal would use the comma-less spelling for homogeneous packs while preserving optional parameter names. Deprecation alone does not change its meaning. Reuse is a source and link compatibility change under SD-10. [P3176R1] [P1219R2] [CXX-VARARGS-DEPRECATION] [SD10]

P3776R1, More trailing commas, proposes trailing commas in function parameter lists but excludes them after C ellipsis parameters. This preserves a grammar distinction between function parameter packs and C ellipsis parameters. [P3776R1]

Agree with Jan on language modes, migration, and trailing-comma wording. Decide whether to remove the old meaning before or alongside homogeneous packs, or use different syntax. Check shared C/C++ headers, macros, and address-taking code. If reclamation is declined, specify a consistent explicit alternative. P3776R1

If the committee approves reclamation, the named comma-less form void send(int value...) would require migration to void send(int value, ...). The name cannot be moved across the ellipsis as an implicit reinterpretation. Preserving every existing declaration is therefore incompatible with reclamation.

7.6.1. The impact of a breaking change

The following survey and its descriptions of the dataset and Boost are retained from P1219R2, published in 2019. They describe that historical dataset, not the state of current code. [P1219R2]

The ACTCD19 dataset at codesearch.isocpp.org (2019 archive) contains a vast amount of source code collected from various open-source projects. According to the codesearch FAQ, the dataset comprises 876,800,403 lines of source code across 2,489,599 files. This dataset was used to estimate the impact of requiring a comma before a varargs ellipsis. [CODESEARCH-FAQ]

Identifying uses of varargs ellipses is decidedly non-trivial. Since this is an area of syntactic ambiguity, only a C++ parser with sufficient knowledge of the language can identify all occurrences and distinguish them from parameter pack declarations. Such a parser would also require special build scripts for each of the projects represented in the dataset. In the absence of those resources, a mix of regular expression searches and human review was used instead.

Only header files (those with extensions of .h, .hh, .hpp, or .hxx) were considered. In order to discard comments and macro definitions, each source file was stripped of preprocessor directives and then run through the C++ preprocessor, reducing the search space to syntactically significant text. (This process still left behind a significant number of macro invocations, because the macro definitions were no longer visible after stripping preprocessor directives. Inactive code blocks, such as those guarded by #if 0, were also retained.) The collective output was then scanned for lines containing ellipses, resulting in 258,196 lines of interesting text, which were then tagged according to the file each line originated in.

A variety of patterns were identified based on common identifiers, operators, and other textual hints that typically declare variadic packs or expand them; these were excluded from further analysis.

From these results, 89,614 lines contain a comma immediately preceding an ellipsis; those lines unambiguously declare varargs functions.

8,101 lines begin with an ellipsis, and further analysis showed that 6,241 of those lines appeared to come from function declarations. Of those, 6,092 are immediately preceded by a comma on a prior line; from the remaining 149 lines, 131 are catch clauses or function declarations containing only an ellipsis. The last 18 lines have macros mixed in with the parameter list for static analysis purposes. Every single one of these ellipses is unambiguous with respect to pack declarations.

From the entire result set, 6,318 lines were positively identified as containing a varargs ellipsis without a preceding comma.

Of the 6,318 confirmed varargs declarations without a preceding comma, 6,182 come from a single source: the boost library. Boost is a very popular general-purpose library in the C++ ecosystem, and several of the open-source projects in the dataset contain their own independent copies. In total, the dataset contains seventeen separate complete or partial copies of various versions of boost. After deduplication, the 6,182 results found in boost are reduced to 879.

The 879 unique hits in boost tend to follow a generic pattern; nearly half (416 hits) come from type_traits/detail/is_mem_fun_ptr_tester.hpp. This one file defines a family of function templates (all named is_mem_fun_pointer_tester), each taking a function pointer of progressively higher arity, from 0 to 24, in every possible combination of qualifiers and calling convention, all both with and without a varargs ellipsis. The intent is to allow generic code to detect at compile time whether or not a given type is a member function pointer type. In modern C++, using variadic templates with class template partial specialization, this 2,759 line file can be reduced to just a small handful of lines. Most of the other hits in boost follow a similar pattern, and are intended to facilitate generic programming in pre-C++11 modes.

Update the code-search survey and Boost analysis using recent data, documenting the dataset and methodology.

8.8. Declarations

Specify correspondence and equivalence in [basic.scope.scope] and [temp.over.link], requiring matching homogeneous packs regardless of parameter names. Check specialization, instantiation, module ownership, reachability, serialization, and cross-translation-unit identity separately from ABI representation. Unseen specializations require reachable definitions or appropriate explicit instantiations. [module.reach]

Check std::meta::template_of and std::meta::template_arguments_of for specializations whose implicit count is not a template argument. Check std::meta::parameters_of for the resulting parameters, including a zero count. [meta.reflection.queries]

8.9. Feature-test macro

Agree with SG10 whether to update __cpp_variadic_templates or add a macro. Choose a new revision value after settling feature scope and compatibility.
