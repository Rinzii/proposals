2. Introduction

This paper proposes function parameter packs whose parameters share one declared element type and use ordinary parameter initialization:

template <class T> // T is not a parameter pack.
void foo(T... vs); // vs is a parameter pack.

C++ already permits a homogeneous template parameter pack:

// Legal since C++11: T is not a parameter pack, but vs is.
template <class T, T... vs>
void foo();

The first pack would contain ordinary function parameters initialized at the call, with a length deduced at compile time and values that may be computed at runtime. The second contains constant template arguments. [CXX-VARIADIC]

This revision proposes a single homogeneous pack at the end of a function’s parameter list. Its declaration makes the function an abbreviated function template, with no explicit template head needed when there are no template parameters to declare. Each specialization has an ordinary function type with a fixed number of parameters and is distinguished in part by the pack length. Existing packs, pack indexing, and nested expansions retain their meanings, including in lambdas.

The named spelling int... values is unambiguous. Supporting unnamed packs as well requires the separate compatibility decision in § 6 Reclaiming the deprecated comma-less spelling, because int... retains its deprecated C-varargs meaning in C++26. [CXX-VARARGS-DEPRECATION]

3. Examples

The current and proposed definitions are independent alternatives.

3.1. Pass existing points and braced initializers

Consider a Point with integer coordinates:

struct Point {
    int x;
    int y;
};

append_points adds points to a path. A constrained pack already accepts separate Point arguments. The proposed declaration gives each parameter a fixed type so callers can also pass braced initializers without repeating Point:

The same append operation with deduced or fixed Point parameter types.
Current C++ With homogeneous packs 
void append_points(
    std::vector<Point>& path,
    std::same_as<Point> auto... points) {
    (path.push_back(points), ...);
}

void append_points(
    std::vector<Point>& path,
    Point... points) {
    (path.push_back(points), ...);
}

For a std::vector<Point> path and named Point objects origin, corner, and finish:

Calls to the two append_points definitions.
Call Current C++ With homogeneous packs
append_points(path) Appends no points Appends no points
append_points(path, origin) Appends one point Appends one point
append_points(path, origin, corner, finish) Appends three points Appends three points
append_points(path, origin, {2, 3}, {4, 5}) Error: cannot deduce types for the braced arguments Appends three points
append_points(path, origin, Point{2, 3}, Point{4, 5}) Appends three points Appends three points

A std::convertible_to<Point> constraint cannot resolve this deduction failure, because it needs argument types before checking conversions. A fixed Point parameter supplies the destination type for ordinary parameter initialization of each pack element. [CXX-DEDUCTION-CALL]

An initializer-list interface also accepts these braced elements in current C++:

void append_points(
    std::vector<Point>& path,
    std::initializer_list<Point> points) {
    path.insert(
        path.end(), points.begin(), points.end());
}

void build_path() {
    std::vector<Point> path;
    Point origin{0, 0};

    append_points(path, {origin, {2, 3}, {4, 5}});
    append_points(path, {});
}

That interface groups the points into one list argument. The proposed pack combines separate arguments with a fixed destination type for each. Both the list and proposed pack reject {2.5, 3} because it would narrow Point::x.

3.2. Keep the count in the result type

point_block returns an array with one element per point, even when the coordinates are computed at runtime. A typed array reference already accepts braced elements and deduces their count in current C++. The proposed pack accepts the points as separate arguments:

Returning an array whose extent is the number of points.
Current C++ With homogeneous packs 
template <std::size_t N>
auto point_block(const Point (&points)[N]) {
    return std::to_array(points);
}

void record_points(Point origin) {
    auto block =
        point_block({origin, {2, 3}, {4, 5}});
    static_assert(
        std::tuple_size_v<decltype(block)> == 3);
}

auto point_block(Point... points) {
    return std::array<
        Point, sizeof...(points)>{points...};
}

void record_points(Point origin) {
    auto block =
        point_block(origin, {2, 3}, {4, 5});
    static_assert(
        std::tuple_size_v<decltype(block)> == 3);

    auto empty = point_block();
    static_assert(
        std::tuple_size_v<decltype(empty)> == 0);
}

Both three-point calls return std::array<Point, 3>. The number of points determines the extent independently of their coordinate values. Both interfaces reject a braced {2.5, 3} element as narrowing. The typed array-reference declaration cannot deduce N from point_block({}), though a zero-argument overload can supply the empty case. Built-in arrays allow neither zero bounds nor reference elements. An rvalue array-reference interface can transfer move-only elements. [CXX-DEDUCTION-CALL] [CXX-ARRAYS] [CXX-LIST-INIT]

A constrained pack also provides sizeof... but retains the braced-argument deduction limit shown above. A typed array reference provides braces and count through one grouped argument. The homogeneous pack combines separate fixed-type parameters, braced initialization, and a count in one declaration that also accepts an empty call. Direct std::array construction or std::to_array suffices when the caller only needs an array.

3.3. Modify the original points

The proposed translate takes Point& parameters to modify the caller’s points. A constrained reference pack already provides the same behavior for the named Point lvalues shown here:

Translating the caller’s Point objects through reference parameters.
Current C++ With homogeneous packs 
void translate(
    [[maybe_unused]] int dx,
    [[maybe_unused]] int dy,
    std::same_as<Point> auto&... points) {
    ((points.x += dx, points.y += dy), ...);
}

void translate(
    [[maybe_unused]] int dx,
    [[maybe_unused]] int dy, Point&... points) {
    ((points.x += dx, points.y += dy), ...);
}

The same call modifies the original objects with either definition:

void move_endpoints() {
    Point start{0, 0};
    Point finish{4, 5};

    translate(2, 3, start, finish);
    assert(start.x == 2 && start.y == 3);
    assert(finish.x == 6 && finish.y == 8);
}

The proposed form states ordinary Point& binding directly. Neither definition accepts translate(2, 3, {0, 0}) or a const Point argument. An initializer list of reference wrappers is another current-language option, discussed in § 4.3 Initializer lists.

3.4. Transfer ownership

translate borrows points. A queue instead takes ownership of its jobs:

struct Job {
    int id;
};

enqueue receives its std::unique_ptr<Job> arguments by value. The current definition constrains their deduced types, whereas the homogeneous declaration states the type directly:

Taking ownership of jobs before moving them into a queue.
Current C++ With homogeneous packs 
void enqueue(
    std::vector<std::unique_ptr<Job>>& queue,
    std::same_as<
        std::unique_ptr<Job>> auto... jobs) {
    (queue.push_back(std::move(jobs)), ...);
}

void enqueue(
    std::vector<std::unique_ptr<Job>>& queue,
    std::unique_ptr<Job>... jobs) {
    (queue.push_back(std::move(jobs)), ...);
}

submit_jobs transfers an existing job and one created at the call. The same call works with either definition:

void submit_jobs() {
    std::vector<std::unique_ptr<Job>> queue;
    auto first = std::make_unique<Job>(Job{1});

    enqueue(
        queue,
        std::move(first),
        std::make_unique<Job>(Job{2}));

    assert(!first);
    assert(queue.size() == 2);
    assert(queue[0]->id == 1 && queue[1]->id == 2);
}

Both definitions transfer ownership through by-value parameters. The proposed pack names their type directly and uses ordinary parameter initialization. The initializer-list alternative in § 4.3 Initializer lists moves through mutable wrapper members.

3.5. Choose a fixed or deduced element type

Fixing the destination type also chooses which conversions the interface accepts. sum_fixed fixes int, while total deduces one T from all applicable arguments unless the caller supplies it explicitly:

Fixed int in sum_fixed and a type parameter T in total.
Current C++ With homogeneous packs 
int sum_fixed(std::initializer_list<int> values) {
    return std::accumulate(
        values.begin(), values.end(), 0);
}

template <class T>
T total(std::initializer_list<T> values) {
    return std::accumulate(
        values.begin(), values.end(), T{});
}

void add_values() {
    sum_fixed({1, 2, 3});
    total({1, 2, 3});
    sum_fixed({});
    total<int>({});

    // Error: narrowing
    sum_fixed({1, 2.5});
    // Error: conflicting T
    total({1, 2.5});
    // Error: narrowing
    total<int>({1, 2.5});
}

int sum_fixed(int... values) {
    return (0 + ... + values);
}

template <class T>
T total(T... values) {
    return (T{} + ... + values);
}

void add_values() {
    sum_fixed(1, 2, 3);
    total(1, 2, 3);
    sum_fixed();
    total<int>();

    // Converts 2.5 to int
    sum_fixed(1, 2.5);
    // Error: conflicting T
    total(1, 2.5);
    // Converts 2.5 to int
    total<int>(1, 2.5);
}

The initializer-list versions of sum_fixed and total<int> reject 2.5 as narrowing, while the proposed function parameters permit its conversion to int. Neither total({}) nor the proposed total() can deduce T.

A std::convertible_to pack can also accept mixed source types while retaining the count. The constraint checks conversion availability and imposes semantic requirements without performing the conversions. The following implementation forwards each argument to an ordinary int parameter for conversion inside the body: [CXX-CONVERTIBLE]

template <class... Args>
    requires (std::convertible_to<Args, int> && ...)
int sum_converted(Args&&... values) {
    return (0 + ... + [](int value) {
        return value;
    }(std::forward<Args>(values)));
}

Both sum_converted(1, 2.5) and the proposed sum_fixed(1, 2.5) return 3. Accepting that conversion is a policy choice: the initializer-list interface rejects the loss of the fractional part.

In sum_converted, different deduced Args produce different specializations and conversion occurs inside the body. The proposed sum_fixed initializes its int parameters before entering the body. Calls with the same count select the same specialization regardless of their source argument types. The braced-initializer distinction appears in § 3.1 Pass existing points and braced initializers. [CXX-DEDUCTION-CALL]

3.6. Pack indexing

Homogeneous packs also use existing pack operations, such as C++26 pack indexing. A count constraint works in both forms:

Selecting a sample with a compile-time bounds constraint.
Current C++ With homogeneous packs 
template <std::size_t I>
double select_sample(
    std::same_as<double> auto... samples)
    requires (I < sizeof...(samples)) {
    return samples...[I];
}

template <std::size_t I>
double select_sample(double... samples)
    requires (I < sizeof...(samples)) {
    return samples...[I];
}

The caller supplies the index and deduction supplies the pack length. For a runtime double reading, select_sample<1>(reading, 0.5, 1.0) selects the second sample in either version. Index 3 fails the constraint.

3.7. Lambdas and function addresses

For a lambda that multiplies a varying number of double factors, the current definition constrains its deduced parameter types. The proposed form declares them directly:

A generic lambda with one numeric parameter type.
Current C++ With homogeneous packs 
auto product = [](
    std::same_as<double> auto... factors) {
    return (1.0 * ... * factors);
};

auto product = [](double... factors) {
    return (1.0 * ... * factors);
};

Both generic lambdas accept product(0.5, 0.8, 0.9). The proposed form also converts integer arguments to double.

To use the proposed sum_fixed as a callback that adds two integers, supply a pointer type with two int parameters. That target selects the corresponding specialization, as with existing variadic templates:

void use_callback() {
    int (*add_pair)(int, int) = sum_fixed;
    int combined = add_pair(2, 3);

    auto address = &sum_fixed; // Error: undetermined count
}

3.8. Existing packs keep their meanings

print_line still accepts text, integers, and other types through auto.... In make_receiver, the returned lambda expands the enclosing Ts into a fixed parameter list:

void print_line(auto... values) {
    (std::cout << ... << values) << '\n';
}

template <class... Ts>
auto make_receiver() {
    return [](Ts... values) {
        return sizeof...(values);
    };
}

void use_existing_packs() {
    print_line("count=", 3, ", ready=", true);

    auto receive = make_receiver<int, double>();
    receive(1, 2.5);
    receive(1); // Error: missing the double argument
}

3.9. Scope of this revision

This revision permits one trailing homogeneous pack, optionally preceded by ordinary parameters as in translate and enqueue. A C ellipsis cannot follow the pack. The following declarations do not meet those rules:

void misplaced(int... values, int last);
void two_packs(int... left, double... right);
void trailing_varargs(int... values, ...);

sum_fixed<3>(1, 2, 3) cannot specify the implicit count as a template argument.

A homogeneous pack declares parameters of the function itself or of a lambda’s call operator. The declarations using Callback = void(int... values); and void register_callback(void (*callback)(int... values)); remain ill-formed. Ordinary pack expansions in aliases and nested function types are unchanged.

4. Motivation and Scope

The examples combine ordinary initialization of separate parameters with a count available during template instantiation. Constrained packs, initializer lists, and typed array references offer different combinations of these properties.

  • The std::initializer_list interface states the accepted type, but limits mutability and requires braces around the arguments. With an explicit argument before the list, min’s precondition could be removed, but calls would still need the form min(a, { b, c, d }).
  • The SFINAE constraint requires every argument to have the same type, but makes the interface harder to read. Using is_same_v with a non-dependent parameter type can also reject desired conversions.
  • The Concepts form enforces the same equal-type requirement as the SFINAE form without the enable_if_t template parameter.

std::initializer_list::size() is constexpr, so the size of a list usable in constant expressions can be computed at compile time. An ordinary initializer-list function parameter does not supply a constant-expression count for a return type or constraint, even when the caller passes a fixed number of elements. sizeof...(x) instead gives the specialization’s pack length independently of the parameter values. [CXX-INITIALIZER-LIST] [CXX-VARIADIC]

A std::initializer_list provides access to an array of const elements and is passed as a single argument. Const reference wrappers still permit modification of the referenced objects: [CXX-INITIALIZER-LIST]

void translate(
    int dx, int dy,
    std::initializer_list<
        std::reference_wrapper<Point>> points) {
    for (Point& point : points) {
        point.x += dx;
        point.y += dy;
    }
}

For the objects in § 3.3 Modify the original points, translate(2, 3, {start, finish}) makes the same coordinate changes. The wrappers group the references into one list argument, while either parameter-pack form accepts separate arguments. [CXX-VARIADIC]

An initializer list also permits ownership transfer through user-defined wrappers with mutable members. Although the list elements are const, those members can be moved from: [CXX-INITIALIZER-LIST] [CXX-MUTABLE]

template <class T>
struct MutableWrapper {
    mutable T value;
};

void enqueue_wrapped(
    std::vector<std::unique_ptr<Job>>& queue,
    std::initializer_list<
        MutableWrapper<std::unique_ptr<Job>>> jobs) {
    for (const auto& job : jobs) {
        queue.push_back(std::move(job.value));
    }
}

void submit_wrapped_jobs() {
    std::vector<std::unique_ptr<Job>> queue;
    auto first = std::make_unique<Job>(Job{1});

    enqueue_wrapped(
        queue,
        {{std::move(first)},
         {std::make_unique<Job>(Job{2})}});
}

The caller supplies the list and wrapper braces and the implementation consumes the mutable members before the backing array expires. Initializer-list copies share those members so consuming through one leaves moved-from members visible through the others. The function’s interface still lacks a compile-time count. [CXX-INITIALIZER-LIST] [CXX-LIST-INIT]

Initializer-list constructors have priority under [over.match.list]. A homogeneous-pack constructor would participate in ordinary overload selection instead so replacing the list constructor can change the selected overload. [CXX-LIST-OVERLOAD]

Consider a container that accepts its initial elements through an initializer-list constructor:

template <class T>
class MyContainer {
public:
    MyContainer(std::initializer_list<T> elems);
    // ...
};

List-initialization selects this constructor:

// invokes MyContainer<int>::MyContainer(std::initializer_list<int>)
MyContainer<int> cont = {5, 10};

If homogeneous packs are permitted in constructors, the corresponding constructor would permit the same initialization:

Decide whether to permit homogeneous packs in constructors and test the examples under R2’s overload model, treating the constructor as an implicit template.

template <class T>
class MyContainer {
public:
    MyContainer(const T&... elems);
    // ...
};

// invokes MyContainer<int>::MyContainer(const int&, const int&)
MyContainer<int> cont = {5, 10};

Adding a constructor for a minimum and maximum changes which overload is selected for two elements:

template <class T>
class MyContainer {
public:
    MyContainer(const T&... elems);
    explicit MyContainer(const T& min, const T& max);
    // ...
};

// error: MyContainer<int>::MyContainer(const int&, const int&) is explicit
MyContainer<int> cont = {5, 10};

For exactly two elements, the additional constructor prevents selection of the homogeneous constructor regardless of initialization syntax. In the initializer-list version shown in the table below, list-initialization selects the std::initializer_list constructor. 5. Design Decisions

5.1. Definitions

A homogeneous parameter pack (or homogeneous pack) contains values of one type and its declaration introduces an independent count. A heterogeneous parameter pack (or heterogeneous pack) permits values of different types. Both terms apply to function parameter packs and template parameter packs.

A function parameter pack’s parameter pattern is its parameter declaration with the declarator ellipsis removed. For an auto... parameter, ordinary placeholder processing first invents a type parameter pack. [CXX-FUNCTIONS] A declaration is homogeneous only if its pattern contains no unexpanded pack after that processing. An ordinary expansion remains an ordinary expansion even when every resulting parameter type is the same.

5.2. Pack declarations

The same declarator syntax can express either an ordinary expansion or a new homogeneous pack:

// heterogeneous function parameter pack
template <class... T>
void f(T... v);

// homogeneous function parameter pack
template <class T>
void f(T... v);

The pattern need not mention a template parameter:

// homogeneous function parameter pack
void f(int... v);

A homogeneous function parameter pack makes the declaration an abbreviated function template. Its signature establishes that status before the body is parsed.

P1061R10 section 3.3 removed support for structured binding packs outside templates after objections to R9’s implicit template region, which covered the remainder of an ordinary function after a structured binding declaration. Here the signature declares the whole function a template. This distinction does not establish committee agreement on the proposal. [P1061R10]

In a function call, the pack’s size is deduced from the arguments. It must therefore appear in a deduced context, limiting a function template to one homogeneous pack at the end of its parameter list, with no following C ellipsis. Once its parameters are formed, the pack behaves like any other function parameter pack.

5.2.1. Abbreviated syntax

The February 2019 Kona EWGI poll in § 7 Straw Polls records support for R2’s named form, not acceptance of this revision or its wording. [P1219R2] [N4795] Since C++20, a function template that needs no template parameter names can use abbreviated syntax, with placeholders such as auto in its parameter list. [P1141R2] [CXX-FUNCTIONS]

The proposed counterpart is:

void foo(int... v);

If the homogeneous pack is the only reason the declaration is a template and its pattern contains no dependent names, the template has no formal template parameters. The template-head must then be omitted. An empty head would be unambiguous here, but the proposal disallows it on template declarations to avoid confusion with explicit specializations:

template <class T>
void foo(T... v); // #1 OK

// #2 OK, declares a template with an empty template parameter list
void foo(int... v);

// Error: function parameter pack in explicit specialization
template <>
void foo(float... v);

// OK, declares an explicit specialization of #2
template <>
void foo(int a);

// OK, declares an explicit specialization of #2
template <>
void foo<>(int a, int b);

// OK, declares an explicit specialization of #1
template <>
void foo<int>(int a, int b);

// OK, declares an explicit specialization of #1
template <>
void foo(float a);

The difference between deducing element types and fixing one type is visible in these declarations:

void a(auto... values) {}
void b(int... values) {}

The first already declares an abbreviated function template in C++26 and permits different deduced argument types. The second is ill-formed in C++26 and would declare a homogeneous pack with a fixed element type and an independently deduced count under this proposal. [CXX-FUNCTIONS] [CXX-VARIADIC]

The function template, its ordinary template arguments, and the pack length determine the specialization. Different counts identify different specializations. Converting arguments to a fixed element type does not add their original types to the specialization’s identity. These proposed uses therefore select the same two-parameter specialization:

void use_b() {
    b(1, 2);
    b(1.0, 2.0);
    void (*callback)(int, int) = b;
    callback(3, 4);
}

For the count two, b has the ordinary function type void(int, int). Function-type equality alone does not identify a specialization: different ordinary template arguments can produce the same adjusted function type. [CXX-DEDUCTION-GENERAL]

The programmer cannot name or explicitly supply the implicit count as a constant template parameter. An empty template-argument list does not specify the count either so it must still be deduced. The count does not make every expression in the function body dependent.

5.3. Lambdas

A homogeneous function parameter pack makes a lambda generic even when its element type is fixed, as in this product of int parameters:

auto a = [](int... v) {
    return (1 * ... * v);
};

An ordinary expansion of an enclosing pack does not by itself make a lambda generic, including when the element type uses pack indexing. [CXX-LAMBDA]

5.4. Pack indexing

For a type pack Ts, Ts...[1] selects its second type, which can serve as the proposed homogeneous pack’s element type. In the examples below, Is is a pack of indices. The expansion pattern of pack indexing is the pack name alone. In Ts...[Is], the indexed occurrence of Ts belongs to that expansion while Is remains available to an enclosing expansion. These C++26 rules apply to the proposed declarations as well. [CXX-VARIADIC] [CXX-PACK-INDEX]

The following is valid C++26. Each lambda has one unnamed parameter:

template <class... Ts, std::size_t... Is>
void indexed(std::index_sequence<Is...>) {
    (..., [](Ts...[Is]) {});
}

int main() {
    indexed<int, double, char>(
        std::index_sequence<2, 0, 2, 1>{});
}

The four indices select char, int, char, and double from the three types. Each indexed type is replaced in full by the selected type, with no ellipsis or bracket suffix left over.

5.4.1. Pairwise and Cartesian expansion

Pairwise expansion places both packs in one pattern and requires equal lengths. This current-language fragment pairs each type with one index constant:

(..., [](Ts, std::integral_constant<std::size_t, Is>) {});

This does not index Ts. By contrast, a Cartesian product requires separate nested expansions. This current-language fragment fixes one type before expanding all index constants:

template <class... Ts, std::size_t... Is>
void cartesian(std::index_sequence<Is...> indices) {
    (..., []<class T>(std::index_sequence<Is...>) {
        (..., [](T, std::integral_constant<std::size_t, Is>) {});
    }.template operator()<Ts>(indices));
}

With three types and four index entries, the nested expansions form twelve pairings. Equal-length packs or repeated identical types can conceal the distinction between selection and pairing. The existing equal-length requirement and innermost-expansion rule account for each operation without changing the meaning of indexing. [CXX-VARIADIC]

5.4.2. Homogeneous packs of indexed types

A second declarator ellipsis can introduce the proposed homogeneous pack when the index is a scalar. The indexed type is selected before the new pack’s independent count is deduced:

template <class... Ts>
auto selected_counter() {
    return [](Ts...[1]... values) {
        return sizeof...(values);
    };
}

For selected_counter<int, double, char>(), the proposed lambda accepts a deduced number of ordinary double parameters. That count is unrelated to the length of Ts.

To create homogeneous lambdas selected by different indices, pass each index to a helper as a scalar. The following example uses the proposed syntax:

template <class... Ts>
struct selectors {
    template <std::size_t I>
    static auto make() {
        return [](Ts...[I]... values) {
            return sizeof...(values);
        };
    }
};

template <class... Ts, std::size_t... Is>
auto make_selected(std::index_sequence<Is...>) {
    return std::tuple{selectors<Ts...>::template make<Is>()...};
}

Each resulting call operator has its own homogeneous count. The expansion of Is in make_selected supplies a scalar index to each specialization of make.

5.4.3. Array parameters

In C++26, the named declaration int... values[Is] expands Is into array bounds. The resulting array parameters undergo ordinary pointer adjustment. With positive extents 1, 2, and 3, the resulting function type has three int* parameters. Zero extents are independently invalid. [CXX-FUNCTIONS] [CXX-ARRAYS]

The C++26 [dcl.name] grammar has no array-suffix production for an abstract (unnamed) pack declarator. P2662R3 removed that production when introducing pack indexing. The named array declaration remains valid. [CXX-DECLARATORS] [P2662R3]

An enclosing fold around the named array-pack declaration has no unexpanded Is left because the parameter declaration already expands it.

The proposal retains the C++26 abstract-declarator grammar. If the committee approves reclamation, an array alias could supply an unnamed homogeneous parameter type with ordinary adjustment. Its array extent remains separate from the homogeneous count.

5.4.4. Empty packs and return types

An empty outer expansion over Is need not instantiate an indexed selection. A fixed index still needs to designate an element when its type is required. In the proposed homogeneous form, calling a lambda with zero arguments does not repair an invalid fixed selection in its declaration. [CXX-VARIADIC] [CXX-PACK-INDEX]

The lambda body { Ts...[Is]{}; } in the indexing table discards the constructed value and returns void. For the scalar types above, replacing it with { return Ts...[Is]{}; } deduces the selected scalar type under the C++26 return-deduction rules. [CXX-LAMBDA] [CXX-AUTO]

5.5. Captures

Constant template parameters can supply values inside a lambda without capturing automatic function parameter objects. This current-language program prints abc without a newline:

template <char... C, std::size_t... I>
void print_constants(std::index_sequence<I...>) {
    (..., [] {
        std::putchar(C...[I]);
    }());
}

int main() {
    print_constants<'a', 'b', 'c'>(
        std::make_index_sequence<3>());
}

The fold expands I and value pack indexing selects from C. Repeated indices 2, 0, 2, and 1 produce cacb. Homogeneous packs leave this program unchanged. [CXX-VALUE-PACK-INDEX] [CXX-VARIADIC]

In the proposed counterpart, characters names function parameter objects:

void print_characters(char... characters) {
    (..., [&] {
        std::putchar(characters);
    }());
}

These function parameter objects require capture. Value capture follows the ordinary copying rules. [CXX-CAPTURES]

The lambda can be omitted:

(..., std::putchar(characters));

Nested lambdas retain ordinary capture propagation. Reference capture does not extend a parameter’s lifetime. [CXX-CAPTURES]

5.6. Alternatives

None of the designs in this section is adopted by this revision. References to proposed behavior in their examples describe the alternative being discussed.

5.6.1. An additional auto marker

An alternative spelling int auto... values could mark the declaration as a template while keeping a fixed element type. It would require new grammar and an exception to the ordinary role of auto as a placeholder. A type name such as int is not a concept constraint. [CXX-AUTO]

Homogeneous template parameter packs already use std::size_t... values. Requiring std::size_t auto... values only for function parameters would give the two homogeneous declarations different spellings. This revision retains the unambiguous named form T... values. Its declarator ellipsis establishes template status.

5.6.2. Empty template heads

An alternative is to allow empty template parameter lists in template declarations:

// OK, declares a template with a homogeneous parameter pack
template <>
void foo(float... v);

Although this alternative is syntactically unambiguous, its resemblance to explicit specializations could confuse programmers. In an e-mail after the 2018 San Diego meeting, Richard Smith said he would oppose adopting homogeneous function parameter packs with this syntax. EWGI shared that view in the 2019 Kona poll recorded in § 7 Straw Polls. [P1219R2]

Combining empty heads on template declarations with omission of template <> on explicit specializations could reduce their resemblance and make template and non-template declarations more consistent.

5.6.3. Alternative specialization syntax

The template <> prefix makes an explicit specialization look like a template declaration. The function, class, and variable specializations considered here are ordinary non-template entities. A template-id can identify the specialization named in or deducible from the declaration, making the introducer redundant. [CXX-SPECIALIZATION]

This revision retains the existing explicit-specialization syntax. Under the alternative below, declarations could omit the template <> introducer without reducing expressivity:

// class template
template <class T>
class C;

// ok, explicit specialization (proposed: not deprecated)
template <>
class C<int>;

// proposed: explicit specialization
class C<int>;

// variable template
template <int V>
constexpr int v = V;

// ok, explicit specialization (proposed: deprecated)
template <>
constexpr int v<1> = 0;

// proposed: explicit specialization
constexpr int v<1> = 0;

// function template
template <class T, class U>
void f(T t, U u);

// ok: explicit specialization (proposed: deprecated)
template <>
void f<int, double>(int i, double d);

// ok: explicit specialization (proposed: deprecated)
template <>
void f<>(int i, double d);

// ok: explicit specialization (proposed: deprecated)
template <>
void f(int i, double d);

// proposed: explicit specialization
void f<int, double>(int i, double d);

// proposed: explicit specialization
void f<>(int i, double d);

// ok: ordinary function declaration (proposed: no change)
void f(int i, double d);

The spellings are alternatives. The two definitions of v<1> cannot appear together.

R2 assessed this alternative as follows in 2019: [P1219R2]

Under this approach, the misleading part of the syntax is removed, and the result is a more consistent language. Non-template entities no longer look like templates. For explicit specializations of function and variable templates, the old syntax can be deprecated. (The old syntax for explicit specializations of class templates probably cannot be deprecated at this time, as their use is very common.) Anecdotally, explicit specializations of function templates are rare and their use is generally discouraged due to subtleties around overloading.

EWGI in Kona in 2019 did not poll this option. R2 reports sentiment in favor of a separate paper exploring it. [P1219R2]

5.6.4. Explicit template markers

An alternative is to require a marker in the template parameter list for declarations with a homogeneous pack:

template <...>
void foo(int... v);

template <class T, ...>
void bar(T... v);

R2 reported the following implementation experience and discussions after the San Diego meeting in 2018: [P1219R2]

This idea, including the use of the ellipsis as the sigil, was suggested by Richard Smith in an impromptu conversation during the San Diego meeting. He and David Vandevoorde both indicated that this requirement would make the feature simpler to implement across a broad range of compilers. This notion is not directly supported by the experience of implementing the feature in Clang, but there is as yet no implementation experience with any other compiler. In Clang, the presence of an unparenthesized ellipsis in a declarator causes the compiler to treat the declaration as having a particular dependent type corresponding to a parameter pack, and the presence of a parameter of that type is enough to differentiate a function declaration as a template declaration instead of an explicit specialization or ordinary function declaration.

P1141R2, adopted in San Diego, adds support for function template declarations that lack a template head entirely; in this case, the presence of the auto keyword in the function parameter list indicates that the function declaration declares a function template. Any implementation that can handle these new declarations should also be able to handle homogeneous packs without added syntax. In a follow-up conversation with Richard over e-mail, he agreed with this conclusion. [P1141R2]

The corresponding lambda form would be []<...>(int... values) {}. A marker could declare the independent count and separately opt into revised unnamed-ellipsis parsing. Making a lambda generic alone does not change indexing or move Is between expansions.

This revision retains abbreviated declarations without an explicit marker. A marker would make template status visible before the parameter list, but it would not replace the rules for count deduction, specialization identity, or overload ordering. Adopting it would require separate grammar and an explicit decision about whether it changes unnamed-ellipsis parsing.

5.6.5. Bare template introducer

An alternative omits the angle brackets when no template parameters are needed:

template void foo(int... v);

This form resembles an explicit instantiation, which uses template without angle brackets but does not declare a template. [CXX-INSTANTIATION] Like the empty-head alternative, it remains unambiguous because the homogeneous pack identifies a template. R2 rejected this approach because a template declaration introduced by template requires an angle-bracketed parameter list. [P1219R2]

5.6.6. Explicit lengths

An alternative is to allow or require a template parameter for the size of the pack. The spelling considered in R2 predates pack indexing: [P1219R2]

template <std::size_t Len>
void foo(int...[Len] v);

A formal length parameter would allow callers to specify the pack length and make its role in specialization explicit. The proposed implicit count can only be deduced.

The language permits querying a pack’s size with sizeof..., but not specifying it explicitly. Explicit lengths could apply to homogeneous template parameter packs as well as homogeneous function parameter packs. Keeping lengths optional in both forms would preserve the existing template-pack spelling and give the two forms a consistent interface.

A type-pack variant spelled Ts...[Len] conflicts with C++26 indexed type selection: that spelling already selects one type from Ts. An explicit marker does not resolve that conflict by itself.

Constraints on sizeof... can restrict the implicit count. Explicit lengths, multiple homogeneous packs, and non-trailing homogeneous packs are deferred. Restoring removed abstract array-pack grammar would be a separate change.

5.6.7. Trivial templates

Extending the empty-template-head alternative beyond homogeneous packs would also permit templates with no template parameters and no homogeneous pack:

template <>
void foo(int n);

The empty-template-head alternative makes the template-parameter-list optional in a template-head to permit homogeneous packs with non-dependent types. It still requires at least one template parameter when there is no homogeneous pack. Relaxing that requirement would allow trivial templates with no template arguments or homogeneous pack count to vary between specializations. These would differ little from ordinary non-template entities, though a trivial function template could be defined in a header without inline.

This alternative also creates an ambiguity with explicit specializations:

// #1: trivial function template
template <>
void f(int v);

// #2: function template with homogeneous pack
template <>
void f(int... vs);

// #3: redeclaration of #1 or explicit specialization of #2?
template <>
void f(int v);

Apart from minor simplifications in the language specification, this alternative offers little beyond making []<>(){} well-formed, while introducing the specialization ambiguity above.

6. Reclaiming the deprecated comma-less spelling

We ask the committee to build on P3176R1 by reclaiming the deprecated comma-less spelling so homogeneous packs can use existing pack syntax with optional parameter names. Jan Schultke’s P3176R1, The Oxford variadic comma, continued the comma-separation work from P1219R2. It deprecated the comma-less spelling while retaining its meaning and standalone ellipsis parameters. [P3176R1] [P1219R2] [CXX-VARARGS-DEPRECATION]

If the committee approves reclamation, void send(int... values) and void send(int...) would declare the same function template. C varargs would retain the distinct spelling void send(int, ...).

Requiring pack names would avoid reclamation but add otherwise unnecessary names to declarations. An explicit marker (§ 5.6.4 Explicit template markers) could preserve optional names at the cost of extra syntax. A different spelling could avoid reuse but would depart from existing pack syntax.

The February 2019 Kona EWGI poll in § 7 Straw Polls supported making the varargs comma mandatory. [P1219R2] [N4795]

    ...

    parameter-declaration-listopt
    parameter-declaration-list , ...
    parameter-declaration-list ...

C++ introduced varargs ellipses with function prototypes and initially prohibited a comma before the ellipsis. C later adopted both features but required a comma to distinguish the last formal parameter from varargs. C++ then permitted the comma for C compatibility, leaving it optional. [P1219R2]

An ellipsis at the end of a function parameter list that could be part of an abstract (nameless) declarator declares a pack if the parameter’s type names an unexpanded template parameter pack or contains auto. Otherwise, it is a varargs ellipsis. [CXX-FUNCTIONS]

For example, these declarations have different meanings in C++26:

// declares a variadic function template with a function parameter pack
template <class... T>
void f(T...);

// same as void f(T, ...)
template <class T>
void f(T...);

6.2. Proposed change

Under the proposed rules, the second declaration would declare a homogeneous function parameter pack. Requiring a comma between a parameter list and a varargs ellipsis would make the disambiguation rule unnecessary while preserving C-compatible declarations.

Reusing the spelling would be a breaking change to source and link compatibility under SD-10. [SD10] The current declaration void send(int...) takes one int followed by C varargs. Its proposed homogeneous meaning would change accepted calls, initialization, function types, address-taking, and template linkage consequences. The explicit comma spelling void send(int, ...) retains its meaning. [CXX-FUNCTIONS]

R2 made the following migration argument in 2019: [P1219R2]

This is a breaking change, but likely not a very impactful one. In the parlance of P0684R2, this would be a "Very Good Change": Compilers can issue warnings in C++20 mode (or earlier) whenever the disambiguation rule is resolved in favor of a varargs ellipsis, and the warning can be resolved without any change in meaning by the addition of a single character. Moreover, the number of instances should be vanishingly small. In modern C++ code, the varargs ellipsis has largely been superseded by function parameter packs. Today, apart from SFINAE uses where the disambiguation rule doesn’t apply, the varargs ellipsis can mainly be found in header files that are intended to be consumed by both C and C++ code, in order to facilitate interoperability between the two languages. In these cases, the declarations must conform to the rules imposed by C syntax, and so they will already conform to the rules proposed here. Lastly, personal experience suggests that the vast majority of C++ users aren’t even aware that the comma preceding a varargs ellipsis is optional. [P0684R2]

P3776R1, More trailing commas, proposes trailing commas in function parameter lists but excludes them after C ellipsis parameters. Its proposed grammar preserves the distinction between function parameter packs and C ellipsis parameters. [P3776R1]

Agree with Jan on language modes, migration, and trailing-comma wording. Decide whether to remove the old meaning before or alongside homogeneous packs, or use different syntax. Check shared C/C++ headers, macros, and address-taking code. If reclamation is declined, specify a consistent explicit alternative. P3776R1

Reclamation would also require migrating the named comma-less form void send(int value...) to void send(int value, ...). The name cannot be moved across the ellipsis as an implicit reinterpretation.

6.3. The impact of a breaking change

The survey and Boost analysis below are retained from P1219R2 (2019), not a survey of current code. R2 reports that the ACTCD19 dataset at codesearch.isocpp.org (2019 archive) comprised 876,800,403 lines of source code across 2,489,599 files from open-source projects, citing the codesearch FAQ. The survey used it to estimate the impact of requiring a comma before a varargs ellipsis. [P1219R2] [CODESEARCH-FAQ]

The survey used regular expression searches and human review because a C++ parser with sufficient language support and build scripts for each project were unavailable.

Only headers with extensions .h, .hh, .hpp, or .hxx were considered. Preprocessor directives were stripped from each file before it was run through the C++ preprocessor to remove comments. Removing the macro definitions left invocations unexpanded. Inactive blocks, including #if 0, also remained. Scanning the output for ellipses yielded 258,196 lines, each tagged with its source file.

Lines with identifiers, operators, or other patterns characteristic of pack declarations or expansions were excluded from further analysis.

A comma immediately preceded an ellipsis in 89,614 lines, unambiguously declaring varargs functions.

Of 8,101 lines beginning with an ellipsis, 6,241 appeared to come from function declarations. Of those, 6,092 had a comma immediately before them on a preceding line. Of the remaining 149 lines, 131 were catch clauses or declarations with only an ellipsis. The last 18 mixed static-analysis macros into parameter lists. None of these ellipses is ambiguous with a pack declaration.

10. Conclusion

We seek agreement on one trailing homogeneous function parameter pack with ordinary parameter initialization and a compile-time count. Its declaration would be an abbreviated function template whose specializations have ordinary fixed-arity function types. Explicit lengths and multiple homogeneous packs remain out of scope.

We also seek a separate decision to reclaim the deprecated comma-less C-varargs spelling so parameter names remain optional. The named homogeneous form can proceed independently of that decision.
